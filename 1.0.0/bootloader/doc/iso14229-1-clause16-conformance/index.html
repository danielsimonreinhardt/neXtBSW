    Conformance with ISO 14229-1 clause 16 (non-volatile server memory programming)¶

    Status BL-24 (2026-09-22). This is a self-assessment of the neXtBSW boot software (bootloader/) and of the application UDS server (ecu/uds) against clause 16 of ISO 14229-1 (edition 2026), which defines what a programmable server has to support so that a conforming client can reprogram it.

    The standard itself is licensed and is not part of this repository (doc/confidential/, excluded by .gitignore). Nothing below quotes it: the rows name the clause, the table and the row, and describe our implementation in our own words. Read this next to the standard, not instead of it.

    How to read the status column

    Status Meaning
    met implemented and covered by an automated test named in the evidence column
    partial the required behaviour exists, but a named part of it is missing or differs; the difference is spelled out
    open not implemented, or only verifiable on hardware (then: "open, board evidence")
    n/a the requirement applies to a capability this ECU does not have

    Verification. Everything marked "met" is verified on the host (simulated flash and CAN, ISO-TP and UDS driven by udsoncan), never on the board. Evidence is given as <test group of tools/test>: <test method>. Rows that need a measurement or a physical fault injection say so and stay open until VER-* covers them on the board.

    1. Table 501 — what the boot software must answer while the network is being prepared¶

    The preprogramming step (16.3.1.1) quiesces the vehicle network before anything is flashed. Its rows apply to the boot software whenever the boot software is what answers - after a failed programming attempt, or when a boot request kept the ECU there. When the application is running it answers these rows instead, so both columns matter.

    Row (service, parameter, step) Boot software Application Evidence
    DiagnosticSessionControl, extendedDiagnosticSession (0x03), step (2) — mandatory met (BL-21). The session grants no rights of its own: security access, fingerprint, erase, download and transfer stay bound to the programming session met (OpenBSW DiagnosticSessionControl) bootloader-host: test_preprogramming_step_of_iso_14229_1_is_answered, test_extended_session_grants_no_programming_rights; app-uds-host: test_write_ram_identifier_only_in_extended_session
    CommunicationControl (0x28), controlType manufacturer specific (disable non-diagnostic communication), step (7) — mandatory met (BL-21). controlType 0x00..0x03, communicationType checked against Annex B.1 (message classes 1..3, subnet 0x0 and 0xF). No action is taken and no state is kept: the boot software sends and evaluates no application messages, so the positive response is all the standard asks for met (BL-21, COM-29). Here it really switches: the state reaches the ECU as "send" and "evaluate", and the send side acts on it — the diagnostic stack hands every change to the generated COM (rte::setApplicationTxEnabled(), tools/rtegen), which stops writing the cyclic application messages and brings them back in their own phase with the E2E counter one step on. The state is restored when the session ends. Evaluating received application messages (controlType 0x02/0x03) is still only carried. A request naming only network management messages is answered but changes nothing — this ECU has none bootloader-host: test_communication_control_subfunctions_and_negative_responses; app-uds-host: test_communication_control_switches_the_application_messages, test_session_end_restores_communication_and_dtc_updates; rtegen: RteCommControlHostTest
    ControlDTCSetting (0x85), DTCSettingType = off (0x02), step (5) — mandatory met (BL-21). On and off are answered; a DTCSettingControlOptionRecord is refused with requestOutOfRange, because without a fault memory there is nothing it could refer to. No action is needed: the boot software updates no DTC status bits partial. The service answers and carries the state, but there is no fault memory yet to freeze (NVM-03). An option record is refused with incorrectMessageLengthOrInvalidFormat rather than requestOutOfRange, because the application declares support for the two byte form only bootloader-host: test_control_dtc_setting_subfunctions_and_negative_responses; app-uds-host: test_control_dtc_setting_freezes_the_status_updates
    RoutineControl (0x31), manufacturer routine, steps (4) and (6) — optional partial. Step (4) "check programming preconditions" is covered by routine 0xF1A0 (BL-02; 0xFF02 up to boot software 0.3.3, BL-24): the client declares the target and memory layout of its image and the boot software refuses to erase or download on a mismatch. Step (6) "disable failsafe reaction" does not exist — the boot software runs no failsafe strategy n/a (the application hands over to the boot software before this step matters) bootloader-host: test_bootloader_blocks_programming_after_a_declared_mismatch, test_mismatching_image_is_rejected_before_erasing, test_compatibility_routine_in_the_supplier_range
    ReadDataByIdentifier (0x22), manufacturer identifiers, step (8) — optional met. 0xF180 boot software identification, 0xF189 software version, 0xF191 hardware number, 0xF18C ECU serial (chip UID), 0xF184 fingerprint, 0xF1A0 compatibility, 0xF1A1 security state. Since BL-22 the identification identifiers carry the numberOfModules byte of Annex C.1 (section 5) met (0xF180, 0xF181, 0xF186, 0xFD00) bootloader-host: test_identification_dids_come_from_one_source, test_target_compatibility_did; bl-security-host: test_uid_and_security_state_are_readable_in_the_default_session
    LinkControl (0x87), step (9) — optional, required for a bit rate switch n/a. No bit rate switch: the programming event runs at the CAN bit rate of the project, the same one the application uses. Implementing 0x87 would only be needed to speed up a download by switching bit rate mid-event n/a (same reason) —

This boot software has both permanently, so a client never needs to download them. That is the stricter of the two options and needs no further evidence.

    4. 16.4.1 — requirements for servers to support programming¶

    16.4.1.1 State of the pins during a programming session¶

    Requirement Status Basis
    In a programming session the server puts its pins into a defined, low-current state - as far as it can do so without endangering vehicle, server or people partial — open, board evidence Analysis. The boot software is only ever entered through a reset: a power-on reset, or the software reset the application performs after 10 02 (hal_boot_request_consume() reads RCM_SRS.SW). A system reset on Cortex-M returns every peripheral and every pin of the MCU to its reset state — inputs, output drivers disabled — which is the low-current default. The boot software then enables exactly two things: the CAN pins of the bootloader bus and, where the board has one, the SPI of a device hook. It drives no application output. What is not covered: outputs whose level is set outside the MCU — external drivers held by pull resistors, the outputs of the SBC itself, and any load that is switched on by default. Those are board facts and need a current measurement on the board, per board. Eval board S32K144 (VER-07, 2026-09-21, 12 V input, KL30B and power stage off): application idle 63.6 mA, boot software in the programming session without traffic 44.2 mA, during a download 44.3 mA - the programming session draws less than the application. There is also no hook today by which a board could name a safe output state for the programming session; adding one would touch blgen and platforms/, outside this task

    16.4.1.2 The boot software itself: protection of its partition and recovery¶

    Requirement Status Basis and evidence
    The boot memory partition is protected against inadvertent erasure met Software address range restriction: app_range_valid() accepts only BL_APP_START .. BL_APP_END, and the erase job additionally clamps the sector range to that window, so no UDS request can reach the boot software, the key sector or anything below the application. bl_sector_map_ok() checks at startup that the areas lie on sector boundaries and that the record sector is outside the application area. The boot software is replaced only by the separate updater application (bootloader/updater), never by the erase/download path the standard warns about. Evidence: bootloader-host: test_bootloader_area_and_record_sector_are_protected, test_hex_outside_the_application_area_is_refused; bl-security-host: test_key_sector_is_outside_every_erase_and_download
    Recovery after (c) disruption of data link communication met The erase job erases the validity record first, before the first application sector. From that moment the installed application is invalid, so any interruption leaves the ECU in the boot software on the next start. A vanished tester is also caught while the link is up: S3 returns the session to default. Evidence: bootloader-host: test_session_timeout_returns_to_default, test_corrupt_app_is_not_started, test_wrong_crc_does_not_validate
    Recovery after (a) loss of supplied power and (b) loss of the ground connection (a) met on the eval board; (b) open Eval board S32K144, boot software 0.3.1 (VER-07, BL-26, 2026-09-21): supply switched off at 52 % of a download and on again (real power-on reset, RCM_SRS 0x82) - the boot software answers on CAN at once, reports no valid validity record, and a new download completes with a correct check. Before BL-26 the boot software stayed unreachable on CAN after such a power-on (SBC read before its start-up time). (b) loss of ground was not injected: the debugger, the UART and the CAN adapter would feed the board back. Same mechanism as (c) and simulated as a power loss in the host tests (host_power_loss(), used by the security tests): the record is invalid, the boot software stays and can be reprogrammed. What the host cannot show is a partially programmed flash phrase caused by a supply collapse during a write — that needs the real flash controller and a switched supply on the board
    Recovery after (d) over- or under-voltage conditions met on the eval board between 6 V and 15 V Eval board S32K144, boot software 0.3.1 (VER-07, 2026-09-21): the supply was lowered from 12 V to 6.0 V and raised to 15.0 V (upper limit of the test rule) during a download - both downloads completed with a correct check. A brown-out below the reset threshold during a write behaves like (a). The boot software measures no supply voltage and has no undervoltage threshold of its own; it relies on the reset behaviour of the MCU and, on boards with one, of the SBC. Whether the ECU always comes back reprogrammable from a brown-out during a write is a board measurement, per board. bl_board_environment_ok() exists only for the updater (external watchdog off), not as a voltage check

    16.4.1.3 Security requirements¶

    Requirement Status Basis and evidence
    A seed and key feature via SecurityAccess protects against inadvertent erasure and unauthorized programming met Seed 16 bytes, key = HMAC-SHA256(device key, seed), device key = HMAC-SHA256(master key, chip UID), so no two chips share a key and the boot software image itself carries none. Failed attempts and the lockout survive a reset. Evidence: bl-security-host: test_device_key_and_record, test_the_uid_decides_the_device_key, test_every_byte_of_the_key_counts, test_repeated_key_and_key_of_an_older_seed_are_refused
    Field service replacement servers are shipped with the security feature activated met Stricter than asked: a chip whose key sector is erased, half written or holds a foreign record has no security access at all — 0x27 answers conditionsNotCorrect and DID 0xF1A1 says why. An unprovisioned device therefore cannot be programmed over CAN at all, rather than being programmable without a key. Evidence: bl-security-host: test_without_device_key_the_security_access_is_refused_with_a_clear_message, test_damaged_or_foreign_record_counts_as_no_key

    5. 16.4.2 — software and data identification, fingerprints (Annex C.1)¶

    Annex C.1 prescribes for the three identification identifiers that the first byte of the record is the number of reported modules; the rest of the structure is manufacturer specific. For the three fingerprint identifiers the whole content is manufacturer specific.

    Identifier Status Note Evidence
    0xF180 bootSoftwareIdentification met (BL-22) Answered by boot software and application as 01 (numberOfModules) followed by the identification text "<prefix> <version>" of that one module. The text is unchanged and, deliberately, unchanged in flash as well: the byte is put in front of it while the response is built, never stored. That keeps the three places that find a bootloader by searching its flash for the text working - the application (COM-11), the updater's upd_check_blob() and canflash blimage. Transition: every device flashed before BL-22 answers the bare text, so canflash reads both forms (parse_identification(), first byte 0x01..0x1F = a module count, 0x20 and above = the first character of a text) and names the old one in its output. Such a device stays readable and flashable; the reverse case, a tester from before BL-22 against a BL-22 server, only loses the version comparison of blupdate, so update the tester first bootloader-host: test_boot_software_identification_carries_the_number_of_modules, test_an_ecu_from_before_bl_22_is_read_and_flashed, test_the_two_identification_forms_read_back_the_same, test_identification_dids_come_from_one_source; app-uds-host: test_identification_identifiers_carry_the_number_of_modules, test_canflash_reads_both_forms_of_an_identification; canflash-tool: IdentificationFormTest
    0xF181 applicationSoftwareIdentification met (BL-22) Application only, same form as 0xF180: 01 and the application's identification text. It is a constant of the build, not read from flash, so nothing searches for it and the transition costs nothing here app-uds-host: test_identification_identifiers_carry_the_number_of_modules, test_read_identifiers, test_multi_frame_response_and_request_flow_control
    0xF182 applicationDataIdentification n/a There is no application data module separate from the application software: one image, one validity record. The identifier would have nothing to report —
    0xF183 bootSoftwareFingerprint open (optional) The boot software is not written through the UDS programming path but by the updater application, so no fingerprint is recorded for it. Worth having once bootloader updates are routine — the updater would have to carry it into the record —
    0xF184 applicationSoftwareFingerprint met 4 bytes date (BCD) plus 12 bytes tester identification. Required before the first erase and the first download, not merely accepted; written into the validity record by routine 0xFF01, so it survives the reset and can be read back from the installed application (BL-10) bootloader-host: test_fingerprint_is_written_and_read_back, test_fingerprint_survives_the_reset_in_the_record, test_fingerprint_of_the_wrong_length_is_refused, test_download_without_fingerprint_is_refused
    0xF185 applicationDataFingerprint n/a Same reason as 0xF182 —
    Write operations to the identification identifiers are rejected met The boot software's 0x2E accepts 0xF184 and nothing else (requestOutOfRange otherwise); the application's 0x2E accepts 0xFD00 and nothing else bootloader-host: test_unknown_data_identifier_is_refused; app-uds-host: test_write_ram_identifier_only_in_extended_session

    6. 16.4.3 / Table 504 — server routine access¶

    Routine Status Note Evidence
    0xFF00 eraseMemory (standardized) met Control option record 44 plus address and length, checked against the application area and walked sector by sector from the generated sector table (PLAT-16). "Response pending" (0x78) follows the timing rules of section 7: P2* only has to cover one sector, and the 0x78 are spaced as ISO 14229-2 asks (BL-25; before, one was sent before every sector) bootloader-host: test_erase_follows_the_sector_table, test_erase_of_one_byte_erases_exactly_its_sector, test_response_pending_covers_long_sector_erases, test_fast_sector_erases_get_one_response_pending
    0xFF01 checkProgrammingDependencies (standardized value, record format of the manufacturer) met CRC-32 over the downloaded image, plausibility of the application entry by the family hook, then the validity record including the fingerprint bootloader-host: test_wrong_crc_does_not_validate, test_application_start_refused_by_the_family_is_not_started
    0xF1A0 check compatibility (system supplier range 0xF000..0xFEFF of Annex F.1) met (BL-24) The client declares target identity and memory layout of its image before erasing (BL-02); after a mismatch the boot software refuses erase and download itself. The same number as DID 0xF1A0, which reads back what the routine compares. The response repeats the identifier of the request bootloader-host: test_compatibility_routine_in_the_supplier_range, test_bootloader_blocks_programming_after_a_declared_mismatch, test_canflash_declares_with_the_new_routine, test_unknown_routine_and_wrong_length; canflash-tool: CompatRoutineTest
    0xFF02 (reserved by Annex F.1; formerly another standardized routine) partial (transition) Up to boot software 0.3.3 this was the compatibility check. Since 0.3.4 (BL-24) the boot software still answers it as the same check with the same state, so a tester from before BL-24 keeps flashing. canflash sends it only to boot software that reports a version below 0.3.4 in 0xF180 (the eval board ran 0.3.1 on 2026-09-22), and after a requestOutOfRange when the target names no version. A conforming tester that uses the reserved value for something else would reach the compatibility check - that is what stays partial until the transition ends (open point 10) bootloader-host: test_former_compatibility_routine_is_still_answered, test_mismatch_declared_with_the_new_routine_is_released_by_the_former, test_an_ecu_from_before_bl_24_is_flashed_with_the_former_routine, test_the_last_version_before_bl_24_gets_the_former_routine, test_without_identification_the_former_routine_follows_a_refusal; bl-update-mutations: six BL-24 mutations

    7. ISO 14229-2 clause 9 — server timing during flash jobs (BL-25)¶

    Clause 16 of part 1 leaves the timing of the programming services to part 2. The rows below are the ones a flash job of the boot software touches; the values are bl_config.h (P2 50 ms, P2* 5000 ms, announced in the response to DiagnosticSessionControl).

    Requirement (ISO 14229-2:2021) Status Basis and evidence
    9.1.1 / 9.2 Table 4: a request whose final response cannot follow within P2 is answered with NRC 0x78 first, and every further response of that request follows within P2* of the previous one met (host) Every flash job (erase, check, TransferData) starts with a 0x78. Before each further step the core predicts its cost from the steps measured so far (erase per KB and sector size, other steps as the longest of the job; an unmeasured step counts as the longest a step may be) and sends a 0x78 when the step could end beyond P2. Evidence: bootloader-host: test_response_pending_covers_long_sector_erases (4-KB and 128-KB sectors of up to 4.1 s, no pause beyond P2), test_full_flash_cycle_then_app_starts
    9.2 Table 4, note b (valid for the programming session by 9.5): consecutive 0x78 of one request at least 0.3 x P2*_Server_Max apart met (host); board evidence open BL_PENDING_MIN_GAP_MS = 0.3 x BL_P2STAR_SERVER_MS, derived in bl_config.h. A step that would need a 0x78 sooner waits for the gap instead; every step fits into P2* behind a fresh 0x78, so waiting is safe. Before BL-25 the erase job sent one before every sector: every 4 ms on the board (2026-09-21, 45 frames for 41 already blank sectors; a sector with content takes about 42 ms, TOOL-48). Evidence: bootloader-host: test_fast_sector_erases_get_one_response_pending, test_response_pending_covers_long_sector_erases (spacing of every 0x78 checked in all five memory layouts)
    9.2 REQ 5.19: the server processes a new request right after the transmission of the previous response met (host); board evidence open The CAN transport accepts the next request as soon as the core has released the previous one; the receive timers work on one time base per poll (BL-25), so a message of any length up to maxNumberOfBlockLength is no longer dropped by a spurious N_Cr timeout. Evidence: bootloader-host: test_transfer_data_of_maximum_length_frame_by_frame, test_download_with_maximum_block_length_and_asynchronous_tick
    9.5 REQ 5.25, Table 6: tS3_Server is stopped when a request starts (first frame of a segmented request, or a single frame) and started again when the final response has been transmitted (a 0x78 does not restart it), when the action is complete if no response is sent, or when the reception of a segmented request ends in an error met (host); board evidence open Since BL-29 (boot software 0.3.2): the transport reports a request from its first frame until the core releases it (bl_transport_rx_pending(), CAN: ISO-TP receive state), and uds_poll() holds S3 while that is true, while a job runs and until the response has left the transport. Before, S3 ran from the moment the previous request was complete, also during the reception of the next block and during a long flash job: a block that needed longer than S3 to arrive got NRC 0x24 (VER-07, STmin 1 ms on a Windows tester), and a job longer than S3 lost the session with its positive response. The link transport (BL-15) implements the same function from the receive state of mcuLink (open point 9). Evidence: bootloader/test/host/test_bl_s3_host.py in three memory layouts - a 1026-byte block over 1.2 x S3 is programmed, S3 starts with the final response and still expires, an N_Cr error restarts it, an erase of 1.2 x S3 keeps the session
