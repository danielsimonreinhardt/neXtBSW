    Reference¶

    Look-up material: every key of the configuration files, with type, unit, whether it is required, its default, the values it accepts and what it means. The pages are generated from the schema in tools/nxconfig/model.py and checked in; a test fails as soon as schema and pages disagree. For how the levels fit together, read architecture overview, section 3 first.

    The driver and service modules have a page of their own, see Modules.

    Page Level File Fields Objects
    Derivative description Derivative mcudb/<family>/<derivative>.yaml, mcudb/<family>/<part>.pinmux.yaml 254 44
    Board description Board boards/<board>/board.yaml 230 47
    Project description Project projects/<project>/project.yaml 221 46
    Diagnostic description (diag.yaml) Project projects/<project>/diag.yaml 241 40
    ECU description (rte.yaml) Project projects/<project>/rte.yaml 39 8

    Modules¶

    Modules - the catalogue of the 15 modules in libs/bsw (device drivers, services, libraries) and the 6 in libs/bsp (contracts, MCU drivers), plus the 6 with a manifest in the ports (platforms/<family>/port, ecu/platforms/<board>): purpose, the board.yaml and project.yaml keys each one reads, host tests and the stated verification with its note. Generated from the module manifests (module.yaml), the module documentation and tools/test/tests.yaml by the same command and checked by the same --check. All 27 modules have a manifest, 1 of them parked (module.yaml.pending). Verification stated: hardware 13, mock 14; every module states it. What is still missing is listed in the section Gaps and by --gaps.

    Console¶

    Console commands - the 30 command groups (114 commands) the application can register on its text console: syntax, purpose, the build or module each one needs, which groups each project gets and which commands need a person at the board. Generated from the command registration and help texts in the C++ sources, the CMake conditions, the module manifests, the projects and the board READMEs by the same command and checked by the same --check.

    How to read the tables¶

    Each object of a file has its own table; the heading is the YAML path of the object, [] stands for an entry of a list and <key> for a key of a map. Columns:

    • Field - full YAML path of the key.
    • Type - integer, number, string, boolean, list of …, map of … to …, or a link to the table of a nested object. A type written one of …, selected by kind means the key kind decides which table applies.
    • Unit - from the schema's naming convention <name>_<unit> (system_hz, deadtime_ns, shunt_uohm, t_nominal_ddegc in 0.1 °C) or from an explicit unit in the schema. none marks a number that has no physical unit on purpose (counts, indices, identifiers, addresses, selector and register values); missing marks a numeric field whose unit the schema does not state yet - a gap to be closed in the schema.
    • Required - yes if the key must be present. Optional keys take the default when left out.
    • Default - value that applies when the key is left out, written as YAML. null means not set; what that implies is in the description.
    • Allowed values - enumerations and the limits the schema enforces (ranges, lengths, patterns). item:, key: and value: apply to the entries of a list or map.
    • Description - from the schema: the description or comment of the field, otherwise the first sentence of its object type. missing in schema marks a field the schema does not explain. Nothing is filled in by hand: a gap here is a gap in the schema, and it is closed there.

    Two short forms: an object whose table equals an earlier one (routines[].stop next to routines[].start) points to it and keeps its anchor. An object of the power stage or motor control is marked after R1: it stays in the schema and is checked, but is not part of the first release, so its page entry lists only the keys.

    Not in these tables: rules that span several keys or files - references between levels, resource conflicts, derivative limits. Those are checked by tools/nxconfig (checks.py and the model validators) and reported with file, line and YAML path.

    Regenerating¶

    .venv/Scripts/python tools/docgen            # rewrite the pages from the schema, from libs/ and from the console sources
.venv/Scripts/python tools/docgen --check    # exit 1 and name the pages if they are stale
.venv/Scripts/python tools/docgen --gaps     # list schema fields without description or unit, module and console gaps

    The output is deterministic (no time stamps, schema order), so the check never fails without a change.
