    Modules¶

    Every directory in libs/bsw (device drivers, services, libraries), libs/bsp (contracts and MCU drivers) and every module with a manifest in a port (family port templates platforms/<family>/port, board ports ecu/platforms/<board>), with what it is for, which configuration keys it reads, which host tests cover it and how far it is verified. The page is generated from the module manifests (module.yaml), the module documentation under doc/ and the test list tools/test/tests.yaml; a test fails as soon as page and sources disagree. How drivers are cut into modules: driver granularity (German). What the configuration keys mean: board description and project description.

    • Purpose - the description of the manifest. not stated means there is no manifest or it has no description.
    • Manifest - module.yaml is read by tools/nxconfig and tools/bswgen; a parked module.yaml.pending is not, so such a module cannot be used by a project yet.
    • Host tests - entries of tools/test/tests.yaml that list a file in the module directory under covers or name the module under modules (tests that lie elsewhere, e.g. in a generator's test directory; tools/test refuses a name without a manifest); run one with .venv/Scripts/python tools/test -k <name>.
    • Verification - the manifest field verification: none (not yet), mock (host tests, register models, generator and build tests) or hardware (behaviour confirmed on a real board), with the sentence verification_note on what is confirmed on a board and what is not (linked as note in the table, in full in the module section). Both are set by hand from the changelog; nothing here is inferred from the changelog or the module documentation, a module without the field reads not stated.

    All 27 modules have a manifest, 1 of them parked (module.yaml.pending). Verification stated: hardware 13, mock 14; every module states it. What is missing per module: Gaps.

    Device drivers and services (libs/bsw)¶

    autosarBase¶

    AUTOSAR base types Std_Types.h, Platform_Types.h and Compiler.h for the RTE and the generated component code (32-bit ARM Cortex-M and Cortex-R, little endian)

    • Directory: libs/bsw/autosarBase, manifest: module.yaml, kind: library
    • Verification: mock - Type definitions only; sizes, signedness, limits and CPU macros checked by a host type test and by arm-none-eabi-gcc -fsyntax-only for Cortex-M4F, Cortex-M0+ and Cortex-R4 (ARCH-45), type identity with <stdint.h> (ARCH-46), besides compiling the target builds.
    • Public headers: Compiler.h, Platform_Types.h, Std_Types.h
    • Integration: CMake target autosarBase

    bccMc33771 (after R1)¶

    NXP MC33771C battery cell controller (7-14 cells) in SPI mode, complex device driver (IO-06)

    After R1: not part of the first release. Directory libs/bsw/bccMc33771 (not published, available on request), manifest: pending (module.yaml.pending). Keys, parameters and verification are listed once the module is released.

    canPhyPassive¶

    CAN transceiver without software control (mode pins strapped by the board), always ready

    • Directory: libs/bsw/canPhyPassive, manifest: module.yaml, kind: device_driver
    • Verification: mock - Covered by generator and target build tests only (build profile S32K148, D-CAN of the eval board); no bus through a passive transceiver has been checked on a board yet.
    • Public headers: can/PassiveCanPhy.h
    • Provides roles: can_phy
    • Integration: CMake target canPhyPassive
    • Board configuration (board.yaml):
      • devices[].part matching SN65HVD1050*, TJA1051* - one instance per board device; devices[].module: canPhyPassive chooses this module where several modules serve the part
      • can[].phy - the CAN buses the device is the transceiver of (role can_phy)
    • Project configuration (project.yaml):
      • use.can - the transceiver role is served for the CAN buses the project uses

    canSystem¶

    CAN buses of the ECU; hardware independent parts - transmit gate (CanPhyGate, follows the readiness reports of the phy providers through CanPhyReadiness, COM-23) and bus state with bus off counters (CanBusMonitor, COM-12), console commands in the console context with a short call into the CAN task (ContextCall, COM-24), receive log lines that fit one logger entry (CanFrameLog, COM-25), behaviour after bus off with log series, doubling pause and dropping pending frames (CanBusOffRecovery, COM-35; project values per bus can.<bus>.bus_off, COM-37)

    • Directory: libs/bsw/canSystem, manifest: module.yaml, kind: service
    • Verification: hardware - Transmit gate, bus state up to error passive and the console commands with their short call into the CAN task are confirmed on the eval board on CAN0; bus-off and a second bus are covered by host tests only.
    • Public headers: can/CanBusOffRecovery.h, can/CanBusOffReport.h, can/CanBusState.h, can/CanChannelStatus.h, can/CanFrameLog.h, can/CanPhyGate.h, can/CanPhyReadiness.h, can/CanSupervisionCycle.h, can/ContextCall.h
    • Provides roles: can_system
    • Requires: can_phy × 1
    • Integration: lifecycle level 2 in task can, console command group can, CMake target canSystem

    dem¶

    Fault memory (simplified AUTOSAR DEM) - ISO 14229-1 status byte, counter and time debouncing with fault detection counter, enable conditions, operation cycles, confirmation, aging, snapshots and extended data, persistent through the NvM; no warning lamp, no OBD

    • Directory: libs/bsw/dem, manifest: module.yaml, kind: service
    • Verification: mock - Status byte, debouncing, confirmation, aging, overflow and persistence are covered by host tests with deliberate faults; the board check (DTCs set by the NTC and by the missing PC_Command message, kept over a power cycle) is open.
    • Public headers: dem/Dem.h, dem/DemTypes.h, dem/EventReporter.h, dem/IFaultMemory.h, dem/OccurrenceReport.h, dem/SafetyResetReport.h, dem/StartReport.h
    • Integration: console command group dem, CMake target dem

    ecuState¶

    ECU state management Startup/Run/Standby/Rundown/Shutdown/Sleep on top of the OpenBSW lifecycle; uses the role power_supply (0..1, without provider the supply is permanent)

    • Directory: libs/bsw/ecuState, manifest: module.yaml, kind: service
    • Verification: hardware - Run, standby with withdrawal, run-down, sleep and the start after a CAN wake-up are confirmed on the eval board; local and cyclic wake-up and the run-down step time-outs are covered by host tests only.
    • Public headers: ecuState/DirectReset.h, ecuState/EcuState.h, ecuState/EcuStateController.h, ecuState/EcuStateIntegration.h, ecuState/EcuStateMachine.h, ecuState/EcuStateRte.h, ecuState/IOutputFlush.h, ecuState/IPowerSupply.h, ecuState/IShutdownStep.h, ecuState/McuStartReasons.h, ecuState/PermanentPowerSupply.h
    • Provides roles: ecu_state
    • Integration: lifecycle level 1 in task bsp, console command group ecu, CMake target ecuState
    • Project configuration (project.yaml):
      • modules.ecuState.<parameter> - one entry per project, parameters below
      • use.can - parameters that name CAN buses accept only buses of use.can
    Parameter Type Unit Default Allowed values Description
    min_run_ms int ms 5000 0 .. 3600000 RUN at least this long after the start before a sleep request is served (diagnostic access, reflashing after a wake-up)
    post_run_ms int ms 2000 0 .. 3600000 STANDBY (post-run) before the run-down, the application runs on and can withdraw the request
    shutdown_timeout_ms int ms 5000 100 .. 3600000 lifecycle shutdown not finished within this time -> restart. Also the bound of the restart itself (SYS-173): the lifecycle has not reached level 0 within this time after the restart request -> direct reset of the MCU
    sleep_timeout_ms int ms 2000 101 .. 3600000 MCU still running this long after the power down request -> restart (more than POWER_DOWN_DELAY_MS 100 ms)
    nvm_timeout_ms int ms 1000 10 .. 3600000 step NvM of the run-down: writing the non-volatile data not finished within this time -> see step_error. Without a NvM provider the step is reported as not present (NVM-01 is blocked) and the limit never applies
    can_stop_timeout_ms int ms 500 10 .. 3600000 step CAN of the run-down: stopping the transmission and leaving the transceivers ready for a wake-up not finished within this time -> see step_error
    wakeup_can str all pattern all\|none\|[A-Za-z][A-Za-z0-9_]*(,[A-Za-z][A-Za-z0-9_]*)*, names: can_bus CAN buses that may wake the ECU: all (every bus of the project), none, or a comma separated list of bus names of the project (board can[], one wake-up bit per bus, ARCH-07)
    wakeup_local str none pattern all\|none\|LOCAL[0-7](,LOCAL[0-7])*, names: any local wake-up inputs of the power supply that may wake the ECU (SBC UJA113x: WAKE/HVIO pins, bank 0 of register 0x37). Default none, because an input that is not wired on the board wakes the ECU at random
    wakeup_cyclic_ms int ms 0 0 .. 3600000 cyclic wake-up (wakeup::TIMER): 0 off, otherwise the requested period. The supply rounds it up to its own grid (SBC UJA113x: watchdog periods 8..4096 ms in Sleep) and reports the value it really uses
    wakeup_during_shutdown str restart pattern restart\|sleep wake-up event during RUNDOWN/SHUTDOWN, restart (evaluate it in a new start) or sleep anyway
    after_watchdog_reset str run pattern run\|sleep start after a watchdog reset, run (application decides) or sleep without request
    step_error str restart pattern restart\|continue a run-down step failed or ran into its time limit: restart the ECU (a half prepared ECU must not sleep) or continue and note the step. Never continued: the NvM step (SYS-174, a data flash write must not meet the power down) - tools/rtegen refuses continue for a project with NvM blocks or data flash areas

    highSideSwitch¶

    Smart high-side switch with input IN, diagnosis enable DEN and current sense IS (PROFET-like)

    • Directory: libs/bsw/highSideSwitch, manifest: module.yaml, kind: device_driver
    • Verification: hardware - Current sense, overcurrent switch-off with latch, open load and the off check are confirmed on the eval board (BTS5030-1EJA, electronic load); the fault current threshold needs a real device fault and is covered by host tests only.
    • Public headers: highSideSwitch/HighSideSwitch.h, highSideSwitch/HighSideSwitchBinding.h, highSideSwitch/HighSideSwitchChannel.h, highSideSwitch/HighSideSwitchConsole.h, highSideSwitch/HighSideSwitchIntegration.h, highSideSwitch/HighSideSwitchNames.h, highSideSwitch/HighSideSwitchSafeOff.h, highSideSwitch/HighSideSwitchSense.h, highSideSwitch/HighSideSwitchSystem.h, highSideSwitch/IHighSideSwitchIo.h
    • Provides roles: switched_output
    • Integration: lifecycle level 1 in task bsp, console command group per instance (parameter console), CMake target highSideSwitchSystem
    • Board configuration (board.yaml):
      • devices[].part matching BTS5030-1EJA - one instance per board device; devices[].module: highSideSwitch chooses this module where several modules serve the part
      • devices[].connect.in -> an entry of dio.outputs[] (digital_output, switched off first by the fault handlers): input IN (switch on)
      • devices[].connect.den -> an entry of dio.outputs[] (digital_output): diagnosis enable DEN (IS active)
      • devices[].connect.is -> an entry of adc[] (analog_input): current sense IS; the board's adc[].sensor of this channel converts it into the load current in mA (highside_is: k_ILIS, R_IS)
    • Project configuration (project.yaml):
      • modules.<device>.<parameter> - one entry per board device served by this module, parameters below

    cycle_ms int ms 10 1 .. 1000 supervision period

    Port modules (platforms/<family>/port, ecu/platforms/<board>)¶

    Modules that belong to one MCU family or one board and therefore live in its port. tools/nxconfig reads their manifests only for a project whose derivative is of that family or which runs on that board (port_module_dirs in tools/nxconfig/config.py); a second family brings its own module for the same parameters.

    capture¶

    Period and duty cycle measurement of a PWM input (FTM dual edge capture), values and quality for the RTE

    • Directory: platforms/s32k1xx/port/bspConfiguration/src/bsp/capture, manifest: module.yaml, kind: mcu_driver
    • Port: family port platforms/s32k1xx/port - loaded by tools/nxconfig for the projects whose derivative belongs to this family
    • Verification: mock - On the eval board only the time-out without an input signal is confirmed; period, duty cycle and the range checks are covered by generator and host tests only.
    • Provides roles: input_capture
    • Project configuration (project.yaml):
      • modules.capture.<parameter> - one entry per project, parameters below
    Parameter Type Unit Default Allowed values Description
    min_frequency_hz int Hz 50 1 .. 10000000 lowest frequency the measurement has to cover. The counter prescaler of the timer follows from it: one period of this frequency has to fit into half the counter range, so that a measurement never becomes ambiguous. A lower value means a longer measurable period and a coarser resolution; a measured period outside the range is reported as a quality error, never as a value. How low it can be depends on the counter clock (largest prescaler 128 times the 16-bit counter); the generator says so if it is too low.
    timeout_ms int ms 200 1 .. 60000 time without a completed measurement after which the quality becomes QLF_ERROR_TIMEOUT (missing signal, constant level, frequency below the range). It has to cover two periods of min_frequency_hz plus one update cycle, otherwise a healthy slow signal would be reported as missing.
    update_period_ms int ms 10 1 .. 10000 cycle in which the application calls InputCapture::update() (the period of the RTE task that reads the capture values). The counter of the timer must not wrap twice between two calls, otherwise a slow signal could be measured as a fast one; the generator checks this against the derived prescaler and refuses the combination instead of measuring wrongly.

    Rules between the parameters (checked by tools/nxconfig): timeout_ms > update_period_ms.

    hall¶

    Three digital Hall signals of a brushless motor (state, sector, period, speed, direction and quality), measured in the pin interrupt of the port with a time stamp per edge

    • Directory: platforms/s32k1xx/port/bspConfiguration/src/bsp/hall, manifest: module.yaml, kind: device_driver
    • Port: family port platforms/s32k1xx/port - loaded by tools/nxconfig for the projects whose derivative belongs to this family
    • Verification: mock - Host tests only (decoder and pin interrupt access against two profiles); no Hall sensor or signal source has been connected to a board yet.
    • Provides roles: hall_sensor
    • Integration: CMake target bspHall
    • Board configuration (board.yaml):
      • devices[].part matching hall3, hall3_* - one instance per board device; devices[].module: hall chooses this module where several modules serve the part
      • devices[].connect.u -> an entry of dio.inputs[] (digital_input): Hall signal of phase U (H1)
      • devices[].connect.v -> an entry of dio.inputs[] (digital_input): Hall signal of phase V (H2)
      • devices[].connect.w -> an entry of dio.inputs[] (digital_input): Hall signal of phase W (H3)
    • Project configuration (project.yaml):
      • modules.<device>.<parameter> - one entry per board device served by this module, parameters below
    Parameter Type Unit Default Allowed values Description
    arrangement str deg120 pattern deg120\|deg60 electrical angle between the Hall sensors. deg120 (the usual brushless arrangement) has the six valid states 100, 110, 010, 011, 001, 101 in that order and reports 000 and 111 as invalid; deg60 has the six valid states 111, 110, 100, 000, 001, 011 in that order and reports 010 and 101 as invalid. The generator turns the choice into the sector table, so no state list is written down twice.
    pole_pairs int required 1 .. 64 pole pairs of the motor: one mechanical revolution is this many electrical revolutions. The mechanical period and the speed use it, state, sector and the electrical period do not. There is no default - it is a fact of the motor, not a value to guess.
    forward str sector_up pattern sector_up\|sector_down which way through the sector sequence of arrangement is reported as direction +1. sector_up is the documented order above (U -> V -> W); sector_down mirrors it, for a motor whose phase order or sensor order is the other way round. It only changes the sign of hall.<Sensor>.direction, never the sector numbers, the period or the speed.
    min_speed_rpm int rpm required 1 .. 200000 lowest mechanical speed that still has to be measured. The generator checks standstill_ms against it: one electrical revolution at this speed has to fit into the standstill time, otherwise a healthy slowly turning motor would be reported as standing still.
    max_speed_rpm int rpm required 1 .. 200000 highest mechanical speed the motor reaches. The generator derives the shortest sector time from it (60e6 / (rpm * pole_pairs * 6) microseconds) and checks debounce_us against it: debouncing must not swallow real edges at full speed. It refuses the combination with both numbers instead of measuring wrongly.
    debounce_us int us 20 0 .. 100000 an edge closer than this to the last accepted edge is counted as bouncing and ignored (0 switches the debouncing off). It is done in the driver, not with the input filter of the port: the filter width of the s32k1xx (PORT DFCR/DFWR) is one register per port and would change every other input of that port too.
    standstill_ms int ms 200 1 .. 60000 time without an accepted edge after which the quality becomes QLF_ERROR_TIMEOUT (standstill): period, speed and direction are not current any more, while state and sector still are - the sensors report the position of a motor that stands still. It also bounds the time base: the driver stamps every edge with the microsecond time of the system timer (32 bit, wraps after about 71.6 minutes), a standstill throws the running revolution away, and the generator checks that six standstill times stay well inside one wrap, so no period can be measured across an ambiguous time.

    Rules between the parameters (checked by tools/nxconfig): max_speed_rpm >= min_speed_rpm.

    safeLifecycle¶

    Safety task of the S32K1 family - cycle of the safety supervision, MCU watchdog service and period check

    • Directory: platforms/s32k1xx/port/safety/safeLifecycle, manifest: module.yaml, kind: service
    • Port: family port platforms/s32k1xx/port - loaded by tools/nxconfig for the projects whose derivative belongs to this family
    • Verification: hardware - The demo values (10 ms, 250 ms time-out, service every 8 cycles until SYS-53) run on the eval board without watchdog reset; 7 cycles (SYS-53), other values and the period check are covered by host and generator tests.
    • Public headers: safeLifecycle/IsrHooks.h, safeLifecycle/IsrWrapper.h, safeLifecycle/ProgressSupervision.h, safeLifecycle/SafetyManager.h
    • Integration: lifecycle level 1 in task safety, CMake target safeLifecycle
    • Project configuration (project.yaml):
      • modules.safeLifecycle.<parameter> - one entry per project, parameters below
    Parameter Type Unit Default Allowed values Description
    task_period_ms int ms 10 1 .. 1000 period of the safety task (SafetySystem schedules it at this fixed rate). Every cycle runs the whole safety supervision, so the period bounds how late a fault the task checks is seen; counters in cycles of other safety modules (e.g. safeSystem.adc_read_error_limit) scale with it. The watchdog is serviced every floor(watchdog_timeout_ms x 1000 / (3 x task_period_ms x lpo_max_per_mille)) cycles, derived by tools/nxconfig at the fastest LPO of the data sheet (mcudb clock.lpo).
    watchdog_timeout_ms int ms 250 1 .. 65535 time-out of the MCU watchdog. It has to hold three service intervals of the safety task (at least 3 x task_period_ms), so that a single late service does not reset the ECU. The family bounds it by its watchdog counter: S32K1 WDOG at the nominal 128 kHz LPO, at most 511 ms (TOVAL 16 bit). The LPO tolerance of the data sheet shortens the real time-out (at 139 kHz 230 ms for 250 ms); the service interval is derived for that shortest time-out (SYS-53).
    cycle_lateness_ms int ms 2 0 .. 999 how late a cycle of the safety task may start against its nominal grid point without a period violation (SAFETY_CYCLE_PERIOD_VIOLATION, SM-04): interrupt load, critical sections, one tick of the OS timer. Below task_period_ms. The value is an assumption until the board measurement B4 of doc/safety/fmea.md confirms it.

    Rules between the parameters (checked by tools/nxconfig): cycle_lateness_ms < task_period_ms.

    Safety RAM gate (MPU), ECC supervision and ROM check (CRC of the application image) of the S32K1 family

    • Directory: platforms/s32k1xx/port/safety/safeMemory, manifest: module.yaml, kind: service
    • Port: family port platforms/s32k1xx/port - loaded by tools/nxconfig for the projects whose derivative belongs to this family
    • Verification: hardware - The first ROM-check pass (valid image passes, changed image held in the safe state) is confirmed on the eval board; the re-check period, the CRC-unit self-test and the suspension during flash writes are host tests only.
    • Public headers: safeMemory/EccLatentTest.h, safeMemory/IntegrityEccHandler.h, safeMemory/MemoryLocations.h, safeMemory/MemoryProtection.h, safeMemory/ProtectedRamScopedUnlock.h, safeMemory/RomCheck.h, safeMemory/RomCheckFlashWrites.h, safeMemory/RomCheckList.h, safeMemory/SafeMemory.h, safeMemory/SafetyShell.h, safeMemory/mpu.h

      • modules.safeMemory.<parameter> - one entry per project, parameters below
    Parameter Type Unit Default Allowed values Description
    rom_check_period_ms int ms 60000 0 .. 86400000 re-check period of the ROM check (SM-14) from the start of one pass to the start of the next; 0 = once per start only. One pass (known-answer test of the CRC unit, then the CRC over the whole application image) runs in the idle context at the lowest priority without a lock, so the period costs only idle time (about 3 to 6 ms per pass for an image of about 190 KB, computed).     safeSystem¶

    Safety supervision of the ADC reference voltage and the internal supplies of the MCU (safety task)

    • Directory: platforms/s32k1xx/port/safety/safeSystem, manifest: module.yaml, kind: service
    • Port: family port platforms/s32k1xx/port - loaded by tools/nxconfig for the projects whose derivative belongs to this family
    • Verification: hardware - Reference and supply monitoring run on the eval board without false alarms (bandgap readings, safeadc counters at 0, no safety reset); a wrong reference voltage and failed readings up to the limit are covered by host tests only.
    • Public headers: safeSystem/SafeSystem.h
    • Provides roles: adc_reference_monitor, internal_supply_monitor
    • Integration: lifecycle level 1 in task safety, console command group safeadc, CMake target safeSystem
    • Project configuration (project.yaml):
      • modules.safeSystem.<parameter> - one entry per project, parameters below
    Parameter Type Unit Default Allowed values Description
    adc_read_error_limit int 10 1 .. 100000 failed readings in a row before the monitor concerned is triggered, applied separately to the bandgap (reference monitor, context 2) and to the internal supply channel (internal supply monitor, context 2; since SYS-41) - in both cases "no measurement possible". A single failed reading is not evidence of a wrong voltage and must not reset the ECU; readings that keep failing mean the voltage can no longer be monitored, which is safety relevant itself. A good reading ends the series; a supply reading skipped for want of a valid reference does not count (that is the reference monitor's case). The limit counts cycles of the safety task, so the time it corresponds to follows from that task's period.
    adc_reference_tolerance_mv int mV 200 1 .. 1000 allowed deviation of the measured ADC reference voltage (VREFH, computed from the bandgap reading) from its nominal value; outside nominal +- tolerance the reference monitor is triggered (context 1). The nominal value is a board fact (board.yaml board.adc_reference_mv), the tolerance is decided by the project: it has to cover the accuracy of the reference source and the spread of the bandgap (taken as 1000 mV).
