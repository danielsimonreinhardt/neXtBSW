    neXtBSW v1.0.0-rc1 — release notes¶

    Release date: 2026-10-05 (tag v1.0.0-rc1)

    Development release – no safety claim.

    neXtBSW targets ASIL B as a software safety element out of context. This release candidate (release R1) does not claim ASIL B capability and is not a safety release.

    • R1 was checked under deviation D-01: the confirmation measures were performed by the safety responsible without independence. No working state and no tag gets an ASIL statement from them.
    • Performed for R1 (all under D-01): CM-01 safety plan, CM-02 safety analyses, CM-04 verification plan and CM-07 safety concept and CM-05 safety case (each closed after a re-check), CM-10 safety manual (accepted with conditions; one finding open until the first public release) and CM-06 release decision (accepted with conditions: the release was decided with the conditions bound CI report, board run on the tagged image and verified export; see the record of the release).
    • Performed after R1, as a documented deviation from their planned timing: CM-03 (dependent failure analysis), CM-08 (tool classification and qualification), CM-09 (component qualification and coexistence) and CM-11 (functional safety audit). The deviation is recorded in safety plan section 5 and as deficit D-22 in the safety case. It is lifted before the first public release or the first release with an ASIL B claim, whichever comes first.
    • R1 is distributed privately. Every recipient receives this statement together with the safety manual.

    What is neXtBSW¶

    neXtBSW is a configurable basic software for 32-bit ARM Cortex-M and Cortex-R microcontrollers (little endian), built on Eclipse OpenBSW and FreeRTOS. A control unit is described in configuration files — MCU derivative, board and project — and generators derive clock tree, pins, CAN bit timing, memory layout, bootloader values and the RTE from them. Application software is attached as Simulink models (AUTOSAR Classic software components) through the generated RTE.

    Start with the README and the documentation map.

    Content¶

    • Configuration and generators: configuration model and checks (tools/nxconfig), BSW and RTE generators (bswgen, rtegen), CAN database generator (dbcgen), calibration objects in swc.yaml with A2L and datasets, configuration and generator identity in the image (console version/info, UDS DID).
    • ECU application and services: derived from the OpenBSW reference application; ECU state management, CAN with a second bus (diagnostic CAN), UDS in the application, fault memory (simplified DEM), NvM core with integrity classes, data flash, persistent operating hours and reset statistics, E2E profiles P01/P02/P11, XCP.
    • Drivers: 27 driver and service modules with neutral contracts; their verification level is listed per module in the module reference and drawn in the module map.
    • Bootloader: UDS bootloader over CAN (ISO-TP), plain C, hardware-independent core; flashing with tools/canflash; bootloader updater; diagnostic CAN supported (nextbsw-bl 0.3.9).
    • Safety mechanisms (stage 1, s32k1xx family port): safe supervisor, safety task and lifecycle, MPU-protected safety RAM, ECC supervision, ROM check, supply and ADC reference supervision, watchdog and halt deadman, safe outputs table with read-back, degraded reaction per PWM group. The list of mechanisms, what each one covers and what an integrator may rely on is in the safety manual section 5.
    • Tools: test runner (tools/test), CI wrapper (tools/ci), workspace update (tools/nxupdate), distribution check (tools/distcheck).

    Not part of this release¶

    • neXtBSW Studio (desktop tool) — it has its own release and is not contained in this distribution.
    • The maintainer's own evaluation board, its projects and its board recordings.

    AN-010 (open) RTE task activation (starvation, late start) is not supervised; only run durations are measured a task that is not activated or starts late is not detected by the BSW AoU-17: develop safety-related code at the target ASIL or provide your own partitioning and timing supervision

    Upgrade from v0.2.0¶

    The notes below are taken from the changelog; a compatibility review per interface (RTE, schema, safe supervisor API, assumptions of use) against v0.2.0 was not made.

    • Version. VERSION reads 1.0.0 (the file holds MAJOR.MINOR.PATCH only); the release-candidate state is the tag v1.0.0-rc1, which the image carries in its repository identification. Moving a customer workspace pin: tools/nxupdate <workspace> --to v1.0.0-rc1 (dry run first; see tools/nxupdate).
    • Bootloader 0.3.5 → 0.3.9. Update fielded bootloaders with the updater (canflash blupdate, see tools/canflash) or with the debug probe (flash-bootloader). Since 0.3.7 the bootloader starts only an application whose record carries the compatibility block, and it checks the image again right before the jump; a record written before that block existed is no longer started (DID 0xF1A0 reports why) — flash the application again with the current tools. 0.3.6 adds the low-voltage detect reset from the reset handler and skips the start window after the watchdog fast-test resets; 0.3.9 fixes a reset loop on the 16-buffer FlexCAN instances (diagnostic CAN).
    • NvM layout. The reserved fault memory block DemEvents grows when a project takes the new standard safety-reset DTCs (in the maintainer's demo: 14 → 39 bytes, 2 → 7 DTCs), and the new reserved block EcuStatistics (operating hours and reset statistics, DID 0x0130) lies behind the component and fault memory blocks. Blocks behind a changed one move: after flashing, the fault memory starts empty once and the statistics start at zero once.
    • AUTOSAR base types. uint32/sint32 (and the other integer types) are now the stdint.h types; on the target uint32 is unsigned long. Code that relied on uint32 being unsigned int (format strings, overloads) needs a look.
    • Stricter checks of nxconfig. New project field project.integrity (qm, asil_a … asil_d): without it a project counts as an ASIL project, qm has to be set deliberately. In an ASIL project a BSW task stack, the interrupt stack or its guard below the default without an evidence note is an error (a warning in a QM project); merging the background task into bsp is refused for projects with a power stage; an interrupt stack value on a family where it has no effect is an error. New project values: bsw_tasks.<task>.evidence, memory.application.isr_stack_size, isr_stack_guard_size and their evidence fields.
    • Product image. Service console commands that write registers, frames, outputs or the fault memory are no longer in the product build (NX_PRODUCT_BUILD=ON); out set refuses safe_off outputs in every build, pwm refuses the PWM groups of the safe outputs table. Read commands and nvm write stay.
