    What this document is. The work product that the safety plan names for activities P6-07 (pre-existing software) and P8-09 (qualification of software components) and that the safety case lists as evidence EW-07. It gives every pre-existing component in the demo image one route — qualify it per 8-12, treat it as own development per part 6, replace it, or leave it QM under the coexistence argument — together with the plan that carries the route out, and it contains the first qualification report, for OpenBSW's safeMonitor. It also records the two tool changes the gap analysis asked for: the modified OpenBSW copies in the safety path are now analysed as own code by the static analysis (gating) and are counted in the coverage thresholds.

    Licence rule. ISO 26262:2018 is cited by part and clause only (for example "8-12" = ISO 26262-8:2018 clause 12); requirements are restated in our own words, and no text, table or figure of the standard is reproduced.

    What it is not. Not the FreeRTOS qualification (postponed by an earlier change; its plan is in section 4.3), not the coexistence argument (that is coexistence.md, whose module classes this document uses unchanged), not a tool qualification (compiler and libraries as tools: tool-classification.md).

    1. Reading of the rules and the routes¶

    1.1 What the standard asks (own words)¶

    • 6-7.4.7 / 6-12, 8-12. Software that was not developed for this element — a library, an operating system, a component taken over from another project — may be used in a safety-related element when it is qualified: there is a specification of what it must do in this use (requirements, configuration, interfaces, behaviour in abnormal conditions), evidence that it does that (verification suited to the ASIL, including requirements-based tests with a measure of structural coverage), evidence that it is suitable for the intended use (assumptions of use, integration evidence), the exact version and configuration it holds for, and the known anomalies. The qualification holds only for that version and that use; a change of either makes it void.
    • 8-12, 10-9.1. A component that is changed is no longer a qualification case: it is developed (or re-verified) under part 6 like own code, or argued by a change analysis. Hence the gap analysis (row 8-27): a modified OpenBSW copy in the safety path is own development and must pass the same gates as own code.
    • 8-14. Proven in use is not used (safety plan tailoring T-07): no field data exists.
    • 9-6 / 6-7.4.8. A QM component in the same image needs no qualification as long as the coexistence argument shows that it cannot violate an ASIL B requirement (coexistence.md); where the argument is open, the component counts as ASIL B (coexistence rule 1.4) and falls back to one of the routes above.

    1.2 Routes used here¶

    Route Meaning Evidence it produces
    R-Q (8-12) qualify the unchanged component for its use in neXtBSW a qualification report per component (template: section 5)
    R-6 (part 6) the component is own development; unit design, unit tests with coverage, static analysis as a gate, code review the part-6 work products of the module (sw-architecture, unit-design, tests, tools/misra, coverage.yaml)
    R-X (replace) remove the component or replace it by own code developed under part 6 the replacement's part-6 work products
    R-QM QM under the coexistence argument; no qualification while every coexistence row of its module holds the rows of coexistence.md section 3
    n/a not linked into the image (host tests, build files, other families) —

    1.3 Inputs¶

    • Module classes and the membership of every copy: coexistence.md sections 2.1 and 6 — used unchanged; the longest path prefix decides.
    • Copy status per file: tools/openbswsync/copies.yaml (OpenBSW submodule 3b6e702): 72 modified, 36 identical, 49 new entries.
    • FreeRTOS inventory, usage and effort: rtos-comparison.md (not published, available on request).
    • Compiler and libraries as tools: tool-classification.md (TN2, compiler TCL 3).

    Notes on the table:

    • Why unchanged OpenBSW parts are R-Q and not R-6. They are pre-existing: neXtBSW did not write them and must not change them (the submodule is never changed). A change would turn a file into a copy (PC-12).
    • Why no component is R-X today. Replacing is always possible but costs more than qualifying the small components; it is the fallback when a qualification finds an anomaly that cannot be handled by an assumption of use.
    • Header-only components (PC-01, PC-02, PC-06, PC-10, PC-11) are compiled into the ASIL B units that include them. Their code therefore appears in those units' objects; the qualification report is still per component, because the component is what is reused and what changes with a submodule update.

    3. Modified copies as own development (PC-12)¶

    3.1 Static analysis as a gate¶

    Before this task tools/misra analysed every OpenBSW copy, but reported copies separately and not gating (static-analysis.md section 2; gap analysis SG5 / AN-031). Now:

    • tools/misra/rules.yaml has a list scope.gating_copies of 19 path patterns, one comment per module, taken from the module table of coexistence.md. A copy with status: modified that matches is classified own and its findings follow the rules of own code: deviation, baseline, or a new finding that fails the run. Identical copies stay separate even when they match (route R-Q, PC-13), and so do copies of QM modules (R-QM, PC-14).
    • tools/misra/test_misra.py checks the list against the document: the set of modified copies the patterns hit must equal the set of modified copies whose module is B-SM, B-SEP or B-DEP in coexistence.md — 47 at this working state; every pattern must hit a copy. Counter-checks: dropping ecu/safety/safeWatchdog/** or adding ecu/application/src/logger/** (QM) is detected.
    • python -m tools.misra baseline --only <file> (new) rewrites the baseline entries of the named files only. It was used to take the 47 files in without taking in the 57 findings that origin/dev already fails with (Q-1).

    4. Qualification plan (8-12)¶

    4.1 Procedure per component¶

    Every R-Q component gets a report with the sections of QR-01 (section 5), in this order of work:

    1. Identify: path, submodule commit, SHA-256 (16 hex digits) of every file, licence, configuration used.
    2. Intended use: which parts neXtBSW uses, by which ASIL B module, how many instances, with which template arguments or configuration.
    3. Specify: component requirements in our words, from the documentation and the code; where they differ, the code decides and the difference is an anomaly.
    4. Assumptions of use: what the maintainer of the component must ensure (lifetimes, contexts, locks, value ranges).
    5. Verify: requirements-based tests (OpenBSW's own tests where they exist, own tests where they do not), with statement and branch coverage of the component; static analysis with the project rule set; a trace table requirement → test; integration evidence in neXtBSW (host tests with the real ASIL B callers, board records).
    6. Anomalies: every difference and weakness found, with its effect in neXtBSW and how it is handled.
    7. Verdict and validity: for which use the component is suitable; the report is void when a file hash or the use changes.

    4.2 Order and effort¶

    Order Component Effort Why this order
    1 PC-01 safeMonitor done smallest, decides every safety event
    2 PC-02 safeUtils, PC-06 interface headers 1.5 AD trivial, but every ASIL B unit includes them
    3 PC-03 safeBspMcuWatchdog 2–3 AD independent watchdog of the MCU; real code has no host test (Q-3)
    4 PC-04 bspInterruptsImpl 1–2 AD separating element; needed before a later change can argue partitioning
    5 PC-11 CMSIS-Core, PC-05 MCU drivers 1 + 5–10 AD with the HSI review (hsi-s32k1xx.md)
    6 PC-10 ETL subset, PC-09 libraries 5–9 AD depend on the usage scans; PC-09 also on the compiler decision TN2
    7 PC-08 FreeRTOS with PC-07 async binding 30–50 AD postponed by an earlier change
    — PC-13 identical copies inside 2–6 qualified with the component they copy

    Total without FreeRTOS: about 16–30 AD; with FreeRTOS: about 46–80 AD.

    4.3 FreeRTOS package (plan only, not started)¶

    Route R-Q as decided on 2026-09-22 (rtos-u1-anfrage, after the comparison rtos-comparison.md): stay on FreeRTOS and qualify it; the migration to a certified kernel was not chosen. Scope and steps, taken from rtos-comparison.md sections 1 and 4:

    • Scope — the kernel V10.6.2 in the configuration of FreeRtosPlatformConfig.h (static allocation, no MPU port, no timers task unless used), the Cortex-M4F SysTick port with OpenBSW's ManualChanges.diff, and the kernel services the async binding calls, including the kernel internals it relies on (AN-057). Other ports (M0+, R4F) are separate reports when those families enter a safety release.
    • Steps — requirements of the used API subset; the port's interrupt masking and context switch reviewed against the architecture manual; tests of the subset on the host (posix port) and on the target (board test suite, gap task 20); static analysis of the kernel files with the project rule set (reported, not gating, since the code is not ours); anomaly list from the FreeRTOS change history between V10.6.2 and the current release.
    • Effort — 30–50 AD for the first core, redone at every kernel update (rtos-comparison.md section 0).
    • Open — whether a qualified component is accepted as the separating element (6-7.4.9); the coexistence argument needs the answer.

    5. Qualification report QR-01 — OpenBSW safeMonitor¶

    5.1 Identification¶

    Item Value
    Component safeMonitor — generic monitor templates of the OpenBSW safety library
    Source external/openbsw/libs/safety/safeMonitor, OpenBSW submodule commit 3b6e702 (2026-09-14)
    Licence Apache-2.0 (header of every file); module.spec: maturity: production, safety: True
    Files (SHA-256, first 16 hex digits) Register.h 1e3248df946ca148, Sequence.h e7b903d0d7d174be, Trigger.h 69ff3b14b06fc1ad, Value.h 68dd7d4def403c7d, Watchdog.h 2993bb7c545cc64b, common.h 0cc4f65c4ec043ef (581 lines of headers)
    Build form header-only, CMake INTERFACE library linked by safeSupervisor; uses etl/platform.h (ETL_MAYBE_UNUSED) only
    Configuration in neXtBSW template arguments of ecu/safety/safeSupervisor/include/safeSupervisor/SafeSupervisor.h: handler SafeSupervisor, event SafeSupervisor::Event; ScopedMutex always the default DefaultMutex (no lock); context DefaultContext for the sequence monitors, uint32_t for trigger and value monitors

    5.2 Intended use¶

    SafeSupervisor (M-SUP, B-SM) owns every safety monitor and is the handler of all of them: 17 TriggerMonitor (Trigger<…, DefaultMutex, uint32_t>), 3 ValueMonitor (Value<…, bool, DefaultMutex, uint32_t>), 2 sequence monitors (SafetyManagerSequenceMonitor over 7 checkpoints of the safety cycle, SequenceMonitor over ENTER/LEAVE) and one DeferredTriggerMonitor that wraps a Trigger for reporters outside the safety task (SafetyEventMailbox.h). Every event a mechanism reports reaches the reaction of SafeSupervisor::handle() through one of these monitors. Watchdog and Register are not used by neXtBSW.

    5.3 Component requirements¶

    Written for this report from the documentation (doc/index.rst, the header comments) and the code; the code decides where they differ (QA-1).

    ID Requirement
    SMON-01 Trigger::trigger(ctx) stores ctx and calls the handler with the configured event exactly once per call.
    SMON-02 Value::check(v, ctx) stores ctx; it calls the handler with the configured event exactly once if v differs from the expected value, and not at all otherwise.
    SMON-03 Sequence::hit(cp, ctx) stores ctx; if cp is not the expected checkpoint it calls the handler once and leaves the expectation unchanged; otherwise it advances the expectation by one, and after the last checkpoint back to the first. The first expected checkpoint after construction is the first one.
    SMON-04 Watchdog::service() counts down from the timeout, saturating at 0, and calls the handler on every call while the counter is 0; kick(ctx) stores ctx and restarts the count at the timeout.
    SMON-05 Register::check(ctx) stores ctx, compares the masked value at each entry's address with the expected value in order, stops at the first mismatch and then calls the handler once; getLastCheckedEntry() names the last entry compared (the faulty one after a mismatch, nullptr before the first check).
    SMON-06 Every public operation that changes state holds exactly one ScopedMutex object for its whole duration; the handler is called while it is held (QA-1).
    SMON-07 The stored context is a copy; getContext() returns the last stored context, and a default-constructed context before the first store.
    SMON-08 The monitor calls the handler in the caller's context and returns after it; it neither blocks nor defers.
    SMON-09 No dynamic memory, no recursion, no exceptions thrown, no static state other than the constant default context; run time is constant per call (Register: linear in the number of entries).
    SMON-10 The monitor keeps a reference to the handler and (Register) to the entry array; it does not copy them.
    SMON-11 The event and the expected value are copied at construction and cannot change afterwards.

    5.4 Assumptions of use¶

    ID Assumption How neXtBSW meets it
    SMON-A1 The handler object (and the Register entry array) outlives the monitor (SMON-10). SafeSupervisor owns the monitors as members and is a static object
    SMON-A2 A monitor is changed and read from one execution context, or the ScopedMutex makes the operations mutually exclusive. getContext() itself is not guarded. all monitors are driven and read in the safety task; reporters outside it post to SafetyEventMailbox, which hands the report over in the safety context (host test safe-supervisor-mpu)
    SMON-A3 With a non-default ScopedMutex the handler runs inside the lock (SMON-06); it must not take the same lock or block. only DefaultMutex is used; a compile-time check is proposed (P-6)
    SMON-A4 The checkpoint type of a Sequence has consecutive values from the first to the last checkpoint, first ≤ last (the monitor advances by +1). both enums in SafeSupervisor.h are consecutive from 0 with first < last; not checked at compile time (QA-3)
    SMON-A5 Watchdog with timeout 0 reports at the first service() call. Watchdog not used
    SMON-A6 The monitor state lies in memory the safety part protects; a corrupted monitor can suppress or invent an event. SafeSupervisor and its monitors lie in the MPU-protected safety RAM (sw-architecture.md)

    5.6 Anomalies¶

    ID Anomaly Effect in neXtBSW Handling
    QA-1 The comments of Register::check, Sequence::hit and Watchdog::service say the handler is called outside the ScopedMutex; the code constructs the lock at the start of the function and calls the handler before it ends, i.e. inside (all five monitors). none: neXtBSW uses DefaultMutex (no lock) everywhere requirement SMON-06 states the real behaviour; assumption SMON-A3; proposed as an upstream documentation fix (P-7)
    QA-2 getContext() is not guarded by the ScopedMutex; a reader in another context can see a partly written context. none today (SMON-A2) assumption SMON-A2
    QA-3 Sequence advances by static_cast<Checkpoint>(expected + 1) and needs consecutive checkpoint values; nothing checks this at compile time. none: both enums are consecutive assumption SMON-A4; a static_assert in SafeSupervisor.h is proposed (P-6)
    QA-4 Watchdog with timeout 0 reports at the first service(); a timeout of N gives a window of N calls including the one that reports. none: not used assumption SMON-A5

    5.7 Verdict and validity¶

    • Trigger, Value, Sequence with DefaultMutex — as used in neXtBSW — are suitable for use in the ASIL B safety part under the assumptions SMON-A1 … A6: the requirements SMON-01 … 03 and 06 … 11 are specified, verified by requirements-based tests with full statement and branch coverage of the component, the static analysis shows no finding that needs action, and the one documentation anomaly (QA-1) has no effect in this configuration.
    • Watchdog and Register are verified to the same depth (SMON-04, 05) but not used; the verdict extends to them only after their intended use is added to 5.2 and checked against the assumptions.
    • Validity. Bound to submodule 3b6e702 and the six file hashes of 5.1, and to the configuration of 5.1. A submodule update that changes one of the hashes, a new template argument (another lock, another context type) or a new user of the component makes the report void until it is re-checked. Proposal P-5 automates the hash check.
    • Status. Complete on the author side; the confirmation review CM-09 (safety plan, I1 independence) is pending, and the acceptance by the safety manager.
