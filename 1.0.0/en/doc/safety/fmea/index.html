    1. Method¶

    1.1 What is analysed per mechanism¶

    For each mechanism, one table with the fields the task asks for:

    Field Content
    Faults considered the failures of the element the mechanism is meant to catch (fault model of the concept, made concrete), and the failures it explicitly does not catch
    Detection what the code reads or compares, where, and how often
    Reaction safe state per concept section 3: S1, S1 held, S1 + S2, S3; who decides (always SafeSupervisor::handle() unless stated)
    Times detection time (fault present → event raised), reaction time (event → reaction in effect), and the minimum FTTI served: the shortest fault tolerance time for which the mechanism can be relied on today (section 1.2)
    Diagnostic coverage class and justification (section 1.3)
    Latent faults of the mechanism how a failure of the mechanism itself is noticed, and after how long
    Evidence test IDs from tools/test/tests.yaml (run with .venv/Scripts/python tools/test -k <id>), target-artefact tests, and board runs recorded in CHANGELOG.md with their date
    Residual / action what remains, with the finding or task that carries it

    A mechanism is a software safety mechanism: the analysis asks what the software detects and how fast it reacts, not how often the hardware fails. Failure rates, the single-point and latent-fault metrics, and the manufacturer's coverage claims for the MCU's own hardware features (ECC, watchdog, MPU, CRC unit) are the integrator's (AoU-09); the MCU manufacturer's safety manual for the S32K1 family is not available to this project, so every hardware coverage claim below is a claim about how neXtBSW uses the feature, not about the feature itself.

    1.2 Time terms¶

    These are the usual terms of the field, explained in our own words (issue 1 said the standard was not consulted; issue 2: the terms agree with the fault tolerant time interval and the fault handling time interval that concept 7.2 issue 3 uses, proposal C7 of the gap analysis; the standard is cited by part and clause only):

    • Detection time — from the moment the fault is present to the moment a mechanism raises its event.
    • Reaction time — from the event to the moment the reaction has taken effect (outputs de-energised for S1; the MCU in reset for S2).
    • Fault tolerance time (FTT) — the time the item tolerates the fault before a hazard can occur. It belongs to the integrator's item (AoU-01), not to neXtBSW.
    • Minimum FTTI served — detection time + reaction time, worst case, as this analysis can bound it today. An integrator may rely on the mechanism for a goal only if his FTT is longer (AoU-05).

    Times are given in two forms where they differ:

    • nominal — with the demo's constants and the safety task running at its period (the concept's section 7.2 values);
    • guaranteed — what the element itself detects if the timing assumption breaks. Today these differ for every check in the safety task (F9, section 2).

    Reaction times: S1 (safe outputs walk) is computed at well under 1 µs at 80 MHz; on the board the walk from the timer to the gate-driver enable is bounded at ≤ 21 µs (B3, oscilloscope 2026-09-22; a tighter bound of ≤ 2 µs of 2026-09-28 has its captures outside the repository, AN-008), so the computed value stays computed (F8). S2 brings the MCU into reset within the reset sequence of the core; the restart time afterwards is measured (B2, section 8.1: up to 1 077 ms through the watchdog path, 858 ms through a fault handler, the stated values) and does not add to the time to de-energise, but it is the time the ECU is out of service.

    1.3 Diagnostic coverage: classes, not percentages¶

    The concept forbids invented numbers (concept section 0), and the manufacturer data that a quantitative figure would rest on is not available. The coverage of each mechanism is therefore given as an ordinal class with the justification written out, so that a reader can disagree with the reasoning rather than with a number:

    Class Meaning in this document
    high the mechanism checks the whole property it guards, by comparison with a reference that is independent of the fault, at a fixed interval (or on every access), and a failure of the mechanism itself is either detected or ends in a safe reaction
    medium the whole property is checked, but with a known blind spot that a realistic fault can fall into: sampling instead of continuous checking, a tolerance band, a reference that shares a cause with the checked value, or a part of the fault modes excluded
    low only a small part of the elements or fault modes is checked (demonstration scope, one pin, one path)
    reaction the mechanism does not detect anything; it is judged by whether it takes effect when called (SM-23 … SM-25, SM-53)
    none the fault is not covered by any stage-1 mechanism

    The standard rates the diagnostic coverage of safety mechanisms per hardware element and technique in its informative annex 5-Annex D (with 11-5.1.12 for memories and 11-5.2.4 for analogue parts); the reader finds those ratings in his own copy of the standard. This document does not map its classes to them: the class is an engineering judgement about neXtBSW's use of a feature. Issue 2 (N1 closed, CM-02 decision Z2, measure M3): the gap analysis iso26262-gap.md (not published, available on request) section 3 answers the question - there is no direct mapping of these classes to the figures expected for the hardware metrics; a figure needs each mechanism re-based on the hardware element it diagnoses, the technique and its test interval (measure M2). The classes therefore stay as they are for Release R1, which makes no safety claim, and the hardware metrics stay with the integrator (AoU-09, N2). M2 is task, after Release R1 and before the first ASIL B release.

    1.4 Evidence notation¶

    • test-id — a test entry in tools/test/tests.yaml. host tests run the real production file against a model or stubs; target tests inspect the built ELF.
    • board YYYY-MM-DD — a board run recorded in CHANGELOG.md under that date.
    • review — the claim rests on reading the code at 63ea900 only; there is no test that would fail if the code broke. These are the weak spots of the evidence and are collected in F15.

    2. The timing basis, corrected (F9)¶

    The concept (section 7.2) gives 10 ms as the detection latency of every check in the safety task. That is the nominal value. The analysis looked for what guarantees it and found nothing below the watchdog:

    • The safety task is scheduled with scheduleAtFixedRate(…, SYSTEM_CYCLE_TIME = 10, …) (ecu/application/src/systems/SafetySystem.cpp; project value modules.safeLifecycle.task_period_ms since an earlier change). No code compares the distance between two safety cycles with a time base.
    • The watchdog is serviced every WATCHDOG_CYCLIC_COUNTER = 8 safety cycles (derived from modules.safeLifecycle.watchdog_timeout_ms and the period since an earlier change) and fires after 250 ms. It therefore fires only when 8 × (actual cycle) > 250 ms, i.e. when the actual cycle exceeds 31.25 ms.
    • The watchdog runs in timeout mode (Watchdog::enableWatchdog sets no WIN), so a safety task that runs too fast is not caught by the hardware either; SM-03 only counts calls of the service function.

    5. Decisions on the findings handed to a separate task¶

    5.1 F3 — the ROM check in one go¶

    The concept names two problems: an unbounded run in idle, and a once-per-start check that is not a run-time mechanism. Since an earlier change the check exists; the analysis decides:

    1. No slicing while the check runs at idle priority. RomCheck::idle() runs in the idle context of the lifecycle (RomCheckSystem.h), without any lock (the pass, since an earlier change checkPass(), is outside the safety shell; only the report is inside). Every supervised task preempts it. Its only cost is that other work of the idle context (console, log drain) waits for the few milliseconds of the run. Slicing is required only if the check is ever moved into a timed context (a task with a deadline) — that becomes a requirement for a separate task: "The ROM check shall not run with interrupts suspended and shall not run in a context with an RTE deadline unless it is sliced."
    2. Duration: computed about 3 … 6 ms for the demo image (43 049 words; assumption: a few core cycles per word for the flash read and the CRC write at 80 MHz). Not measured — board checklist item B1 (section 8).
    3. A re-check period is needed, because the first intended applications include battery management, where ECUs are often powered for long periods without a restart. Today the run-time protection of the program flash rests on SM-16 (double-bit errors on read) alone. Proposed task T5: periodic re-check with a period as a module parameter of safeMemory (milliseconds; 0 = once per start, today's behaviour), restart of the pass after each full run, a known-answer test of the CRC unit before each pass, the CRC unit reserved for SM-14 (no other user today; a second user must be serialised), and suspension while the program flash is written (a later in-application update must not produce a false ROM_CHECK_FAILURE, which holds the ECU until a power cycle). Until T5 exists, proposed AoU-25: the integrator restarts the ECU at least as often as his latent-fault interval requires, or accepts SM-16 as the only run-time check of the flash.

    Implemented by an earlier change (host verified with mutants; board B1 and B9 open in issue 1 - passed since, 8.1 and 8.2): - Period: module parameter modules.safeMemory.rom_check_period_ms (manifest platforms/s32k1xx/port/safety/safeMemory/module.yaml, generated into integration/safeMemoryConfiguration.h), default 60 000 ms, 0 = once per start. Start to start, on the system time of the platform. - Context: RomCheck::idle() is called by the idle handler of the application (ecu/application app.cpp, only in an image with the reference CRC) and, as before, once by the component romcheck; both run in the idle context. The pass itself runs without a lock and outside the safety shell; only the bookkeeping at its end and the report enter the shell (one shell per pass, none per round of the idle loop while it waits). Decision 1 above therefore still holds: no slicing. - Known-answer test of the CRC unit before every pass (ROMCHECK_UNIT_FAILED → ROM_CHECK_FAILURE). - Suspension: every flash writer brackets its write with safety::FlashWriteScope (indicator RomCheckFlashWrites in ordinary RAM, library romCheckFlashWrites, outside the MPU protected sections). The NvM does so for every write of its memory (nvm::FlashWriteBracket around the IEepromDriver of the port: on the S32K1 the FlexRAM stores of the FlexNVM EEPROM emulation). A flash command started elsewhere is seen through FTFC FSTAT[CCIF]. No pass starts while a write is open; a pass during which one began is discarded and repeated, never reported. A due pass kept off for more than one period is reported (ROMCHECK_OVERDUE), so the indicator cannot switch SM-14 off silently. - Not done: slicing (not needed, decision 1); a check in tools/nxconfig that a period other than 0 exceeds the longest flash write (the manifest says so; the tool is outside this task).

    5.3 F5 — SPI as a common cause¶

    Decided: not a stage-1 problem, and no separate SPI supervision in stage 1. Reasoning:

    • No credited stage-1 mechanism uses SPI. The safe outputs walk writes port and FTM registers; the watchdog, the deadman, the MPU, ECC, ROM check and the supply checks are MCU-internal. A failed SPI master therefore removes no stage-1 detection and no stage-1 reaction.
    • What depends on SPI is stage 2: the device diagnostics of the gate driver, the cell controller and the SBC. For them the common cause is real and belongs into the dependent-failure analysis of a separate task.
    • The SBC watchdog, where enabled, is triggered over SPI; a failed SPI therefore ends in an SBC reset — a safe direction (stage 2, SM-42).

    What stage 1 contributes is the report path: the device context word proposed in G5 shall carry the bus instance, so that SafeSupervisor::handle() can recognise communication faults of several devices on the same bus within one window as one event ("bus lost") and choose one reaction. That is an addition to the G5 task, not a task of its own. A related task carries the other side: the SPI master is a resource shared between partitions.

    Status after a later change (host verified): bus id in bits 31..24 of the context word (kind SPI/I2C/UART/CAN/other, position of the bus among the used buses of that kind in board order - safeSupervisor/DeviceReport.h, the same rule in tools/rtegen device_bus_id). Communication faults (DEVICE_REPORT, class COMMUNICATION) of two different devices on one bus within 20 safety cycles (200 ms nominal) are logged once as "bus lost", further ones in that window are folded into it; the verdict ends after a window without a communication fault. The one reaction is S3 plus QLF_ERROR on the qualifier of every device value on that bus (gd.<device>.qlf today): by the safety manager's decision a verdict built from reports that other tasks posted may not switch off - a package that needs a switching-off reaction to a lost bus detects it in the safety task and raises DEVICE_FAULT. Limits: 8 buses tracked at the same time (a further one is logged without correlation), the window is a code constant (two cycles of the slowest cycle_ms a manifest allows; moves such constants into a configuration level), and the verdict freezes while the safety task stops (safe direction: it stays lost).

    10. Review questions of the architecture (section 11)¶

    This task changed no reusable code, no generator and no bootloader; it added this document, a consistency test under doc/safety/test/, and pointers in concept.md. The questions are answered for the analysis.

    1. Board without an SBC? Yes. Only stage-1 mechanisms are credited; none uses the SBC. F13 names the consequence explicitly: without an SBC nothing limits a reset loop. Since an earlier change the reset-loop limit (T4) does, with the MCU's own reset status and a record in no-init RAM only.
    2. Different crystal and system clock? Yes. All times are stated as times; the one computed duration (ROM check, walk) names the 80 MHz it assumes. F9 and section 5.2 (system clock check) make a wrong clock a detected fault rather than an assumption.
    3. Different derivative, S32K3 / STM32 / Cortex-R? Yes. The analysis follows the concept's split into neutral and family mechanisms; the register list of section 5.2 is by class and names the S32K1 registers as the instance of the family port. Other families get their own entries.
    4. Two or more CAN buses? Yes. SM-31/SM-32 are analysed per bus; F5's correlation is per bus instance.
    5. Several tasks and free priorities? Yes, and F9/F10 are exactly about task timing that is assumed rather than supervised.
    6. Every new value in exactly one configuration level? No new value is introduced. Proposed ones name their level: the re-check period of T5 is a module parameter of safeMemory (project level, since an earlier change modules.safeMemory.rom_check_period_ms); the reset-loop limit of T4 is a module parameter of the supervisor (provisional defaults in the family port until its manifest exists, proposed modules.safeSupervisor.reset_loop_limit / reset_loop_clear_ms); the register list of a separate task is derived, not configured.
    7. Host test with its own test profile? The new test doc/safety/test/test_fmea.py checks the document against the concept and tools/test/tests.yaml (every stage-1 mechanism analysed, every cited test exists, no coverage percentages); it needs no board profile. The code gaps are F15/T3.
    8. Tool core free of Qt, messages with a YAML path? Not applicable.
    9. Device driver granularity? Not applicable — no driver analysed (stage 2).
    10. Placement under platforms/? Not applicable — no new file there.
