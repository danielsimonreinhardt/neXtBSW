    neXtBSW — argument over the admissible configuration range (SYS-92, N3)¶

    Baseline: v0.2.0

    Status: 2026-09-30, issue 1 (SYS-92, proposal N3 of safety-plan.md), written against dev at 65f3dc9. Readers: the safety manager, the author of a module manifest or of a check in tools/nxconfig, the integrator who configures neXtBSW for his ECU, and the author of the safety manual (DOC-19). Language: English, like the rest of doc/ (CLAUDE.md, user 2026-09-17).

    What this document is. neXtBSW is configurable software: the stage-1 safety mechanisms take times, counts, tables and memory layouts from the three configuration levels (derivative, board, project). For such software the standard leaves two routes (6-C.4.5, read through iso26262-gap.md (not published, available on request) rows 6-36 and 6-38): verify the configured software for the data set actually used, or verify it for the admissible range of the configuration data. This document states, for every configuration value the stage-1 mechanisms depend on, which route neXtBSW takes, what range the project has verified and with which evidence, and which verification the integrator owes for his own data set. It is the argument the tailoring T-10 of the safety plan promises and the input for the configuration chapter of the safety manual.

    Licence rule. ISO 26262 is cited by part and clause only.

    1. The route and why¶

    Range where a check can carry it. A safety mechanism of stage 1 rarely depends on a single value; it depends on a relation between values (time-out ≥ three service intervals at the fastest LPO; one interval shorter than a window; deadman level above the RTOS boundary). Such a relation is decidable from the configuration alone. neXtBSW decides it in two independent places — tools/nxconfig (with the YAML path of the value, the configure step stops on an error) and a static_assert on the generated macros in the code that uses them — so every configuration that builds satisfies it. For these values the verification is valid for the admissible range, and the admissible range is defined as: declared range of the manifest ∩ every relation the checks enforce.

    Data set where the property is outside the configuration. Some properties depend on facts the configuration does not contain: the accuracy the integrator's function needs, the longest flash write of his application, the interrupt load of his software. For these the checks can only enforce the declared range; whether a value in that range is right is verified for the data set — by the project for its own profiles, by the integrator for his.

    Why not the range route for everything. Target tests over the full range would need hardware per value combination, and the properties of the second kind cannot be judged without the integrator's facts. Why not the data-set route for everything: then every change of a value would invalidate the element's evidence; the checks make most of it re-usable.

    Precondition of the argument. The checks run on the integrator's configuration: the image is built only through the build, which runs nxconfig and the generators (AoU-26 of tool-classification.md), and nxconfig and the generators are classified and qualified as there. The configuration files are safety-related data under change control (AoU-10).

    Remarks:

    • CV-20 is not a configuration value; it is listed because the deadman's reaction time depends on it and on the clock plan (NX_CLOCK_LPIT_HZ, derived), and a project might need another value (finding G3). It is not counted among the 19 values of section 0.
    • The ROM-check areas are not a configuration value: they come from the linker template and the image check; the calibration region is excluded and checked by its own record (SYS-91).
    • safeLifecycle, safeSupervisor, safeSystem and safeMemory are the stage-1 modules with project parameters; the test checks that every one of their parameters is a row here with the declared range of its manifest.

    3. The argument per route¶

    Range (11 values: CV-01, CV-02, CV-04, CV-05, CV-06, CV-10, CV-12 … CV-16, and CV-20 as code constant). For each of them: the safety property is a relation; a check enforces it on every configuration with the YAML path, and a second check in the code (static_assert, #error, image check) enforces it on the generated values; the configuration-level tests exercise values across the declared range including both sides of every limit (nxconfig-watchdog tests 228/229 ms against the shortest time-out, 511/512 ms against the counter). Conclusion: a configuration inside the admissible range keeps the property; one outside it does not build. What the range argument does not cover: that the software behaves as designed at every value — the host tests exercise the mechanisms at the demo values and at one or two stub profiles (G1), and the board only at the demo values. Behaviour that scales with a value (a longer period means a longer detection time) is computed in concept.md section 7 as a formula of the values, not measured per value.

    Data set (8 values: CV-03, CV-07, CV-08, CV-09, CV-11, CV-17, CV-18, CV-19). The project verifies its own data sets (demo, charge, buildtest, S32K116 minimal) and states the rationale of the defaults in the manifests. For the integrator's data set the verification is his (section 5); the checks only guarantee the declared range and, where it exists, a warning (CV-07).

    4. Findings¶

    ID Finding Consequence Proposal
    G1 No target build and no generator reference profile uses safety values other than the defaults (10/250/2 ms, 3/60 000/200 ms, 60 000 ms); non-default values exist only in configuration-level tests and host stubs the range argument rests on the checks; that the generated code builds and runs at other values is shown only for the stubs C1
    G2 rom_check_period_ms must be longer than the longest flash write of the ECU (manifest text), but no check enforces it a too-short period turns a long EEPROM write into ROM_CHECK_FAILURE (S1 held) — availability, not safety; the integrator must know it C2, AoU-CFG-4
    G3 the halt-deadman time-out is a code constant (10 ms) a project whose fault tolerance time needs a shorter or allows a longer standstill cannot configure it C3
    G4 the device-bus window is only warned about when it is shorter than two supervision cycles a configuration with a too-short window builds; the correlation then misses faults AoU-CFG-5
    G5 no checked-in project has a calibration segment; the production profile runs only in target-calibration the calibration route is verified by derived profiles, not by a maintained project C1

    5. Verification the integrator owes for his data set¶

    Proposed for the safety manual; numbered AoU-CFG-n so that they do not collide with numbers proposed in parallel. They refine AoU-10 and AoU-26.

    ID Assumption of use Values
    AoU-CFG-1 The integrator builds his image only through the build (so every check of section 2 runs on his configuration), treats every warning of nxconfig on a value of section 2 as a finding he resolves or justifies in writing, and keeps his configuration files under change control (AoU-10, AoU-26). all
    AoU-CFG-2 For every value of section 2 that differs from the defaults he repeats, on his ECU, the board checks of fmea.md section 8 that depend on it (watchdog reset, period violation, reset-loop limit, ROM check, safe outputs) and records the result with the configuration it was run with. CV-01 … CV-06, CV-11, CV-12
    AoU-CFG-3 He measures the start distance of the safety cycle under his worst-case load (as board check B4) and sets cycle_lateness_ms from that measurement with margin; the default 2 ms is the demo's measured value, not a property of neXtBSW. CV-03, CV-18
    AoU-CFG-4 He sets rom_check_period_ms longer than the longest flash write of his application (EEPROM emulation, NvM), and not longer than the latent-fault interval his analysis allows (AoU-25). CV-11
    AoU-CFG-5 He chooses the data-set values from the needs of his function and records the rationale: ADC reference tolerance against the needed accuracy (AoU-24), read-error limit and device-bus window against his fault tolerance time, E2E profile and data ID per signal (AoU-11). CV-07, CV-08, CV-09, CV-17
    AoU-CFG-6 He confirms that the halt-deadman time-out of 10 ms and the other fixed times of stage 1 fit his fault tolerance times (AoU-05), or requests a change (C3). CV-20
    AoU-CFG-7 If the neXtBSW bootloader starts his application image, he keeps the ROM check (SM-14) active in that image: built only through the build, so that the reference CRC is written and the check is compiled in (AoU-CFG-1), and with a re-check period (CV-11, AoU-CFG-4) or a restart interval (AoU-25) that covers his latent-fault interval. Reason (safety review BL38-P1, 2026-10-03, F5): since BL-36/BL-38 the bootloader checks the image again immediately before the jump without a second full CRC, so an image byte that changes between the CRC at start and the jump without a flash command (debugger, bit fault; with a held extended session the window can last minutes) is left to the flash ECC and SM-14. CV-11

    6. Result for the safety manual¶

    The safety manual does not exist yet (DOC-19). Proposal C4: its configuration chapter states the route of section 1 in two sentences, carries the value register of section 2 (or references it), and carries AoU-CFG-1 … AoU-CFG-6 with their final numbers. The consistency test checks the reference as soon as the safety manual exists.

    7. Tasks proposed by this document¶

    ID Title Done when Prio
    C1 Target test profile with non-default safety values a test project (or a derived profile as in target-calibration) builds for the target with values other than the defaults for every range value of section 2 (e.g. 20 ms period, 400 ms time-out, reset-loop limit 5, ROM-check period 2 s, a calibration segment), the reference outputs are checked in, and the host tests of the safety cycle run with its generated configuration P2
    C2 ROM-check period against the flash write time tools/nxconfig warns or refuses when rom_check_period_ms (other than 0) is shorter than the longest flash write the configuration implies (EEPROM emulation in use: backup-sector wait), with the YAML path; test with an own profile P3
    C3 Halt-deadman time-out into the configuration the time-out is a project value of the module that owns the deadman, with range, derived ticks and the existing static_asserts; default 10 ms; reference outputs unchanged for the defaults P3
    C4 Configuration chapter of the safety manual doc/safety/safety-manual.md (DOC-19) states the route, references config-range.md and carries AoU-CFG-1 … AoU-CFG-6 with final numbers; test_config_range.py checks the reference P2

    8. Review questions of the architecture (section 11)¶

    This task changes no code, generator or configuration. Board without an SBC: no value of section 2 assumes an SBC. Different crystal: the timing values run on the LPO or are relations to the safety task, whose own clock is what the period check measures; CV-20 depends on the LPIT clock through a derived value. Other derivative, S32K3/STM32/Cortex-R: CV-04 and CV-16 are derivative level; CV-02's upper bound is the family's watchdog counter, which nxconfig takes per family; the register is the list another family has to fill. Several CAN buses: CV-17 per signal and bus. Several tasks: CV-18. Exactly one level per value: every row names one level; none is set in two. Host test with own profile: test_config_range.py checks this document against the manifests. Qt, YAML paths: every check named reports with the YAML path. Driver granularity, platform rule: not applicable.
