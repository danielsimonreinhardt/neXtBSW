    What this document is. The written configuration management plan that iso26262-gap.md (not published, available on request) found missing (rows 8-12, 8-13, 8-14, 2-12; section 6 task 10; finding SG7). It states which items are under configuration management, how they are identified, what a baseline is, how a release is made, and how the safety documents name the state they are about. The standard is cited by part and clause only (for example "8-7.4.3" = ISO 26262-8:2018, 7.4.3); no text of it is reproduced.

    What it decides and what it only proposes. Binding is the safety manager's decision iso-q3 of 2026-09-22: a release is an annotated tag vX.Y.Z on master; before it there is a green CI run with an archived report, the safety documents refer to the tag, the qualification reports exist and the reviews are closed. Everything else here works that decision out. Issue 1 marked the points where the plan went beyond it as [Proposal] and put four of them to the decision log (section 11); the safety manager decided all four as recommended on 2026-09-28, and issue 2 marks them [Decided Q-CMn]. What is still marked [Proposal] (the release lines of 4.4, the fields of the tag message beyond the status line) was not part of those questions; P9 is binding since 2026-10-02 because it is the safety plan's precondition R6 (accepted with the safety plan).

    What it is not. Not the change management process (that is plus), not the verification plan, not the documentation management rules. It names the interfaces to them.

    1. Scope, roles and relation to other plans¶

    1.1 Scope¶

    The plan covers the neXtBSW development repository (private, the repository owner's GitHub account) as the development repository of the SEooC, including the work products needed to reproduce the element and its evidence (8-7.4.3). It covers the open source line (published as github.com/danielsimonreinhardt/neXtBSW, an export of this repository without history) and the licensed lines of lizenz-und-release.md (not published, available on request) only in so far as each of them is derived from one baseline of this repository (section 4.4).

    A customer repository (workspace with nextbsw.yaml, customer-project.md) is the integrator's configuration management, not this plan's. The interface is one sentence: the integrator pins a release tag of this repository, and tools/ci run --workspace <dir> --release proves the pin is a clean, annotated, reachable release.

    1.2 Roles¶

    neXtBSW has one human. The roles are named so that a second person can take one of them later (iso-q1 is still open; since 2026-09-30 the safety manager reviews himself under deviation D-01, see the row "Reviewer").

    Role Held by Responsibility in this plan
    Configuration manager, release authority the maintainer accepts this plan; approves every merge to master and every release tag; decides the safety status of a release
    Integrator of dev the maintainer (exactly one at a time) merges checked contributor branches to dev, keeps planning, changelog and tests.yaml, pushes dev, prepares release candidates, creates the tag after approval
    Contributor contributors (a task branch locally, a session branch in contributor sessions), the maintainer changes only the paths of their task; never commit to dev/master, never tag
    Reviewer an independent person not yet named (iso-q1); for now the safety manager himself (decision of the safety responsible 2026-09-30 on AN-093; safety plan tailoring T-11; reviews/README.md section 3.1, deviation D-01) confirmation reviews. A review by the safety manager is a confirmation without independence: it does not meet P6, so no release can be a safety release on it, and no working state or tag gets an ASIL statement until an independent person has reviewed it (section 5.1, P6)

    Independence: the integrator re-runs tests and builds of every contributor branch, and the safety manager accepts; for the author of code and its tests this is not independence at I1 (gap row 8-23). This plan does not change that.

    1.3 Interfaces to other plans¶

    Plan / process Task What it takes from this plan What this plan takes from it
    Safety plan – the release definition and its preconditions (section 5.1) the list of work products per release and who checks them
    Verification plan – the baseline a report belongs to; the rule that a report is archived per release (section 7) the report format, what "green" means per level

    3. Identification and naming¶

    3.1 Branches¶

    Branch Purpose Who writes Rule
    master released states only integrator, after the safety manager's approval receives only merges from dev (--no-ff); no direct commit, no hotfix on master — a fix goes through dev and a new PATCH release
    dev integration branch integrator receives only checked task branches; pushed after every merge (after git fsck --full --no-dangling); never force-pushed
    a task branch one task of a local contributor the contributor stays local; kept after the merge
    a session branch one task of a contributor session the contributor session pushed to origin, merged by the integrator

    The task ID in the branch name is the link to the change request (section 8).

    3.2 Versions¶

    • The element has one version: the root file VERSION, MAJOR.MINOR.PATCH without suffix (read by CMake, nxconfig, Studio and tools/ci).
    • [Decided Q-CM4] SemVer meaning for a base software: MAJOR = an incompatible change of an interface the integrator uses (RTE interface, configuration schema, safe-supervisor API, AoU); MINOR = new function, compatible; PATCH = fix without interface change. As long as MAJOR is 0, a MINOR step may break interfaces, and the changelog says so.
    • The release tag is v + VERSION (tools/nxconfig/version.py: tag_of). No other tag name starts with v<digit>.
    • The Studio has its own version v_x.y.z (tools/studio/version.py); it is not a tag. A release tag records which Studio version belongs to it.

    3.3 Commits in records¶

    • In records meant to survive (tag messages, safety case, archived reports) a commit is written in full (40 hex).
    • In prose a short hash of at least 7 characters is fine; it must be unique in the repository at the time of writing.
    • A short hash of the OpenBSW submodule is marked as such ("OpenBSW submodule at 3b6e702"), because it does not resolve in the neXtBSW repository.

    4. Baselines¶

    4.1 Definition¶

    A baseline is an annotated git tag vX.Y.Z on a commit reachable from master (iso-q3). Because git commits are content-addressed, one tag fixes every configuration item in git at once: source, configuration, generated code, own tools, tool pins, tests, safety documents, board captures and the OpenBSW submodule commit (its gitlink). What lies outside git is bound to the tag through its hash in the tag message (section 5.3): the archived CI report and, through versions.toml, every external tool archive.

    Rules:

    1. Annotated, never lightweight: the tag object carries tagger, date and the message of section 5.3. tools/nxconfig/pincheck.py rejects a lightweight release tag (tag-lightweight).
    2. On master: the tagged commit is the merge commit on master (or reachable from it); pincheck rejects tag-unreachable.
    3. VERSION equals the tag: tools/ci is red otherwise (check_release_version).
    4. Immutable: a published tag is never moved or deleted, and never re-created with the same name. A wrong release is corrected by the next PATCH release, whose changelog names what was wrong.
    5. [Decided Q-CM2] Signed from the first safety release on, with the safety manager's SSH signing key (git config gpg.format ssh, git tag -s). Development releases stay annotated only. Signing does not change any other rule; pincheck does not (yet) check a signature (G3): until it does, step 7 of 5.2 includes git tag -v vX.Y.Z for a safety release, run against the safety manager's allowed_signers file.

    4.2 Safety status of a baseline [Decided Q-CM1]¶

    The decision binds the preconditions to "release". v0.1.0 already exists and does not meet them — it was made as a reproducible version for customer pins, before this plan. To keep both true, a release tag states its safety status in its message:

    Status Meaning May be cited as evidence in a safety case Preconditions
    development release a reproducible, versioned state; the integrator may pin it for development no P1–P3 and P7–P8 of section 5.1
    safety release a state for which the SEooC claim (iso-q2: developed with the methods of part 6 for ASIL B, without the management part) is made yes all of P1–P9

    The status never changes after tagging. A development release that later passes the reviews does not become a safety release; the next PATCH release does.

    Alternative, not chosen: only a state that meets all preconditions gets a vX.Y.Z tag at all, and development states for customer pins use another tag form (for example vX.Y.Z-dev.N). That conflicts with a separate task (VERSION without suffix, CMake takes numbers only) and with pincheck; the maintainer chose the status line (Q-CM1, 2026-09-28).

    4.4 Release lines¶

    [Proposal] An open source export or a licensed line is not a baseline of its own; it is one baseline plus one distribution profile (tools/distcheck export --profile <p>). Its identity is "vX.Y.Z, profile open", and the export records the full commit hash of the tag it was made from. A licensed overlay carries the same version (the overlay-version check of pincheck). How the export is published is a separate task's decision, not this plan's.

    5.2 Steps¶

    Step Action Command / check Who
    1 Freeze the candidate on dev: set VERSION, close the changelog section, set every CI-08 header to Baseline: vX.Y.Z (the tag name is known before the tag exists, so no document has to cite a hash of itself) tools/nxconfig version; test G5 integrator
    2 Full CI run on the candidate; keep the output folder python -m tools.ci run --strict --clean [--slow] --out build/ci-out-vX.Y.Z integrator (workstation) or GitHub Actions (workflow_dispatch / PR dev → master)
    3 Integrity git fsck --full --no-dangling; git status --porcelain empty integrator
    4 Approval of merge and tag with safety status decision item maintainer
    5 Merge to master without fast-forward git checkout master && git merge --no-ff dev -m "Merge dev in master: neXtBSW X.Y.Z (Studio v_…)"; then git diff dev master must be empty integrator
    6 Create the annotated tag on the merge commit with the message of section 5.3 git tag -a vX.Y.Z -F msg-vX.Y.Z.txt master; for a safety release git tag -s with the SSH key (Q-CM2) integrator
    7 Prove the tag is a release python -m tools.ci check --release (runs pincheck on the tree: annotated, reachable from master, clean, VERSION equal); python tools/nxconfig pin projects/<p>/project.yaml --release; on the tagged checkout python -m unittest doc/safety/test/test_cm_plan.py (all state lines Baseline: vX.Y.Z); for a safety release git tag -v vX.Y.Z integrator

    A failure at any step stops the release. A tag that is already pushed is not removed (rule 4 of 4.1); the next PATCH release replaces it.

    6. How safety documents name their baseline¶

    6.1 Rule¶

    Every document of CI-08 carries one line in its header that says which state its statements are about:

    • Baseline: vX.Y.Z — the document was checked against that release and is part of it. This is the only form a safety release accepts (P4).
    • Working state: dev at <commit> (after vX.Y.Z) — the document was written between two releases. At the next release, step 1 of 5.2 replaces the line with Baseline: v<next> after the document has been re-checked against the candidate (or the release says in its message that the document was carried unchecked, which excludes a safety release).

    The existing sentences "written against dev at <hash>" and the "Update (task, against dev at <hash>)" blocks stay as history: they say when and against what a part was written. They no longer define the document's state. Commit hashes in the body (a board record at image c9a4f31, an inventory at 19df315) are evidence of a past observation and stay as they are.

    6.2 Why the tag and not the commit¶

    • One name for all documents of a release instead of one hash per document (finding SG7).
    • A tag says the state was released (reachable from master, CI green); a dev hash says nothing about that.
    • The tag cannot move; a hash can be unreachable after a history rewrite (the project had one, filter-branch in 2026-09, lizenz-und-release.md (not published, available on request)).

    6.5 Consistency test (G5)¶

    test/test_cm_plan.py checks, on every run:

    1. every file directly under doc/safety (*.md, *.yaml) except the generated ones has exactly one state line, and it lies in the header (before the first ## heading or --- rule; for YAML in the leading comment block);
    2. the line has one of the two forms of 6.1, nothing else on it;
    3. Working state: the commit resolves, is an ancestor of HEAD, and the named release is the newest release whose content the commit contains; Baseline: the tag exists and is not newer than VERSION;
    4. on a checkout that carries the release tag v + VERSION (step 7 of 5.2) every line is Baseline: v<VERSION>;
    5. the table of 4.3 lists exactly the release tags of git for-each-ref refs/tags/v*, each with its full commit;
    6. the exempt generated files are exactly the rows of the document register (anomaly-register.md section 6) with status generated.

    The git checks (3 to 5) are skipped with a message when the clone is shallow or has no release tags; the text checks always run. Counter-checks on broken copies show that each rule sees its fault.

    7.1 Reproducing a baseline¶

    The procedure the plan promises (8-7.4.4); not executed for this issue:

    git clone <origin> neXtBSW && cd neXtBSW
git checkout vX.Y.Z && git submodule update --init
git describe --exact-match   # must print vX.Y.Z
python -m tools.ci setup --python-packages
python -m tools.ci run --strict --clean --release --out build/ci-repro

    Expected: verdict pass, the same entries and test cases as the archived report, and the same artefact sizes. Whether the images are byte-identical across machines is not proven: individual tasks recorded a byte-identical demo image before and after their change on the same workstation (for example), not across machines and operating systems. Until it is proven, the image CRC of a board record is valid for the image that was flashed, and a rebuilt image is compared by its CRC before it is used as that evidence.

    8. Changes and their base configuration¶

    Change management itself is the task list (task IDs, done_when, owner lines with dates, the decision log) and will get the safety impact field of a separate task. This plan adds only the link to configuration management (8-8.4.2: a change request names its base configuration):

    • The base configuration of a change is the dev commit its branch started from. git records it (git merge-base dev <task branch>); the integrator writes it into the merge commit message or the changelog entry when it matters for a safety document ("against dev at …").
    • A change that touches a CI-08 document sets that document to Working state: dev at <commit> (after vX.Y.Z).
    • A change of CI-06 (tool pins) requires a full CI run (versions.toml header) and is named in the next release message.
    • A submodule update of external/openbsw is a task of its own, never a side effect.
