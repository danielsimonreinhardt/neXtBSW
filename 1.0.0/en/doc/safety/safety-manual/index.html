    What this document is. The integrator-facing safety manual of neXtBSW as a Safety Element out of Context (SEooC), the work product of confirmation measure CM-10 of the safety plan (safety-plan.md section 5). It says what neXtBSW assures and what it does not, which assumptions of use (AoU) the integrator must meet and how, which configuration rules keep the claim valid, which limitations he inherits, and where the evidence is. It adds no new safety statement: every sentence restates an existing statement of the repository and names its source. Where the sources disagree or are out of date, this manual says so (section 15) instead of deciding.

    Licence rule. ISO 26262:2018 is cited by part and clause only (for example "10-9.2.4" = ISO 26262-10:2018, clause 9.2.4). No text, table or figure of the standard is reproduced.

    What it is not. Not a safety case (safety-case.md), not an assessment, not a statement that an ECU built on neXtBSW is ASIL B capable. neXtBSW is a hobby project; nothing here has been assessed by anyone outside it (concept section 0).

    1. What neXtBSW assures, and what it does not¶

    1.1 The element¶

    neXtBSW as it is built into an ECU image, plus the tools that produce parts of that image (concept 1.2): safety supervision (ecu/safety/safeSupervisor, ecu/safety/safeWatchdog), the family safety port (platforms/s32k1xx/port/safety/*), the fault handlers, the debug-halt guard, the RTE and its run-time supervision, ECU state and start reasons, E2E and the signal qualifier, the CAN system, the analogue input path, the MCU drivers of the family, the bootloader, the device drivers (stage 1: only their safe_off declaration) and the configuration data with its generators. Out of scope: the application (SWCs), the hardware, the item-level safety concept (concept 1.2, AoU-01, AoU-09, AoU-17).

    1.2 The claim¶

    neXtBSW is developed following the methods of ISO 26262-6 at ASIL B, without the management part (safety plan 1.2). For the element this means: parts 6, 8 and 9 applied at ASIL B with the tailoring of section 12; part 2 applied as far as a single-person project can (safety plan, roles, tailoring, safety case, confirmation measures, release procedure). The capability is ASIL B (concept 2.1, confirmed in a separate task), as ASIL capability of an element out of context (10-9.1; gap analysis section 4 point 3).

    Stage 1 (concept 1.4): the safety argument is built from mechanisms whose detection runs on the MCU and uses only the MCU, its peripherals and the configuration. Diagnostics of parts outside the MCU (gate driver, cell controller, SBC, high-side switch) are stage 2 and not credited; their safe_off declaration is stage 1.

    1.4 Platform status¶

    The family safety port exists for s32k1xx only (concept 1.3, 9.2). On stm32, s32k3xx and rm4x an integrator gets the family-neutral part (supervisor, events and reactions, safe outputs table semantics, RTE deadlines, E2E, ecuState) and nothing of sections 6.2 and 6.4 of the concept. That is a gap, not a silence.

    Where the time goes with bootloader 0.3.9 (oscilloscope on RESET_b and on the chip select of the SBC's SPI, board 2026-10-03, same folder, c-20261003-*.csv; F1). The fault reset is followed by the two resets of the MCU watchdog fast test (SM-07): the reset pulses lie at 0, +229.0 and +173.0 ms (after power-on +251.7 and +173.0 ms). Since bootloader 0.3.6 only the first start after the fault reset passes the bootloader's start-up window of 200 ms:

    • start 1 = bootloader initialisation ≈ 20.6 ms + start-up window 200 ms (inside it the CRC over the application image, ≈ 144 ms) + application up to its fast test ≈ 8 ms;
    • start 2 = bootloader initialisation ≈ 20.6 ms + CRC ≈ 144 ms + application up to its fast test ≈ 8 ms;
    • start 3 = bootloader and CRC as start 2, then the application up to its first frame.

    Therefore saves ≈ 112 ms (two windows of 200 ms minus the CRC that was computed inside them, 2 × 56 ms), not the 400 ms of two whole windows. The MPU path is 36 ms longer than with bootloader 0.3.6 (664 ms): ≈ 11 ms come from the larger application image (longer CRC in each of the three starts), the rest lies on the application side (fault to reset and start 3 to the first frame); splitting that rest up is task, not part of release R1. For his board, bootloader and start-up the integrator measures the restart time himself (AoU-CFG-2).

    The bootloader phase is not supervised. On s32k1xx the bootloader disables the MCU watchdog as its first action (bootloader/platforms/s32k1xx/hal_s32k1xx.c, bl_system_init()) and never enables it; on stm32 the independent watchdog is not running after power-on or software reset and the bootloader does not start it. The application enables its watchdog in its own start-up. From every reset until then, no neXtBSW mechanism supervises the program flow. This is safe under three conditions, which the integrator confirms: (1) every power output is in its reset state while the bootloader runs - the bootloader configures no pin of a power output, only CAN and, on boards with an SBC, its SPI (AoU-07, AoU-SEC-3); (2) the phase is bounded: without a tester it ends after the start-up window with the jump, or the bootloader stays with outputs in reset state; a hang in the bootloader is left only by a reset from outside (power cycle, SBC watchdog served by the bootloader - with bootloader.sbc_watchdog: serve, and since an earlier change always with an SBC without software development mode, since an earlier change also with an SBC that is only read (AoU-34) - or the tester's ECU reset); (3) a bootloader that stays (no valid image, programming session) is a state with de-energised outputs, not a functional state. The start decision itself is not a RAM value of the past: since an earlier change the bootloader checks the start again immediately before the jump, and a record without compatibility block (written before a later change) is never started (SM-51; S11 of the safety review 2026-10-02). Since an earlier change (bootloader 0.3.8) that check reads record, compatibility block and entry again and compares the record's CRC field and size with the one CRC-32 over the image computed at the start, instead of a second CRC over the image; the bootloader has no flash write path between the two checks outside the programming session, which keeps it from jumping, and an image body changed by anything else is the application's ROM check SM-14 at its start.

    5. Safety mechanisms the integrator may rely on¶

    How to read the table. Guaranteed detection (nominal) is the time from the fault to the event, as bounded by the failure analysis (fmea.md section 2 and 3.7): checks in the safety task are guaranteed at 17 ms while the task runs (nominal 10 ms, SM-04 since an earlier change); a task that stops is SM-01's. FHTI is the maximum fault handling time interval of the element = guaranteed detection + reaction until the outputs are de-energised (the naming of gap proposals C7/M1); the walk itself is computed below 1 µs at 80 MHz and bounded at ≤ 21 µs by a board measurement (fmea 8.1, B3). The integrator compares the FHTI with the fault tolerant time interval of his goal (AoU-05). Class is the ordinal coverage class of fmea.md 1.3 — a judgement of neXtBSW's use of a feature, no percentage. Clause; neXtBSW rating is the answer of the gap analysis to open point N1 (iso26262-gap.md (not published, available on request) section 3), since an earlier change in this form: first the clause of the standard against which the integrator rates the mechanism in his hardware metrics (part and clause only; the standard's own ratings are not carried here, the integrator reads them in his copy), then neXtBSW's own rating with what the mechanism sees and what not, in the words of fmea.md section 3; "—" where section 3 has no row (proposal M2 open). Latent faults names how a failure of the mechanism itself is found (fmea section 3).

    neXtBSW's rating scale. neXtBSW has no failure rates and no safety manual of the MCU (AoU-09, fmea N2), so it cannot say which share of a hardware element's failures a mechanism detects. What it can show from the repository is how deep the detection of the faults in its own fault model is demonstrated. The rating says that, on a scale of its own that is deliberately not "low / medium / high", so that it cannot be read as the standard's classes:

    Rating Meaning Where the evidence is
    E3 the fault, or its register-level equivalent, was injected on the target and the reaction was recorded, in addition to host tests board run named in fmea.md section 3 or 8, capture or changelog entry
    E2 the detection is exercised on the host against the fault model, and built-in faults (mutants) of the detecting code are all found; on the target at most the absence of false alarms or the reaction alone host test with a mutation profile (*-mutations, mutants named in fmea.md)

    6. Timing: what the element guarantees, and what the integrator compares¶

    The times come from four values (concept 7.1; defaults of the demo project):

    Value Where set Default
    safety task period modules.safeLifecycle.task_period_ms (project) 10 ms
    watchdog service interval derived by nxconfig: floor(time-out × 1000 / (3 × period × LPO maximum per mille)) cycles 7 cycles = 70 ms
    MCU watchdog time-out modules.safeLifecycle.watchdog_timeout_ms (project) 250 ms
    halt deadman time-out / poll code constants of the family port (config-range CV-20, finding G3) 10 ms / 1 ms

    The relation three services before the time-out at the fastest LPO of the derivative is checked by nxconfig (safety_timing, test nxconfig-watchdog) and by static_asserts; the S32K1 counter limits the time-out to 511 ms (concept 7.1, config-range CV-02). Other values scale the times of section 5 as formulas of the values (config-range.md section 3); the tables above hold for the defaults.

    Two traps the concept calls out (7.3): a reset is not instantaneous (restart times in section 4), and 10 ms is the floor for anything in the safety task, not a guarantee — preemption by higher-priority tasks and interrupts adds to it; tools/schedana is where the integrator shows his schedule (AoU-08, AoU-CFG-3). A later fast control loop at PWM rate (../architecture/fast-control-loop.md (not published, available on request), not implemented) would be an interrupt above the safety task; its credited backstops stay SM-04, SM-06 and SM-01 (section 8.1 there).

    8. Configuration rules for safe operation¶

    The route in two sentences (config-range.md section 1). The relations the stage-1 mechanisms need are verified for the whole declared range by checks that run on every configuration (tools/nxconfig with the YAML path, static_assert on the generated values, generator refusals), so a configuration outside the admissible range does not build. The behaviour of the built software is verified per data set — for the project's own profiles by the project, for his data set by the integrator (AoU-CFG-1 … AoU-CFG-7).

    The value register is config-range.md section 2 (CV-01 … CV-20, 19 values plus the deadman constant): level, declared range, relation checked, what the project verified, route. 11 values are argued for the range, 8 per data set. All target builds of the project use the default safety values (finding G1); on the board only the demo values ran.

    Rules, each from its source:

    1. Build the image only through the build; never edit a generated file; tool versions pinned (AoU-26, AoU-CFG-1).
    2. An error of nxconfig stops the configure run; a warning on a safety value is a finding the integrator resolves or justifies in writing (AoU-CFG-1).
    3. Every power output in the safe outputs table: PWM groups in the project, safe_off: true in the manifest (AoU-06); inactive levels right for the circuit (AoU-07).
    4. The three pins of the safety section only in their role (AoU-30).
    5. The safety task stays above every application task (above_application, checked; config-range CV-18); the watchdog service interval is derived, not set (concept 7.1).
    6. rom_check_period_ms between the longest flash write and the latent-fault interval; 0 means once per start (AoU-25, AoU-CFG-4).
    7. A calibration segment with a parameter whose safety is not qm needs on_invalid: refuse; no XCP in the production profile (config-range CV-15; AoU-28, AoU-SEC-5).
    8. One E2E profile and data ID per safety-relevant signal (AoU-11, config-range CV-17).
    9. Degraded mappings only for degradable events, in groups that share no timer; the integrator confirms independence beyond timer and bus (AoU-32; SSR-088).
    10. The product image is built with -DNX_PRODUCT_BUILD=ON (no test and fault-injection commands; AoU-SEC-6).
    11. bootloader.sbc_watchdog chosen deliberately (AoU-34).
    12. A hardware threshold (hw_thresholds, SM-58) may be configured but carries no credit (section 5); host verified, board proof not part of release R1; the input stays away from VDDA at start (AoU-37).
    13. On s32k1xx the LVD reset is always on (SM-59, not credited): the supply keeps VDD above 3.05 V (AoU-39).

    10.2 Architectural and product limitations¶

    • Single channel on one core: supervisor and supervised share core, clock domain, RAM, flash and supply; no lockstep, no second MCU voting (concept 2.1, AoU-13; dfa.md).
    • No partitioning of the application: the MPU protects the safety manager's data and stack only is open (concept 6.3, AoU-17). Task activation is not supervised (F10).
    • Register lock and check cover the classes derived by an earlier change; the remaining classes are SSR-070 (partial).
    • Run-time comparisons detect a change, not a wrong design (DFA-5 of dfa.md): the MPU descriptor check, the register check and the safe outputs table take their expected values from the same generated data that configured the hardware; a wrong design value, a generator fault or a wrong derivative fact is configured and expected alike. The design side is covered by tool confidence (section 9), generator tests with own profiles and mutants, and board tests of the generated result per project (AoU-DFA-c).
    • A PWM timer whose clock gate is switched off freezes its pins and does not take the walk of the safe outputs table (DFA-4): the group is de-energised only through a safe_off enable on another peripheral bound to it; nxconfig warns for a used group without one, and whether the walk opens the gate first is open for a separate task.
    • Read-back that S1 took effect (G1) closed on the host since an earlier change (S1) (S1 held, the groups of SD, the S1 + S2 sequence of ecu/safety); SSR-060 partial: the hard fault and watchdog handlers and the halt deadman of the family port, board proof B15/B16 open; no plausibility between two sources (G2), no age supervision of device values (G3), no safe state for bus-commanded actuators (G4) — SSR-061 … SSR-063 open.
    • Family port for s32k1xx only (section 1.4); SM-55 and the hardware threshold are not described for every derivative (fmea SM-55, hardware-mechanisms 2.4: S32K116).
    • The bootloader's own integrity is not checked by any stage-1 mechanism (fmea N4).
    • The bootloader phase runs without MCU watchdog (section 4, HSI 4.13): safe only with all outputs in their reset state while it runs (AoU-07, AoU-SEC-3); a hang there is ended by a reset from outside, not by neXtBSW.
    • A lost SIRC (the clock of the halt deadman's LPIT) is a residual risk (section 5, faults of the time bases; dfa.md DF-05): the halt deadman stops with it, nothing walks the table, and only the hardware reset of the MCU watchdog de-energises the outputs, after at most about 283 ms on the eval board; the cause of the hang is open, investigation and architecture with a separate task after release R1. A stopped system time is not seen by the period check (kind 4/5 see only a slow or fast one); the halt deadman SM-06 and the watchdog SM-01 react (section 5).
