    This document is the tool part that the safety concept concept.md hands to a separate task (concept sections 1.2, 8.3, 8.4 and 10.5). It classifies every tool that produces, transforms, transfers or checks a part of the ECU image, says how an error of the tool would be noticed, and names the safeguards that exist and the ones that are missing. It uses the concept's identifiers unchanged (ASG-*, AoU-*, SM-*, F*, G*) and those of the failure analysis fmea.md (F9 …, T*, N*).

    ISO 26262 and this document. Issue 1 was written without the standard. Since 2026-09-22 the maintainer holds a licensed copy of ISO 26262 parts 1–12 (outside the repository). This document now follows ISO 26262-8, clause 11 (confidence in the use of software tools) and is meant as the software tool criteria evaluation report of neXtBSW's tools in the sense of ISO 26262-8, clause 11.5.1; the qualification reports of clause 11.5.2 are proposal G. Licence rule: the standard is cited only by part and clause ("ISO 26262-8, clause 11.4.5"); no sentence, table or figure of it is reproduced, everything is said in this document's own words, and the consistency test safety-tools refuses references to tables or figures of the standard. Where a decision is the safety manager's and not the standard's, it is recorded as such (section 9.2).

    No invented numbers. No failure rates, no probabilities of tool errors, no coverage percentages. The detection levels are ordinal classes with the reasoning written out, like the diagnostic-coverage classes of fmea.md.

    1. Method¶

    1.1 The three questions per tool and use case¶

    A tool is classified per use case, not once for all: the same program can be harmless as a planning aid and relevant when its verdict is used as evidence. The standard asks for exactly this: the usage plan names the use cases, and impact and detection are determined from the intended usage (ISO 26262-8, clauses 11.4.4.1 and 11.4.5; ISO 26262-10, clause 13). A classification is valid only for the use cases it names; a new use case of a tool needs a new classification (impact analysis) before it is relied on.

    1. Tool impact (TI). Can a malfunction of the tool, in this use case, put an error into the product or let an error in the product go unnoticed? The class names are those of ISO 26262-8, clause 11.4.5.2 (issue 1 called them TI0 and TI1; the meaning is unchanged):
    2. TI1 — no: there is an argument that the output does not reach the image, and no verification result that the safety argument relies on depends on it.
    3. TI2 — yes, in all other cases. Every generator whose output is compiled into the image is TI2, and so is every verifier whose "pass" is used as evidence.
    4. Tool error detection (TD). If the tool does malfunction, how confident are we that the erroneous output is prevented or detected before it is used — by a check that does not trust the tool?
    5. TD1 — high: an independent check looks at exactly the erroneous item (an expectation derived without the generator's logic, a check in the linked image, a run-time mechanism that detects this very error class), and the check has been shown to fail on a broken generator or broken output (fault injection).
    6. TD2 — medium: the output is exercised and many errors would show (compiled and executed on the host, validated input, consistency between consumers), but an error that is consistent with itself could pass.
    7. TD3 — low or none.

    Where the choice of TI or TD is doubtful, the more conservative class is taken (ISO 26262-8, clause 11.4.5.3). Our TD1 is deliberately stricter than the standard's wording: it also asks for fault injection that shows the check fires. 3. Tool confidence level (TCL), derived — never chosen (ISO 26262-8, clause 11.4.5.4). In this document's words: a use case without impact (TI1) or with high detection (TD1) is TCL 1; with impact (TI2), medium detection gives TCL 2 and low detection TCL 3. The consistency test applies exactly this rule to every row of section 3.

    TCL 1 needs no qualification method; TCL 2 and TCL 3 need one (ISO 26262-8, clause 11.4.6.1). The standard offers four alternative methods — increased confidence from use (clause 11.4.7), evaluation of the tool's development process (clause 11.4.8), validation of the tool (clause 11.4.9) and development according to a safety standard — and grades them by ASIL. At ASIL B, for TCL 2 as for TCL 3, the first two are the highly recommended ones; validation and development according to a safety standard are only recommended. Because the methods are alternatives, a combination fitting the ASIL may be chosen, the higher-graded ones should be preferred, and the choice needs a written rationale (ISO 26262-8, clause 4.3). For a project whose generators change every week, increased confidence from use is not available (it needs an unchanged specification and holds only for the evaluated version, clauses 11.4.7.2 and 11.4.7.4), and no assessment of our development process exists; validation is therefore the realistic method, with a rationale (section 5, TN3). The standard itself points to the other way out: add checks of the tool output to the development process until TD1, so that no qualification is needed (ISO 26262-10, clause 13) — that is route 1.

    A run-time mechanism (SM-*, K7) counts towards TD only under two conditions (TN1). First, it must detect the specific error class of the tool — SM-51 detects a wrong validity record because the bootloader recomputes it; a mechanism whose own configuration comes from the same generator does not count (a wrong safe outputs table is walked faithfully by SM-23; the standard asks for such interdependencies to be considered, ISO 26262-8, clause 11.4.5.2, note 3). Second, the error must show deterministically before release: the standard names measures of the development process — tests, reviews, checks in the tool — and detection only in the field is not among them (ISO 26262-8, clause 11.2). SM-51 and SM-14 qualify, because a wrong record or reference CRC stops every start of the image, so the integrator's first test on the target sees it (AoU-26). The watchdog behind schedana does not: a starved task shows only under the load that causes it, possibly first in the field — no TD credit.

    1.2 Kinds of safeguard¶

    Concept section 8.4 lists four safeguard kinds that already exist. They are refined here into eight, so that each tool can be credited precisely:

    Kind Safeguard Independent of the generator?
    K1 Independent expectation: the expected content is derived from the configuration by another path — reference-manual register addresses, cantools for the bit layout, a Python reference model, the example values of a specification yes
    K2 Generated code compiled and executed on the host against the generators' own test profiles (not only the eval board) partly: it tests behaviour, but the expectation is often written by the same author as the generator
    K3 Validation before generation: a wrong or incomplete configuration is refused with a message carrying the YAML path, instead of being generated no (same tool) — it prevents configuration errors, not tool errors
    K4 Build-time enforcement in the target code: static_assert, #error, counts that must match (e.g. NX_SAFE_OFF_OUTPUT_COUNT, SM-24), derivative facts checked against the device header yes, if the checked fact comes from a different source than the generated value
    K5 Check in the target artefact: the linked ELF or HEX is inspected (disassembly, symbols, section placement, checksums) yes
    K6 Fault injection: a broken generator, generated file or production code must make the test fail (mutants) shows that K1/K2/K5 detect
    K7 Run-time mechanism that detects the error class of the tool in the product (e.g. SM-51, SM-14) yes, if not configured by the same generator; credited for TD only if the error shows at every start (section 1.1)
    K8 Controlled tool environment: pinned versions of Python packages (tools/ci/constraints.txt, checked by python -m tools.ci check), one interpreter per repository (.venv), generators run by the build only prevents, does not detect

    1.3 What was looked at¶

    For every tool: where the build or the maintainer runs it (CMakeLists.txt, bootloader/CMakeLists.txt, bootloader/updater/CMakeLists.txt, ecu/application/CMakeLists.txt, ecu/uds/CMakeLists.txt, ecu/xcp/CMakeLists.txt, cmake/NxRomCheck.cmake, tools/studio/core/commands.py), which generated files it writes and which mechanism consumes them, and which entries of tools/test/tests.yaml test it and how (read in the test sources: expectation derived how, mutants yes or no, own profiles yes or no).

    3.10 romCheckImage (post-link step of SM-14)¶

    TI2: it writes the reference CRC and the list of areas into the image. TD1: the CRC is checked against a known vector and a register model of the CRC unit, the rules (gaps, content outside the areas, missing or implausible list → build error, changed byte → mismatch) are tested on synthetic images and on the real linker template (rom-check-image, K1, K5, K6); on the target, SM-14 recomputes the CRC at every start and a wrong reference leads to ROM_CHECK_FAILURE and S1 held (rom-check, K7) — fail-safe. An area missing from the list would weaken SM-14 silently, and exactly that is a build error ("does not cover every flash byte"). The K7 credit meets both conditions of section 1.1: SM-14 checks exactly the reference the tool wrote, with its own CRC computation, and a wrong reference stops every start, so it cannot survive the integrator's first run on the target. The only content the tool accepts outside the list is the area with its own reference, which the linker template defines around the calibration segment; the tool refuses it if an area of the list overlaps it, and SM-14 checks it at run time against its own header, not against the tool's reference. TCL 1.

    3.14 Compiler, assembler, linker (arm-none-eabi-gcc 11.4, binutils)¶

    The options of qualification are described in concept section 8.3; the norm answer is TN2 (section 9.2). TI2. TD3 for the image in general: the host tests are built with a different compiler (zig cc / clang), so they prove the logic, not the emitted target code; the checks that do look at the target code cover selected mechanisms only — the disassembly of the fault handlers and the halt deadman (safe-outputs-order), section placement (safety-context-elf), the real linker over the template (application-linker), the CRC over the real hex (rom-check-image), the safe outputs table, the RTE tables and the priorities in the image (safe-outputs-table, elfcheck-timing*) — plus the board runs. The standard asks that tests which do not run in the target environment have their differences to it analysed and covered by later tests in the target environment (ISO 26262-6, clauses 9.4.5 and 10.4.7); today no such analysis exists, which is a gap of the element, not only of the tool argument.

    TCL 3 today. At ASIL B a TCL 3 tool needs one or a combination of the qualification methods, and the highly recommended ones are increased confidence from use and evaluation of the tool's development process; validation is only recommended and then needs a rationale (ISO 26262-8, clauses 11.4.6.1 and 4.3). For GCC 11.4 in our configuration neither highly recommended method is within reach of the project today: confidence from use needs recorded use of this version with this configuration and a systematic record of its malfunctions (clauses 11.4.7.2 and 11.4.7.3), and a process evaluation of GCC would have to be done against a recognised standard (clause 11.4.8). Target TCL 2, not TCL 1: proposal I runs the host tests of the safety modules also as target code (compiled by this compiler with the product options, executed on the target core or its simulator) and compares the results with the host run; proposal J makes the compiler version and options that built an image checkable; proposal L collects the known wrong-code faults of GCC 11.4 for the used options. Together they give TD2 — many miscompilations of safety code would show, but not every construct of the whole image is exercised — and the remaining TCL 2 needs a qualification method with rationale. The decision between (1) a commercial toolchain with a qualification kit, whose predetermined classification must then be checked against our use cases (clause 11.4.2), (2) validation of GCC 11.4 with a test suite for the language subset and options we use, with rationale, and (3) the TD2 route with I, J, L plus validation is the maintainer's (TN2).

    5. Two routes, and which one is taken where¶

    Route 1 — raise detection until TD1. A check of the output that does not use the generator's logic. Its value is independent of how the generator is written, it keeps working when the generator is refactored, and it is visible to the integrator: he can run it on his own project (AoU-26). It is the route for the items of section 4, because there a wrong output is a direct fault mode of the element (concept 10.5). The standard backs this route explicitly: its tool clause applies only where a tool's relevant output is not examined or verified (ISO 26262-8, clause 11.4.1); a code generator whose generated code is verified is its own example of high detection (clause 11.4.5.2, example 1); and the guidance calls adding checks of the tool output to the development process the alternative to qualification, valid independently of the tool version as long as the use cases stay the same (ISO 26262-10, clause 13). Its advantage here is decisive: the generators change every week, and a qualification would have to be repeated for each version.

    Route 2 — qualify the tool (TCL 2) by validation. For everything else a generator writes (UART, pin names, console strings, most of the RTE plumbing) a check per item would be out of proportion. The existing test suites already are a validation in substance: own profiles, a deliberately broken input per check, mutants of the output. What the standard asks of it (TN3):

    • Admissible, with rationale. At ASIL B validation is only a recommended method for TCL 2; the highly recommended ones (increased confidence from use, evaluation of the tool development process) are not available for tools that change every week (section 1.1). Choosing validation alone is allowed because the methods are alternatives, but the record must say why it is sufficient (ISO 26262-8, clause 4.3). The rationale proposed here: the tools are in-house and fully visible, their requirements are written, the validation runs on every commit (so it always matches the version used, which confidence from use never could), it includes fault injection, and the safety-relevant items are additionally covered by route 1.
    • What the validation must show (ISO 26262-8, clause 11.4.9.2): that the tool meets the requirements of its classified purpose; that every malfunction found during validation is analysed with its possible consequence and a measure against it; and how the tool reacts to anomalous conditions — wrong or incomplete input (K3 covers this for the configuration), forbidden option combinations, and an incomplete update of the tool (for us: a package version differing from constraints.txt, a stale generated file, a packaged Studio with older tool copies, TF9).
    • What the record must contain (ISO 26262-8, clause 11.4.6.2, in our words): the tool's identification and exact version; its TCL with a pointer to this document; the maximum ASIL of the requirements it could violate, per use case; the configuration and environment the qualification holds for; who qualified it; the method chosen and its rationale; the results; and the usage constraints and malfunctions found. The planning data of section 1.4 and the information of ISO 26262-8, clause 11.4.4.2 (description, user guide, behaviour under anomalous conditions, known malfunctions with work-arounds) go with it. The work product is the software tool qualification report (ISO 26262-8, clause 11.5.2). That is proposal G.
    • Per version. A qualification holds for the qualified version and environment only (ISO 26262-10, clause 13); a change of the tool or of its environment (Python, a package) needs the validation again. For our tools this is cheap if the record is produced by the CI run of the released commit — proposal G asks for exactly that.

    Common to both routes: the checks run on our test profiles and on the demo. An integrator's project is a different configuration; the safeguards only protect him if they run on his project too. That is the reason for the proposed AoU-26 and for proposal C, which makes the configuration that was checked recognisable in the image. The standard says the same from two sides: a classification made independently of the item must be checked for validity before the tool is used for that item, and the tool must then be used in the version, configuration and conditions the classification assumed (ISO 26262-8, clauses 11.4.2 and 11.4.3); and configurable software must be verified for the configuration data set actually used (ISO 26262-6, Annex C, clause C.4.4).

Use cases are part of the usage plan and impact and detection are determined from the intended usage (ISO 26262-8, clauses 11.4.4.1 and 11.4.5.2; ISO 26262-10, clause 13); a classification holds only as long as the use cases do. Run-time mechanisms: only with two conditions. Detection is credited to measures of the development process — tests, reviews, checks inside the tool (ISO 26262-8, clause 11.2 and clause 11.4.5.2, note 1) — and interdependencies between a tool and whatever checks it must be considered (clause 11.4.5.2, note 3). A product mechanism therefore counts only when it checks exactly the tool's error class independently of that tool and the error shows deterministically in the integrator's own tests before release (SM-51, SM-14: every start fails). Detection that depends on the operating situation (watchdog behind schedana) is not credited. The class names are the standard's: TI1 = no impact, TI2 = impact (clause 11.4.5.2); doubtful cases are estimated conservatively (clause 11.4.5.3) section 1.1 (names, conditions for K7, conservative rule), 3.8, 3.10, 3.11, summary table (TI0/TI1 → TI1/TI2), AoU-26 (first start on target)
    TN2 Which qualification does the compiler need at ASIL B? answered, decision open With TD3 the compiler is TCL 3; at ASIL B the highly recommended qualification methods are increased confidence from use and evaluation of the tool's development process, validation and development according to a safety standard are only recommended; the methods are alternatives, and a combination with rationale is required (ISO 26262-8, clauses 11.4.6.1 and 4.3). Neither highly recommended method is within reach for GCC 11.4 in our configuration (clauses 11.4.7 and 11.4.8). The standard also allows lowering TD by process measures instead of qualifying (ISO 26262-10, clause 13), and independently asks that host tests be complemented by tests in the target environment (ISO 26262-6, clauses 9.4.5 and 10.4.7). Route: proposals I, J, L give TD2 → TCL 2, which still needs a qualification method with rationale. The choice between a commercial toolchain with a qualification kit (its classification then checked against our use cases, ISO 26262-8, clause 11.4.2), validation of GCC 11.4 for our language subset and options, and the TD2 route with validation is the safety manager's — decision log section 3.14, summary table (target TCL 2, proposals D, I, J, L), section 1.4 (compiler identification and configuration), proposals I, J, L
    TN3 Is validation (route 2) enough for TCL 2 generators at ASIL B, and what must the record contain? answered Admissible, but not the preferred method, so only with a written rationale: at ASIL B validation is a recommended, not a highly recommended method for TCL 2 (ISO 26262-8, clauses 11.4.6.1 and 4.3); the highly recommended ones are not available for tools that change every week (clauses 11.4.7.2 and 11.4.7.4). The validation must show conformance to the tool's written requirements, analyse every malfunction found, and examine the reaction to anomalous conditions including an incomplete tool update (clause 11.4.9.2). The record must hold identification and version, TCL with its analysis, maximum ASIL per use case, configuration and environment, who qualified, method, results, and usage constraints and malfunctions found (clause 11.4.6.2), together with the tool information of clause 11.4.4.2; it is the qualification report of clause 11.5.2 and holds per version (ISO 26262-10, clause 13). Route 1 remains the preferred way for the safety-relevant items (ISO 26262-8, clause 11.4.1) section 1.1 (methods), 1.4 (planning data), section 5 (rationale, validation criteria, record content, per version), proposal G (content, P2)
    TN4 May the TD1 of the host compiler rest on the mutation runs? answered Not for all host tests. A mutation run shows that one test, compiled by this compiler, fails on its mutants; it covers the modules that have one. For the rest the choice is doubtful, and doubtful cases are classified conservatively (ISO 26262-8, clause 11.4.5.3), with the interdependency between compiler and verdict considered (clause 11.4.5.2, note 3). zig cc is therefore TD2 → TCL 2 today, TD1 only for tests with their own mutation run; TCL 1 for all after proposals K (a mutation run per safety module) and I (the same tests as target code by a second compiler) section 3.16, summary table (zig cc TD1 → TD2, TCL 1 → TCL 2, target TCL 1, proposals I, K, L), proposal K
    TN5 What must the integrator get for his Embedded Coder classification? answered His code generator is his tool: he classifies it for his use cases and maximum ASIL (ISO 26262-8, clause 11.4.4.1), and as integrator of an element out of context he checks every assumption the element makes (ISO 26262-10, clause 9.2.4.5). neXtBSW must give him what his classification depends on: the RTE interface description; the Embedded Coder settings that tools/swc/swc_create.m applies, because they are part of his tool configuration (ISO 26262-8, clause 11.4.4.1); and the statement that no neXtBSW check verifies the behaviour of the generated model code, so his detection must come from his own verification of that code (ISO 26262-6, clause 9.4.5). Nothing beyond that is needed from neXtBSW; the swc tools themselves stay classified here section 3.13 (second use case of the swc tools), AoU-29 (new) addition

    11. Review questions of the architecture (section 11)¶

    This task changed no reusable code, no generator and no bootloader; it added this document, a consistency test under doc/safety/test/, a test entry, five open requirements with the regenerated matrix, and a pointer in concept.md.

    1. Board without an SBC? Yes. No tool classification depends on the SBC; the safe outputs table and its checks include a board without power outputs (S32K116 profile), and proposal A keeps that profile.
    2. Different crystal and system clock? Yes. The clock plan is classified as a derived value of nxconfig (section 3.1); its check today runs at four system clocks, and proposal C makes the configured clock plan recognisable in the image.

The classification is per tool, not per family; the stm32 generator is part of bswgen's row, and proposal D is explicitly required to run for S32K116, S32K148 and a stm32 profile, and to take its expectation from mcudb, which also holds RM46L852.
    4. Two or more CAN buses and different IDs? Yes. dbcgen's proposal E covers every signal of every DBC of every project; nothing assumes one bus.
    5. Several tasks and freely chosen priorities? Yes. Proposal F compares the task list and priorities of the project with its configuration, whatever they are; the schedana classification distinguishes planning from evidence (AoU-08).
    6. Every new value in exactly one configuration level? No new configuration value. Proposal C adds a derived value (the configuration identity), computed by the generator, not configured.
