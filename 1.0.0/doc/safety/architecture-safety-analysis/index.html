    What this document is. The gap analysis iso26262-gap.md (not published, available on request) section 6 no. 16 asks for a safety analysis at the software architectural level that does not stop at the safety mechanisms: the failure modes of the RTE, the ECU state management, the CAN stack, the NvM and the bootloader and their effect on the software safety requirements (SSR, ssr.sdoc) — part 6, clause 7.4.10 and its informative annex on the analysis of the architecture — and, as measure M5 of the gap analysis, a deductive complement: one fault tree each for the assumed safety goals ASG-01, ASG-02 and ASG-06 that ends in mechanisms and shows the single points. fmea.md analyses the mechanisms themselves (how well SM-xx detects its fault); this document analyses the parts the mechanisms are supposed to protect, and asks for each of their failures: does a requirement break, which mechanism notices, and what is left.

    Licence rules followed here. ISO 26262 is not in the repository. Issue 1 was written in a contributor session without it; since 2026-09-22 the standard is licensed to the maintainer and compared in iso26262-gap.md (not published, available on request) (issue 2 corrects the issue-1 statement "not available"). The standard is cited by part and clause only, as the gap analysis does. The guide words of section 1.2 are this project's own wording; whether they match the annex of part 6 completely is open point O1 (section 9), which needs a reader of the licensed standard. No other standard is quoted.

    What it is not. Not a quantitative analysis (no failure rates, no probabilities — AoU-09), not the analysis of the application components (the integrator's, AoU-17/AoU-18), not the device packages, not the dependent failure analysis (dfa.md, which this document uses and does not repeat).

    1. Method¶

    1.1 Steps¶

    1. Parts and their contribution. For every part: where it runs (task, priority, interrupt), which data and control it hands to the safety part or to the application, and which SSR mention it (section 2).
    2. Failure modes per part (inductive). Every interface and every internal function of the part is walked with the guide words of section 1.2. A failure mode is recorded when it is possible in this code — not every combination of guide word and function; combinations that cannot happen are listed once at the end of each part.
    3. Effect. For each failure mode: local effect (inside the part), effect on the SSR (which requirement no longer holds, or "no SSR speaks about it"), effect on the assumed goals (ASG).
    4. Measure and verdict. The mechanism (SM-xx), requirement or assumption that detects or prevents it, with the test that shows it. Verdict words:
    5. covered — a base-software mechanism or a build check detects or prevents it, with evidence;
    6. covered with application — the base software provides the means (qualifier, E2E, mode), the application must use it; the assumption that carries this is named;
    7. open — nothing detects it, or the mechanism that should is itself missing; a finding is named.
    8. Deductive complement. Fault trees for ASG-01, ASG-02 and ASG-06 (section 5), built top-down from the goal, with the failure modes of section 3 and the mechanisms of fmea.md as the lower levels. A basic event that reaches the top through OR gates only, with no mechanism at any level, is a single point at stage 1.
    9. Findings. Every open verdict that is not already a known finding gets an ASA-n (section 6) with a proposed measure and task.

    1.2 Guide words (project wording)¶

    Guide word Meaning for a software part
    omission a function is not executed, a value not written, a message not sent or not received
    commission a function is executed although it should not be, a value written that should not be
    late / early executed outside its time window (includes "never" as the limit of "late")
    wrong value a value is produced with the wrong content — calculation, wrong source, wrong configuration
    stale an old value is presented as current
    corrupted a stored or transferred value is changed between writer and reader
    wrong sequence steps are executed in the wrong order, or an operation is interrupted between steps
    interference the part changes data or timing that belongs to another part (the three kinds of the freedom-from-interference annex of part 6: memory, timing, exchange of information)

    1.3 Evidence notation¶

    As in fmea.md section 1.4: a test id in backticks names an entry of tools/test/tests.yaml; "review" means code reading at 65f3dc9; "board" names a record in CHANGELOG.md. The consistency test checks that every test id cited in an "Evidence" cell exists.

    Two facts shape the whole analysis and are stated once here:

    • None of the five parts raises a safety event except the RTE (RTE_TIMING_VIOLATION, S3) and, through the ROM check, the calibration re-check (ROM_CHECK_FAILURE). A wild write from any of them into the safety data is SM-10's (covered); into another part's data it is not detected (DF-42). This is not repeated per failure mode.

    5.4 What the trees add to fmea.md¶

    fmea.md section 4 confirms the verdicts "partial" (ASG-01), "covered with limits" (ASG-02, ASG-06). The trees keep those verdicts and make two things visible that the per-mechanism view cannot show:

    1. The ordinary stop paths are not safety paths. Diagnostic resets, the ECU state machine's restarts and the lifecycle run-down all end in a reset that de-energises through the pin reset state, not through S1, and the safety part is shut down before that end (G2.4, FM-ECU-04). For ASG-02 this is the largest structural gap outside the mechanisms: ASA-1, ASA-2, ASA-3.
    2. Silent defaults feed the command path. Three services substitute a value without saying so — the NvM default, the held DIO/ADC value and a disabled reception time-out (ASA-4, ASA-6, ASA-9). The qualifier concept exists (SM-30); these three simply do not use it. Issue 2: the NvM uses it since an earlier change (nvm.qlf.<Block>, ASA-9 closed); the other two remain (ASA-4, ASA-6).

    7.1 Assumptions of use (numbers to be assigned by the maintainer)¶

    ID Assumption
    AoU-ASA-a On a board whose CAN transceiver reports no status (passive transceiver, canPhyPassive), the transmit gate follows the bus-off state only. The integrator confirms that a transceiver fault that does not lead to bus-off is acceptable for his item or adds his own supervision (ASA-10).
    AoU-ASA-b In the product, XCP is either not built in or protected by the integrator; UDS services that write component ports or reset the ECU are protected by security access and by a precondition the integrator defines (until ASA-1/ASA-8 provide one).
    AoU-ASA-c The pins of every power output reach a de-energised level while the MCU is in reset and while the bootloader runs (the bootloader configures only the communication pins and runs with the MCU watchdog disabled). This extends AoU-07 from "reset" to "reset and bootloader" (FM-BL-04, G2.4).
    AoU-ASA-d Until ASA-2 exists, the application switches its actuators off when the ECU mode view reports RUNDOWN, because the RTE does not drive the outputs to their init value at run-down.

    10. Review questions of the architecture (section 11)¶

    This task changed no reusable code, no generator and no bootloader; it added this document and a consistency test under doc/safety/test/. The questions are answered for the analysis and for the measures it proposes.

    1. Board without an SBC? Yes. No failure mode is credited to the SBC; ASA-10 and AoU-ASA-a are exactly about the board with a passive transceiver.
    2. Different crystal and system clock? Yes. No time in this document depends on a clock; the time-outs named are configuration values.
    3. Different derivative, S32K3 / STM32 / Cortex-R? Yes. The parts analysed are family-neutral (RTE, ecuState, CAN core, NvM, bootloader core); the family-specific statements (bootloader hal_init disables the WDOG, FlexNVM READY) are marked as S32K1 and would get their own row per family.
    4. Two or more CAN buses? Yes. The RTE is bound to one bus today (can.bus); the failure modes are per message and per bus, and ASA-4/ASA-7 are rules per message and per port, not per bus.
    5. Several tasks and free priorities? Yes. FM-RTE-01, FM-RTE-07, FM-CAN-10 and ASA-5 are about several tasks.
    6. Every new value in exactly one configuration level? The only new value proposed is bootloader.accept_legacy_image (ASA-12), a project value; ASA-7's confirmation key belongs to rte.yaml at the port, like a separate task's key at its pin. Everything else is derived by the generator.
    7. Host test with its own test profile? The consistency test needs no board profile. The proposed code measures each name a host test (section 6).
    8. Tool core free of Qt, messages with a YAML path? The proposed rtegen/nxconfig checks (ASA-4, ASA-5, ASA-7) are to report with the YAML path of the message or port.
    9. Device driver granularity? Not applicable — no driver analysed.
    10. Placement under platforms/? Not applicable — no new file there.
