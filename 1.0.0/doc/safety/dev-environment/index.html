    neXtBSW development environment: languages, guidelines, tools, build and test flow¶

    Status: 2026-09-28, issue 1, draft for acceptance by the safety manager. Baseline: v0.2.0 Readers: the safety manager, the maintainer, every contributor that writes C, C++ or a generator, and an integrator or reviewer who wants to know with what and under which rules neXtBSW is made. Language: English, like the rest of doc/.

    What this document is. The one place that names the software development environment of neXtBSW, as asked by 6-5.5.1 and found missing by iso26262-gap.md (not published, available on request) (rows 6-01 and 6-02, section 6 task 21; safety plan row P6-01, safety case row EW-14). It states which languages are used and why (6-5.4.2), which coding guidelines cover the topics the standard lists for them (6-5.4.3), the neXtBSW C++ subset NXCPP (section 4), the tools with their pinned versions and tool confidence levels, and the build and test flow per lifecycle phase. It does not repeat what other documents own; it points to them.

    Decision behind section 4. User decision (2026-09-28): neXtBSW defines its own C++ subset and enforces it with the tools it already has (cppcheck, clang-tidy, the compiler, the test runner); deviations are justified; no commercial MISRA C++ tool is bought. MISRA C++:2023 therefore stays not claimed (it is named only as the reference the subset was compared against, section 4.5).

    Licence rule. ISO 26262 is cited by part and clause only (for example "6-5.4.3" = ISO 26262-6:2018, clause 5.4.3); no text, table or figure of it is reproduced. MISRA guidelines are named by number with a short description in our own words, never with their text.

    Consistency test. test/test_dev_environment.py checks this document against the repository: every version of section 5 against the file that pins it, every tool-enforced NXCPP rule against the active compiler options and analysis checks, and the code-scan rules of section 4.3 against the code itself.

    1. Scope and phases¶

    The environment covers the software lifecycle of part 6 as tailored by safety-plan.md for a software SEooC, and the supporting processes of part 8 that need a tool (configuration management cm-plan.md, verification, tool confidence). One environment serves all phases (6-5.4.1 asks for consistency across them): the same pinned toolchain builds, analyses and tests, on the workstation and in CI.

    Phase (clause of part 6) Environment element Where
    Software safety requirements (6-6) StrictDoc in doc/requirements/safety/ssr.sdoc (YAML in doc/safety/requirements.yaml until step 3), tools/trace traceability.md (not published, available on request)
    Architectural design (6-7) natural language and informal notations, module manifests, tools/schedana doc/architecture/README.md
    Unit design and implementation (6-8) C99, C++17 with NXCPP, generators with Jinja2 templates sections 2–4 of this document
    Unit verification (6-9) host tests (zig c++/zig cc), static analysis, coverage, mutation runs section 7
    Integration and verification (6-10) target build (arm-none-eabi-gcc), image checks (elfcheck, disassembly tests) sections 6, 7
    Testing of the embedded software (6-11) eval board, J-Link, Vector VN1610, tools/boardtest section 7.3
    Configuration data (6-C) three-level YAML, tools/nxconfig checks config-range.md

    The workstation is Windows (repository .venv, PYTHONUTF8=1); the CI runs the same pipeline (python -m tools.ci run --strict) on windows-latest by default (.github/workflows/ci.yml); tools/ci fetches the same archives for Linux, which the contributor sessions use. A difference between the three is a tool change in the sense of section 5.4.

    2. Languages¶

    6-5.4.2 asks that the language is chosen by criteria such as an unambiguous definition, support for embedded real-time software and for modularity, abstraction and structured constructs. The choice below was made by OpenBSW, which neXtBSW builds on; the table records the reasons as they apply to neXtBSW.

    Language Standard / dialect Used for Compiler Why this language
    C ISO C99 (CMAKE_C_STANDARD 99), ISO mode -std=c99 (CMAKE_C_EXTENSIONS OFF; DE2 closed) bootloader and updater, E2E library, startup and newlib hooks, C parts of the platform, the C component interface of the RTE arm-none-eabi-gcc small runtime, direct register access, the language of the vendor headers; MISRA C:2012 exists as a mature subset with a free checker
    C++ ISO C++17 (CMAKE_CXX_STANDARD 17), ISO mode -std=c++17 (CMAKE_CXX_EXTENSIONS OFF; DE2 closed) application frame, RTE runtime, drivers, platform port, safety mechanisms (supervisor, watchdog, safe I/O, MPU, ROM check) arm-none-eabi-g++ the language of OpenBSW; classes and interfaces carry the layer and role model of the architecture, templates and constexpr move checks to compile time (static_assert on generated tables); used as the subset of section 4
    ARM assembly GNU as, unified syntax startup, FreeRTOS port, context switch of the fault handler arm-none-eabi-gcc the few places C cannot express (stack switch, exception entry)
    Linker script GNU ld memory layout, generated from bl_memory.ld.j2 by blgen arm-none-eabi-ld layout is data of the derivative (mcudb), not code
    Python 3.12 (tools/ci/.python-version) configuration check, generators, verifiers, test runner, Studio CPython the tools run on the host only; their output is checked (tool confidence, section 5), not their source against a coding standard
    YAML, Jinja2, CMake — configuration levels, generator templates, build description — declarative; checked by nxconfig with YAML paths, templates by reference outputs
    Simulink MATLAB R2024a, Embedded Coder, AUTOSAR Blockset the example application swc/DemoSwc — out of the element's scope (concept 1.2); the integrator's language and code generator

    What a language leaves undefined or weak is covered by the guidelines of section 3: undefined and implementation-defined behaviour of C by MISRA C:2012, of C++ by NXCPP; the target's implementation-defined choices (int 32 bit, little endian, wchar_t 4 byte, plain char unsigned, bit-fields unsigned) are fixed by the toolchain file and given to cppcheck as --platform=arm32-wchar_t4 (tools/misra/rules.yaml).

    4. The neXtBSW C++ subset (NXCPP)¶

    4.1 Basis¶

    NXCPP is a positive list of restrictions on C++17 for neXtBSW's own C++ code (ecu, libs, platforms outside 3rdparty, the C++ parts of bootloader), in the order of the enforcement strength. It starts from the OpenBSW "disallowed features" (no dynamic memory, no RTTI, no exceptions), adds the checks that already runs, and names each rule's enforcement. It is not a MISRA C++:2023 compliance statement (section 4.5).

    Scope rules:

    • Host tests and mocks (**/test/**) are not product code; NXCPP-05, NXCPP-19 and NXCPP-20 do not apply there.
    • OpenBSW copies (tools/openbswsync/copies.yaml) are checked by the tools like our code but reported separately (static-analysis.md section 2); the code scan of section 4.3 includes them, because an OpenBSW construct in the image is in the image.
    • Generated code (board headers, RTE, CAN database, UDS tables) follows NXCPP through its templates; a finding in it is a generator finding.

    4.2 Rules¶

    Enforcement: tool — a tool rejects a violation (build fails with -Werror, or the static analysis or the consistency test turns red); tool + review — a tool catches part of the rule, the rest is reviewed; review — only a review catches it, and the rule names a proposal (section 4.6) that would make it a tool rule. "State" is the measurement at 6f868b5.

    ID Rule (own words) Topic Enforcement Enforced by State 2026-09-28

    NXCPP-02 No GNU language extension outside platform code; in platform code only attributes (section, used, naked, always_inline) and inline assembly subset tool + review cmake: CMAKE_CXX_EXTENSIONS OFF, cmake: CMAKE_C_EXTENSIONS OFF (P2) ISO mode since an earlier change: an extension that conflicts with ISO (typeof, asm without underscores) does not compile; extensions that ISO mode still accepts without -pedantic and the platform-code exception stay with the review; every profile builds unchanged (no source change needed)

    4.3 The code scan (scan: rules)¶

    Four NXCPP rules have no clang-tidy or cppcheck check among the active ones, but can be checked with certainty by reading the source: the constructs are keywords or #include lines. The consistency test test/test_dev_environment.py scans bootloader, ecu, libs and platforms (C++ files .cpp, .h, .hpp; without test, tests, 3rdparty, generated; 357 files at 6f868b5), after removing comments and string literals:

    Scan Rejects
    exceptions the keywords throw, try, catch
    rtti dynamic_cast, typeid
    heap a call of malloc, calloc, realloc, free; a new expression that is not a placement new (new ( …)); a delete expression (= delete of a special member is allowed)
    goto the keyword goto
    headers an #include <…> of a standard C++ header that is not on the allow-list

    Allow-list of standard headers (freestanding or without allocation; each one used today):

    algorithm, array, atomic, cinttypes, cstdarg, cstddef, cstdint, cstdio, cstring, initializer_list, iterator, new, numeric, tuple

    A header outside the list (for example vector, string, map, memory, functional, iostream, thread, mutex) needs either an entry here with the reason (it allocates nothing and needs no OS support) or a deviation (section 4.4). cstdio is on the list for snprintf-style formatting only; file and stream functions are covered by NXCPP-05 (they allocate) and by the newlib stubs, which return errors. new only declares the platform's own operator delete and placement new; it allocates nothing, and elfcheck rejects an image that links operator new or the allocator. Headers of C (stdint.h …) and of the vendor, ETL, estd and OpenBSW are not standard C++ headers and are not scanned.

    The scan is a heuristic reader, not a compiler. It is exact for the keywords and includes it looks for; it cannot see a heap call hidden behind a macro or a library function. That is why P5 adds the check that closes it: the linked image must not contain the allocator. Since an earlier change (2026-10-01) elfcheck rejects every image that defines it (code heap-symbol), so NXCPP-05 is a tool rule (DE5 closed).

    4.4 Deviations¶

    A deviation from an NXCPP rule is written, justified and approved like a MISRA deviation, in the same process (static-analysis.md section 4):

    1. Tool rule, finding of clang-tidy or cppcheck → an entry in tools/misra/deviations.yaml (DEV-nnn, rule, files, source-line pattern or symbol, reason in own words, raised by, approved_by). This exists today; the entries DEV-001 … DEV-014 already cover the register access of NXCPP-11.
    2. Tool rule, finding of the code scan → a comment on the same line, // NXCPP-nn deviation: <DEV-nnn>, and an entry DEV-nnn in tools/misra/deviations.yaml with rule NXCPP-nn ([Proposal] — the misra checker accepts only the rule names of its tools today; until it accepts NXCPP-nn, the test honours the comment only when the DEV-nnn it names exists in the file).
    3. Review rule → the reviewer records the deviation in the task's changelog fragment ("Abweichung NXCPP-nn: Grund") and, if it stays in the code, the comment of item 2.

    Approval is the safety manager's, as for every deviation; an open approval belongs. No NXCPP deviation exists today beyond the approved DEV-002/DEV-003 (register and fixed-location access, NXCPP-11) and the baseline entry of cert-dcl50-cpp (NXCPP-18), which is a baseline finding, not a deviation; it needs a decision (DE6).

    4.5 What NXCPP does not cover, compared with MISRA C++:2023¶

    The subset was compared topic by topic with the rule groups of MISRA C++:2023 (by group, not by rule text). It covers the groups on exceptions, dynamic memory, RTTI, recursion, initialisation, casts, virtual functions and destructors, switch and statement structure, and part of the integral-conversion and concurrency groups. Not covered, and therefore not claimed:

    • the full essential-type model of integral and floating arithmetic (only narrowing, signed bit operations and signed/ unsigned comparison are checked);
    • rules on templates, lambdas and constexpr beyond what the compiler rejects;
    • lifetime rules on references and pointers to temporaries beyond clang-analyzer-cplusplus.* and core.*;
    • the rules on the preprocessor for C++ units (the add-on's C view of C++ gives notices only, static-analysis.md 1);
    • the resource and library rules outside the allow-list of section 4.3.

    An integrator whose process requires MISRA C++:2023 runs a qualified tool on neXtBSW's C++ code himself; this is a proposed assumption of use for a separate task (next to the one of static-analysis.md section 6).

    5.4 Changing a tool¶

    A new version of a pinned tool is a change under cm-plan.md: version, URL and SHA-256 are changed together in the one file of the table, then python -m tools.ci setup and a full python -m tools.ci run --clean; a new ARM GCC must build every target profile warning-free with -Werror; a new cppcheck or clang-tidy needs a new baseline, reviewed finding by finding (tools/misra/requirements.txt header). The TCL argument of the tool is re-read for the new version (tool-classification.md section 3). This document's table is then updated; its consistency test fails until it is.

    6. Build flow¶

    One command (cmake --preset <profile> and cmake --build --preset <profile>) runs all steps; the preset base is cmake/NxPresets.json (Ninja Multi-Config, default RelWithDebInfo with -O2 -g3 -DNDEBUG, CMAKE_COMPILE_WARNING_AS_ERROR ON, C -Wall -Wextra, C++ -Wall -Wextra -Wvla). The toolchain file cmake/toolchains/NxArmNoneEabi-gcc.cmake adds the core options from the derivative and the C++ options of NXCPP-03, NXCPP-04 and NXCPP-21 (-fno-exceptions -fno-rtti -fno-threadsafe-statics), plus -fstack-usage, -ffunction-sections -fdata-sections, -fno-common, -fshort-enums, -mno-unaligned-access.

    Step What Tool Check that follows
    1 read and check the three configuration levels, derive values (clock plan, CAN timing, memory layout) nxconfig messages with YAML path; nxconfig check
    2 generate board headers, memory layout and linker script, bootloader configuration bswgen, blgen reference outputs (bswgen-reference), static_assert in generated headers
    3 generate RTE, CAN database, UDS tables rtegen, dbcgen, diaggen reference outputs (rtegen-reference), static_assert
    4 compile and link bootloader, updater and application arm-none-eabi-gcc, CMake, Ninja warning-free with -Werror
    5 post-link: calibration header, ROM check references, validity record calseg, romCheckImage, canflash record CRC over the real image (rom-check-image)
    6 A2L for calibration a2lgen a2lgen, xcp-host
    7 check the linked image against the configuration elfcheck (sections, core attributes, timing tables, priorities) elfcheck* entries of tools/test/tests.yaml

    A build directory belongs to one compiler; a moved compiler needs --fresh (cmake/NxBuildDirCheck.cmake).
