    neXtBSW board test specification per SSR with operational use cases¶

    Status: 2026-10-02, issue 1, written against an integration branch at 92edce0b, draft for acceptance by the safety manager. No case of this issue was run at the board; every procedure was run on the host against recorded board captures and against a simulated board (section 6). Working state: dev at 92edce0b (after v0.1.0) Readers: the safety manager, who runs the cases at the board and accepts the specification as safety manager; the maintainer, who keeps the suite current with the firmware and links the records into the verification report of a baseline; the reviewer of confirmation measure CM-04 (integration and test strategy). Language: English, like the rest of doc/.

    What this document is. The target test specification that iso26262-gap.md (not published, available on request) section 6 no. 20 asks for and that the safety plan names as part of P6-20 (testing of the embedded software): for every software safety requirement of ssr.sdoc whose verification includes the board, the board test cases that verify it, ordered by operational use case - start-up, S1, S1 held, S2, sleep and wake-up, flashing, diagnostic session and normal operation - with what each case needs at the bench (oscilloscope, 24 V, a motor, the debugger, a person at the board). The cases are repeatable: each one is a procedure of tools/boardtest that drives the console and the CAN adapter, asks the person at the board for what only a person can do or read, records a transcript and evaluates it with fixed checks; the results of a run are archived as a record next to the board captures (section 7).

    What it is not. Not the verification plan: verification-plan.md owns the methods, their ratings, the environments and the regression rings; this document is the specification of the cases at its embedded-software level (its sections 2.3 and 5.2). Not the board regression list of a safety release: which cases run on the tagged image of a safety release, and how a difference analysis may let an earlier record stand (VP-6, task proposal T-VP2), is a separate task; it selects from the cases here and links their records. Not the board checklists of the analyses: fmea.md section 8 (B1 ... B16) stays the place where an analysis says what it needs measured; the cases here take those checks over where they verify an SSR and name them.

    Licence rule. The standard is cited by part and clause only; nothing of its text is reproduced.

    A case that needs a test or special image says so in the column "Image" of section 5.2 and in its build field; the runner prints both before the case starts.

    4. How a case is written, run and evaluated¶

    A case is a procedure in the suite file of the project, tools/boardtest/suites/evalboard_s32k144_demo.yaml (not published, available on request): steps that act (console command, console capture for N seconds, CAN probe, UDS request, wake frame, canflash, an instruction or a question to the person at the board) and checks on the transcript the steps leave behind. The checks are regular expressions matched in order:

    • expect must match after the previous match; its named groups become values of the run (start reason, reset-loop cause, restart gap on CAN, image CRC, ...);
    • absent must not match between the previous and the next matched expect - "no reset while S1 is held", "no event while the ROM check repeats";
    • equals / differs compare captured values (reset-loop cause 0x2 of a fault exception, 0x1 of a watchdog reset, 0x117 of an assertion, wake-up sources not reset);
    • delta compares the difference of two values with a project value (the ROM-check period against modules.safeMemory.rom_check_period_ms, the project's value or the module default) - no time is written into the tool.

    A live run writes the console traffic in the capture format of tools/boardtest/captures and adds lines #> ... for the results of CAN steps, the answers of the person at the board and the output of external tools (#| ...). The same evaluator judges a live transcript and a recorded capture: replaying a capture skips only the #> checks. So every case with a reference capture is checked against what the board really printed, without a board, at every run of the host tests, and a firmware change of a console line turns the case red on the host first.

    Commands (no hardware for the first four):

    .venv/Scripts/python tools/boardtest --project projects/evalboard_s32k144_demo suite list [--oc S2] [--ssr SSR-065]
.venv/Scripts/python tools/boardtest --project projects/evalboard_s32k144_demo suite check      # against ssr.sdoc
.venv/Scripts/python tools/boardtest --project projects/evalboard_s32k144_demo suite matrix     # tables of section 5
.venv/Scripts/python tools/boardtest --project projects/evalboard_s32k144_demo suite replay BT-S2-04 [capture ...]
.venv/Scripts/python tools/boardtest --project projects/evalboard_s32k144_demo --port COM17 suite run START S2 \
    --out tools/boardtest/captures/evalboard_s32k144_demo/<date>_suite-<tag> --image <app.hex> --baseline <tag> \
    --tester <name>

    suite run takes case ids, operating-case codes or all (runnable cases only). A step that cannot run (adapter missing, port busy) ends its case with an error and the run goes on with the next case.

    5. Cases per SSR¶

    5.1 How to read the tables¶

    The first table has one row per SSR that has a board item in ssr.sdoc or a board case: the board items (clauses) of the SSR, the cases that cover them, their operating cases, and whether any of these cases needs the oscilloscope, 24 V, a motor, the debugger or a person at the board; "- (beyond the method)" marks an SSR verified by test or review whose board case adds evidence beyond its method. The second table has one row per case with its image, equipment, the reference capture its checks are tested against on the host, and the earlier board records of the same behaviour. Both tables are generated (suite matrix) and compared with this document by test_suite.py.

    5.4 BT-RUN-08 in detail - bus off and automatic recovery (BTS-6 b)¶

    Equipment: console, CAN adapter, a person at the board (user). Image: dev.

    1. can status before the fault: CAN0 open, phy ..., tx ... (the bus is open and the ECU transmits).
    2. Hand action (operator step of the suite): short CANH and CANL of CAN0 for at least 10 s while the ECU transmits, or pull the terminating resistor and every other node so that no frame is acknowledged. A short of 3 s (2026-09-23) or a wrong bit rate (2026-10-02, com05_busoff) only reaches error passive and does not satisfy the case. Then remove the short (or restore the termination), wait 5 s, press Enter.
    3. can status after the fault must show, in one line: bus off N times (now .. ms, longest .. ms, R recoveries) with N >= 1 and R >= 1, ever bus off yes and recovery automatic. The bus state at that moment is error active (recovered) or error passive, but never stuck in bus off. A status with bus off 0 times fails.
    4. Automatic recovery without a reset or an operator command: canprobe (3 s) must see the ECU's frames on the bus again (#> canprobe: passed).

    Reference capture: the existing records stay (2026-09-23_board/10_com35_can_status_after, which shows the error-passive status after the short, no bus off yet, and 2026-09-22_board/90_com26_p9_recovered, which shows bus off 9812 times ... recovery automatic of a separate task); the first run that reaches the bus off on CAN0 replaces them as the reference.

    7. Records and archive¶

    A run with --out <folder> leaves, per case, the transcript <case>.console.txt and, for the whole run, suite-run.json and summary.md:

    • what ran on what: project, suite file, baseline (tag or commit given with --baseline), git describe of the repository, the image given with --image with its SHA-256, the tester, start and end time;
    • per case: result (passed, failed, error), the SSRs it covers, the values it captured (start reason, reset-loop cause, restart gap, image CRC from canflash, operator readings such as the walk time on the scope), and every failed check with its step.

    The folder goes to tools/boardtest/captures/<project>/<date>_suite-<baseline>/ and is committed like every other board capture; the verification report of the baseline links it (decides which cases a safety release needs). A failed case is a finding: it goes to the anomaly register with the record as evidence, never edited away. A transcript of a passed run can become the reference of its case (references: in the suite file), so the host checks follow the firmware the board really ran.

    9. Review questions of the architecture (section 11)¶

    The tool and the suite file are the only new parts. Board without an SBC, other crystal, other derivative, several CAN buses, several tasks: the tool takes the console baud rate, the CAN bus with its bit timing, the messages of the ECU, the diagnostic addresses and every project value from the project (tools/boardtest/project.py and project_value); the board-specific expectations (console lines of this firmware, signal names, the expected WDOG_CS) live only in the project's suite file, and another project writes its own. Exactly one configuration level: the suite reads project values (ROM-check period) at run time and writes none. Own test profile: the evaluator is tested with a synthetic project whose ROM-check period differs from the eval board's. Core free of Qt, messages with a path: no Qt; suite errors name the file and the YAML path (procedures.BT-X-01.steps[0]...).
