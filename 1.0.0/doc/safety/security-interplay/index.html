    neXtBSW — interplay of functional safety and cybersecurity (N1)¶

    Baseline: v0.2.0

    Status: 2026-09-30, issue 1 (proposal N1 of safety-plan.md), written against dev at 65f3dc9. Readers: the safety manager, the author of any change to the bootloader, UDS, XCP or the console, the integrator who runs the cybersecurity engineering of his item, and the author of the safety manual. Language: English, like the rest of doc/.

    What this document is. The record of the interplay between functional safety and cybersecurity that the gap analysis found missing (iso26262-gap.md (not published, available on request) row 2-02, clause 2-5.4.2.3: the safety organisation keeps communication channels to the cybersecurity side where both touch). For an element without a cybersecurity process of its own the channel is this document: it lists every interface through which code, configuration, calibration data or safety-relevant state of a running ECU can be changed in the field, says what a change through it does to the safety argument, which protection exists, and what the integrator must add as an assumption of use for the safety manual.

    What it is not. Not a threat analysis and risk assessment and not a cybersecurity concept: neXtBSW has no cybersecurity management and makes no cybersecurity claim. Attack feasibility, risk values and cybersecurity goals belong to the integrator's item-level engineering; this document hands him the interfaces and their safety effect as input. Cryptographic hardware and secure boot are the subject of csec-concept.md; they are cited, not repeated.

    Licence rule. ISO 26262 is cited by part and clause only. No other standard is quoted.

    1. Method¶

    Interface. Any path by which, on an ECU in the field and without rebuilding the software, one of the following changes: the program code (application, bootloader), the configuration or calibration data the safety mechanisms use, the non-volatile state they read, or the run-time state of a safety function (running, safe state, reset). An interface that only reads (UDS read services, XCP upload) is not listed; its confidentiality aspect is the integrator's.

    Effect on the safety argument. Which assumed safety goal (ASG), software safety requirement (SSR) or mechanism (SM) of concept.md an unauthorised or erroneous use of the interface can defeat, and whether a stage-1 mechanism would still detect it. "Detected" means detected as a fault, not recognised as an attack.

    Sources. The code at 65f3dc9 (paths in the table), the project files of the demo (projects/evalboard_s32k144_demo/{project,diag}.yaml), csec-concept.md, tool-classification.md (AoU-26 … AoU-29) and concept.md (AoU-10, AoU-16).

    Remarks on the register:

    • IF-01 and IF-02 are the ones that matter most. They replace the element itself. The security access with a per-device key is a real barrier against a casual tester, but as long as the debug port is open (IF-08) the key can be read from the key sector, and as long as the image is not signed, anybody who has the key of one device can load any image with a matching CRC into it. For the safety argument this means: the evidence of the safety case is about the released image; which image runs in the field is protected only by the integrator's measures.
    • IF-03 is safety-relevant even when it is authorised. Programming a vehicle while the item is active switches its safety function off. neXtBSW has no information about the vehicle state; the application hook isModeChangePossible() is the place where the integrator's precondition belongs (S2).
    • IF-05 is the interface where safety and security already meet in code. The plausibility check of a separate task is a safety mechanism (it limits a legitimate but wrong calibration); it happens to limit an attacker too, but only to the range of the design. The production profile of a separate task is the actual closure.
    • IF-07: the fault-injection commands are needed for the verification of the safety mechanisms (board tests of fmea.md section 8). They are a security hazard in a product removes them from the product build.
    • IF-10: the safety case must not count E2E as protection against manipulation. The concept states E2E against faults of the communication channel only (SM-31).

    2.1 Security mechanisms seen from safety¶

    A security mechanism that reacts at the wrong moment can itself create a hazard or remove a safety reaction. The existing mechanisms were checked for that:

    Mechanism Could it weaken a safety reaction? Result
    lockout after 3 failed security attempts (bootloader 10 s, application 10 s) it blocks programming and the protected diagnostic jobs only; no safety reaction depends on them no effect
    refusal of an XCP write (ERR_OUT_OF_RANGE) the previous value stays; the design range is kept no effect (it is a safety mechanism)
    on_invalid: refuse of the calibration segment the application does not start its runnables; the safety task and the supervisor run, outputs stay off safe by design
    updater refuses a secured Flash Configuration Field prevents an accidental lock, but also prevents securing the chip by update (S1) no safety effect; a security gap
    session time-out of the bootloader (S3 server 5 s) the bootloader stays in programming; the application does not run availability only

    3. Rules for the interplay¶

    These rules apply to every change of neXtBSW that touches one of the interfaces of section 2, and to the review of such a change. They are the communication channel of 2-5.4.2.3 for an element without a security organisation.

    ID Rule
    R-1 A security measure never delays or removes a safety reaction: detection, the safe outputs table walk, the safe state and the reset of the safe supervisor keep precedence over every lockout, authentication or session state.
    R-2 A path that exists to test a safety mechanism (fault injection, safe state on command, register writes behind a driver) is a security hazard: it stays behind a build option that is off in the product build, or it is removed from the product build.
    R-3 A security finding that can reach a safety function or change what runs on the ECU is a safety anomaly: it goes into the anomaly register with its effect on the interfaces of section 2, and the safety manager decides.
    R-4 A change that adds, widens or removes an interface of section 2 updates this register in the same merge; the maintainer treats it as a change with safety impact (8-8.4.3).
    R-5 No safety requirement relies on a security mechanism: the stage-1 mechanisms are argued against faults; where a safety argument needs protection against deliberate change, it is stated as an assumption of use (section 4), not claimed.
    R-6 Protection that is configurable (XCP on/off, production profile, security levels in diag.yaml, flash security) is a configuration value in exactly one configuration level and is checked by tools/nxconfig with the YAML path where a combination is unsafe (as for profile: production with xcp).

    4. Assumptions of use proposed for the safety manual¶

    Numbered AoU-SEC-n here so that they do not collide with numbers other tasks propose in parallel gives them their final numbers. They refine AoU-10, AoU-16 and AoU-28, which remain valid.

    ID Assumption of use Interfaces
    AoU-SEC-1 The integrator treats every write of program or calibration data (application, bootloader, calibration segment) as a security-relevant function of his item and protects it with his own measures (secured workshop access, signed images once a related task is available, key management of the per-device keys). neXtBSW verifies integrity and compatibility of an image (SM-51), not its origin. IF-01, IF-02, IF-06
    AoU-SEC-2 The master key from which the per-device keys are derived, and the provisioning step that writes them (tools/canflash/provision.py), are kept under the integrator's key management; a device key must be assumed known once the debug port of that device was open. IF-01, IF-02
    AoU-SEC-3 Entry into the programming session (10 02, lc bootloader) and the ECU reset (11) switch the safety function of the item off for their duration. The integrator implements the vehicle-state precondition (e.g. vehicle stationary, power stage off) in the application hook for session changes, and confirms that the pin reset state of every power output is safe while the bootloader runs. IF-03, IF-04
    AoU-SEC-4 Every DID and routine of the integrator's diag.yaml that writes a safety-relevant value or drives an output is protected by a security level and interlocked by the application (refines AoU-28). The integrator decides whether clearing DTCs (14) and suppressing their setting (85) needs a precondition in his item. IF-04
    AoU-SEC-5 In the product, XCP is off (memory.calibration.profile: production or no xcp: section / NX_XCP=OFF), or the integrator adds resource protection for calibration; the plausibility check of a separate task limits values to the design range but does not authenticate (refines AoU-28). IF-05, IF-06
    AoU-SEC-6 The product image is built without the test and fault-injection console commands: -DNX_PRODUCT_BUILD=ON, which also refuses the build options NX_GD_ENABLE_COMMAND, NX_HARDFAULT_TEST_COMMAND, NX_SAFETY_FAULT_INJECTION_COMMAND, NX_FLEXNVM_PARTITION_COMMAND, and the UART is not accessible in the vehicle (the service commands stay in the product console). IF-07
    AoU-SEC-7 The debug port is closed in the product (flash security set, or the port physically inaccessible) — refines AoU-16. While it is open, none of the protections of IF-01 … IF-06 holds against a person with access to it. IF-08
    AoU-SEC-8 Data a safety function of the application reads from the bus or from NvM is protected against deliberate manipulation by the integrator where his threat analysis requires it (e.g. SecOC); E2E protects against faults of the channel only, and NvM blocks have no protection against deliberate change. IF-09, IF-10

    Reference from the safety manual. The safety manual (doc/safety/safety-manual.md) does not exist yet. Proposal S4: it gets a section "Cybersecurity interface" that states that neXtBSW makes no cybersecurity claim, references this document and carries AoU-SEC-1 … AoU-SEC-8 with their final numbers. The consistency test checks the reference as soon as the safety manual exists.

    What it changes for the register State

    6. Tasks proposed by this document¶

    ID Title Done when Prio
    S1 Flash security in the product a configuration value (board or project level, per architecture section 4) selects secured or unsecured Flash Configuration Field for bootloader and updater; nxconfig refuses secured without a documented rescue path; the updater accepts the configured field; the safety manual states the choice (AoU-SEC-7) P2
    S2 Precondition hook for session change and ECU reset the application's isModeChangePossible() delegates to a hook the integrator provides (default: always allowed, as today), documented in the UDS module; host test with a hook that refuses 10 02 and 11 (AoU-SEC-3) P3
    S3 XCP resource protection or product build without XCP either XCP seed & key on the per-device key (as a separate task), or nxconfig warns when a project has xcp: and a parameter with safety other than qm but no production profile; a project decision (AoU-SEC-5) P3
    S4 Security section in the safety manual doc/safety/safety-manual.md has a section on the cybersecurity interface that references security-interplay.md and carries AoU-SEC-1 … AoU-SEC-8 with final numbers; test_security_interplay.py checks the reference P2

    7. Review questions of the architecture (section 11)¶

    This task changes no code, generator or configuration. Board without an SBC, other crystal, other derivative, S32K3/STM32/Cortex-R: the interfaces are family-neutral (bootloader, UDS, XCP, console); IF-08 names the S32K1 Flash Configuration Field — another family has its own debug-lock mechanism, and S1 makes the choice a configuration value instead of a constant. Several CAN buses: the bootloader listens on one configurable bus; XCP and UDS on the configured buses; every bus that carries IF-01, IF-04 or IF-05 is in scope. Several tasks: not affected. New values: none; S1 and S3 would add values, each in one level. Host test: test_security_interplay.py. Qt, YAML paths, driver granularity, platform rule: not applicable.
