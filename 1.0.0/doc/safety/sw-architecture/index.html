    neXtBSW — software architectural design specification of the safety part¶
    Issue 1, 2026-09-28
    Task Gap analysis iso26262-gap.md (not published, available on request) section 6 no. 7; rows 6-07 … 6-19
    Status draft for review; written by a contributor on the safety manager's behalf (author side, see section 9)
    Built against branch dev at 20b2e04, demo project projects/evalboard_s32k144_demo, build preset evalboard-s32k144-demo (RelWithDebInfo), xPack GCC 11.3.1

    0. What this document is¶

    The software architecture of neXtBSW as a whole is described in doc/architecture/README.md (layers, roles, module manifests, configuration levels) and in the module manifests. The safety documents describe the mechanisms (concept.md section 6), their analysis (fmea.md, dfa.md), the requirements (ssr.sdoc) and the hardware-software interface (hsi-s32k1xx.md). What the gap analysis found missing (rows 6-10, 6-11, 6-18, 6-19) is one view of the safety part that says which units implement which mechanism, in which task or interrupt, with which data, which requirement is allocated to which component at which ASIL, how much of the resources it needs, and how the design was inspected. This document is that view. It adds no mechanism and changes no requirement.

    References to ISO 26262:2018 are given as <part>-<clause> (for example 6-7.4.13), in the project's own words; the standard is not quoted.

    Scope: stage 1 of the concept (base-software mechanisms, concept.md section 1.4) on the only family with a safety port, s32k1xx. Numbers are those of the demo image (S32K144, Cortex-M4F). What changes for other families is named where it matters (section 10).

    1. Components of the safety part¶

    A component here is a group of units with one responsibility and one place in the repository; a unit is a class or a translation unit (the level at which the host tests and the coverage measure). IDs are used by the allocation in section 4.

    Components in the image without an allocated safety requirement (QM by intent): console and its commands, the logger, UDS and DoCAN, XCP, the CAN stack above the gate, NvM, DEM, the device drivers (stage 2), the OpenBSW lifecycle and async framework, FreeRTOS, newlib, ETL. Until the coexistence decision (gap analysis Q4, rows 6-13 and 6-14) they count as ASIL B by default — they run in the same address space and on the same stacks as the safety part (section 3.4 shows that the console and the ETL assert handler are on the deepest stack paths of the safety task).

    1.1 Interfaces inside the safety part¶

    Interface Provider → user Form Rule
    Monitor API trigger(context), check(bool), hit(checkpoint) C-SUP → every mechanism member monitors of SafeSupervisor::getInstance() detection only raises an event; the reaction is decided in SafeSupervisor::handle() alone (SSR-001, concept section 5)
    Deferred event box C-SUP ← C-RTE (tasks without write access) plain struct in general .bss, delivered by deliverDeferredEvents() in the safety cycle the reporting task never opens the MPU gate
    Safe state enterSafeState() / leaveSafeState() C-SIO → C-SUP functions S1 is one-way upwards: leaving releases only the indicator (SSR-004)
    Safe outputs table nxSafeOutputs[] C-GEN (generated) → C-HFH, C-SIO, deadman ISR const array of address/value/clock-gate words in flash walked without stack, RAM or driver objects; the same table for every switch-off path (SSR-005)
    MPU gate fusaGateGetLockAndUnlock(), ProtectedRamScopedUnlock C-MEM → C-LCY functions + RAII scope the protected RAM is writable only inside the safety cycle and the safe ISR hooks (SSR-020, SSR-021)
    Safe ISR hook SafePreIsrHook/SafePostIsrHook C-LCY → safe handlers (SAFE_ISR) wrapper per vector opens and closes the gate around a safety interrupt
    Watchdog BSP safety::bsp::Watchdog family BSP → C-WDG static class serviced from the safety task only (SSR-010)
    Supervision-peripheral expectations C-INT (LpitHaltDeadman::EXPECTED_CONFIGURATION) → C-SPC constexpr struct one definition for init and check
    Generated configuration C-GEN → all headers from project.yaml / mcudb (NX_MODULE_SAFELIFECYCLE_*, safeIoConfiguration.h, safeOutputsConfiguration.h, interruptPriorities.h) values in exactly one configuration level, relations checked by nxconfig and by static_assert (SSR-011)

    2. Dynamic view¶

    2.1 Execution contexts¶

    Priorities are the ordering keys of ecu/asyncCoreConfiguration/tasks.yaml; FreeRTOS priorities follow from their order. Stacks from ecu/application/src/app/app.cpp and ecu/configuration/include/app/appConfig.h.

    Context Priority / level Stack Safety content
    task safety 60, highest (above_application: true) 2048 B (safetyStack, MPU) safety cycle every task_period_ms = 10 ms (project value), watchdog service every 7th cycle, delivery of deferred events; lifecycle transitions of the component "safety"; console command safety
    task sysadmin 50 2048 B lifecycle manager (run levels)
    task can 40 2048 B CAN transceivers, transmit gate (SM-32), UDS, XCP
    application task swc (RTE) 30 2048 B runnables of the SWCs; deadline supervision raises into the deferred box (SM-05)
    task bsp 20 2048 B BSP, SBC, ECU state (SM-50, SM-53), halt deadman retrigger (SM-06)
    task background 10 2048 B run-time statistics
    idle 0 2048 B console input, logger output, ROM check pass (RomCheck::idle, lowest priority, preempted by every supervised task: SSR-025)
    FreeRTOS timer task highest + 1 1024 B —
    HardFault / BusFault / UsageFault fixed above all levels MSP 4096 B (1024 B before), 1 KB no-write guard below customHardFaultHandler: safe outputs table first (SM-17), dump, reset: an MSP below the stack limit (overflow into the guard) is moved back to the top before any C code, own line
    ERM double-bit, FTFC fault, WDOG pre-reset NVIC level 0 (reset value, not set by the image) MSP ECC (SM-15, SM-16) via SAFE_ISR; WDOG_EWM branches to the fault handler
    LPIT0 ch 1 — halt deadman level 4 = NX_IRQ_MAX_SYSCALL_LEVEL − 1, above the RTOS boundary MSP walks the safe outputs table when not retriggered within 10 ms (SM-06)
    FlexCAN0 message buffers level 8 (rank 3) MSP receive/transmit; SAFE_ISR wrapper
    LPUART2 console level 9 (rank 4) MSP —
    SysTick, PendSV, SVC level 15 (kernel) MSP scheduler; configASSERT → RTOS_ASSERT (S1 + S2)

    2.2 Start-up and lifecycle levels¶

    1. Reset_Handler → main() of the family port: clocks, watchdog configuration, watchdog self-test (SM-07, SSR-017; failure → S1 held), reset-loop limit (startResetLoopLimit, SSR-065; limit reached → S1 held), MPU init (SM-12), ROM check registration, then the scheduler.
    2. app::startApp() adds the lifecycle components; run level 1: platform, runtime, safety (SafetySystem::init → SafetyManager::init: watchdog, supplies, pin lock (SM-21), cycle timer, period check), ecu; run level 2: platform part two; level 3: UDS, XCP; level 8: sysadmin; level 9: RTE.
    3. SafetySystem::run schedules the safety cycle at a fixed rate of 10 ms in the safety task.
    4. Shutdown (run-down, SM-53): components in reverse order with a time-out per step; SafetySystem::shutdown cancels the cycle and disables the watchdog.

    2.3 One safety cycle (SafetyManager::cyclic)¶

    ENTER → MPU gate state on entry (SM-11) → period check against LPTMR (SM-04) → PERIOD_CHECKED → every 7th cycle the watchdog service with its own enter/leave sequence and configuration re-check (SM-01 … SM-03) → safe_memory::cyclic (MPU descriptors SM-13, ECC status) → MEMORY_CHECKED → SafeSystem::cyclic (ADC reference SM-18/19, internal supplies SM-20) → SYSTEM_CHECKED → SafeIo::cyclic (register check SM-22) → IO_CHECKED → supervision-peripheral checks (deadman SM-06, watchdog control) → PERIPHERALS_CHECKED → delivery of deferred events (RTE deadlines) → LEAVE → MPU gate state on exit. Every checkpoint is a hit() of the sequence monitor (SM-04): a skipped or reordered check is SAFETY_MANAGER_SEQUENCE_DEVIATION.

    2.4 Reaction sequences¶

    Reaction Sequence (all in SafeSupervisor::handle() under the interrupt lock) Events (demo)
    S3 report and continue log line, return RTE_TIMING_VIOLATION, DEVICE_REPORT, CHECK_REGISTER_ERROR without I/O support
    S1 enterSafeState(): walk the safe outputs table, indicator on; leaveSafeState() when the register is correct again (indicator only, SSR-004) CHECK_REGISTER_ERROR (with PLATFORM_SUPPORT_IO): its context names the cause - 1 check fine again, 0 the SAFETY_TEST pin, else class (bits 31..24) and entry (bits 15..0) of the register list, in the log line
    S1 + S2 enterLimpHome() → enterSafeState() → console line → reset-loop record → softwareSystemReset() sequence deviations, watchdog configuration/service, MPU, ECC, ADC reference, supplies, lock register, deadman configuration, period violation, STACK_OVERFLOW, RTOS_ASSERT
    S1 held holdSafeState(): limp home, S1, one console line, then loop: walk the table again, service the MCU watchdog; interrupts stay locked; ends only with power cycle or external reset WATCHDOG_STARTUP_CHECK_FAILURE, ROM_CHECK_FAILURE, DEVICE_FAULT (well-formed report of a device configured for it; otherwise S1 + S2), RESET_LOOP_LIMIT
    bypass fault handlers and the halt deadman walk the table before anything else, then dump/report (concept section 5) HardFault, BusFault, UsageFault, WDOG_EWM, deadman time-out

    The reaction times per class are in concept.md section 7; they are not repeated here.

    3. Freedom from interference — what the architecture provides¶

    Summary of what exists (details: concept 6.3, dfa.md, task for the rest), sorted by the three kinds of interference of 6-Annex D:

    Kind Provided Not provided
    memory MPU region for the safety data and the safety stack, gate open only in the safety context (SM-10 … SM-13); runtime stack check of every task at the context switch (configCHECK_FOR_STACK_OVERFLOW 2 → STACK_OVERFLOW, S1 + S2); since an earlier change a guard of 1 KB directly below the interrupt stack (MSP) that the core may read but not write (MPU descriptor 6, checked every cycle by SM-13): an overflow ends in the hard fault reaction (SM-17) no partitioning of the application; before a later change the MSP had no guard (section 7.3, finding STK-2)
    timing and execution safety task above every application task; period check against an independent timer (SM-04); program-flow checkpoints (SM-04); watchdog with window relation (SM-01 … SM-03); halt deadman above the RTOS boundary (SM-06); RTE deadlines (SM-05, report only) the watchdog follows one task (AoU-14)
    exchange of information E2E for configured signals (SM-31), qualifier for analogue values (SM-30), deferred event box instead of opening the gate no protection of the internal RTE buffers against a faulty writer in the same address space

    5. Design principles applied (6-7.4.3)¶

    Principle (own words) How the safety part meets it Gap
    hierarchical structure detection → reaction → recovery (concept section 5); family-neutral C-SUP/C-WDG over the family port —
    restricted size and complexity of components one mechanism per unit in the family port; the supervisor's handle() is the one large switch by design handle() has 23 cases; its cyclomatic complexity is not measured
    restricted size of interfaces monitor API with three calls and one context word —

    7. Worst-case stack¶

    7.1 Method¶

    tools/stackuse (README) combines the -fstack-usage output of the build with the call graph of the linked image. Frame of a function = the larger of its .su value and the sum of its stack decrements in the disassembly; call graph on the exact symbols; indirect calls only as far as the profile resolves them, otherwise the context is marked incomplete; recursion only as bounded where the profile says so, with the number of times a function can be on the stack. The facts the image does not contain (contexts, stacks, targets of indirect calls, interrupt levels) are in the profile profiles/evalboard_s32k144_demo.yaml, each with its source. The full report of the baseline build is reports/evalboard_s32k144_demo.md (not published, available on request).

    Cross-check of the two frame sources in the demo image: 1 457 functions have both; 1 308 agree exactly, 14 have a larger sum in the disassembly (taken), the rest are template instances merged under one key (the larger .su value taken). 895 indirect call sites exist in the image (310 virtual); the profile resolves 51 callers.

    Task stacks carry, in addition to the call tree, the exception frame of a preemption and the context FreeRTOS saves on a switch: 108 B + 100 B = 208 B (context_bytes). Interrupt handlers run on the MSP; per nesting level one exception frame of 108 B (Cortex-M4F, extended frame with lazy FP stacking, plus alignment).

    7.5 Limits of the estimate¶

    • The profile's resolutions of indirect calls are a review item: a wrong resolution hides a path. Each resolution names its source in the profile.
    • Merged branches over-estimate (see 7.2); nothing under-estimates as long as the resolutions are complete, no function uses alloca or a VLA (the image has none: all .su qualifiers are static) and the bounded cycles are bounded as stated.
    • Measured values are not available: a stack watermark on the board (FreeRTOS uxTaskGetStackHighWaterMark, MSP fill pattern) would give a lower bound to compare against — open, needs the board. : main() fills the free MSP with a pattern as its first statement; inject mspuse (test build with NX_SAFETY_FAULT_INJECTION_COMMAND) prints the high-water mark since then, which includes the start-up phase the tool only bounds from below. Board run open.

    10. Other families¶

    The family-neutral components (C-SUP, C-WDG, C-RTE, C-E2E, C-CAN, C-ECU) carry over. The family port (C-LCY, C-MEM, C-SYS, C-SIO, C-SPC, C-HFH) exists only for s32k1xx (concept.md 1.3). The stack tool is family-neutral for Arm Thumb-2 images (Cortex-M and the Thumb state of Cortex-R); a new family needs its own profile with its exception frame size (Cortex-M0+: 32 B, no FP; Cortex-R4F: the port's own interrupt frame, no hardware stacking) and, on Cortex-R in ARM state, an extension of the instruction patterns in sp_decrement (stmfd, sub sp, sp, # are covered, push in ARM state is the same mnemonic).

    11. Review questions of the architecture (section 11)¶

    Changes: a new document and a new tool under tools/stackuse (host tool, not in the image).

    1. Without an SBC: the tool and the document are independent of the SBC; the MCU watchdog path is described.
    2. Other crystal / clock: no clock value in the tool; frames do not depend on the clock.
    3. Other derivative / S32K3, STM32, Cortex-R: the tool reads any Arm Thumb image; derivative facts (MSP size, exception frame, levels) are in the profile. Section 10 names what a Cortex-R profile needs.
    4. Two or more CAN buses: CAN handlers are contexts of the profile; a second bus is a second entry.
    5. Several tasks, free priorities: every task is a context of its own with its own stack; ISR levels come from the profile.
    6. One configuration level per value: the tool introduces no configuration value of the image; the profile only records image facts with their source (stack sizes, levels), it does not feed the build.
    7. Host test with its own profile: tools/stackuse/test/profile_test.yaml with a made-up image; the demo profile is tested against the real build only when one exists.
    8. Tools free of Qt, messages with YAML path: no Qt; profile errors name the YAML path (contexts[0].entries).
    9. Device drivers: not affected.
    10. Files under platforms/: none.
