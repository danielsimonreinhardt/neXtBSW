    neXtBSW hardware-software interface of the stage-1 safety mechanisms — s32k1xx¶

    Working state: dev at 6812a0b4 (after v0.2.0)

    Status: 2026-09-28, issue 1, written against dev at ae92e89. Task no. 8 of iso26262-gap.md (not published, available on request) section 6 (requirement 6-04 of its section 2.2: the hardware-software interface is refined and every safety-related dependency described). Readers: the integrator (safety manual), the contributors of the register list, ECC injection, hardware paths (freedom from interference), and whoever writes the HSI of the next family. Language: English, like the rest of doc/.

    Update (2026-09-30, finding H9, anomaly AN-066). Decision of the safety responsible 2026-09-30: the family port switches the PMC low-voltage detect reset on instead of leaving the gap to AoU-09. boardInit() writes PMC_LVDSC1 = LVDRE (reset on, interrupt off, no acknowledge) in every start (platforms/s32k1xx/port/main/include/pmc/LowVoltageDetectReset.h); a VDD falling below VLVD (2.80 … 3.00 V) now resets the MCU instead of only a VDD below VLVR (2.50 … 2.70 V). Rows changed: section 2 (PMC), 4.8 (LVDSC1), 5 (LVD/LVW vector), 8 (H9, now partly closed) and 9; the mechanism is catalogued as SM-59 in concept.md 6.4 (not credited) and analysed in fmea.md. What remains of H9: the bit is written at each start but not re-checked cyclically (it is not in the SafeIo list, 4.9). Host verified with a register model; board proof open.

    Update (2026-10-01, rest of H9). PMC_LVDSC1 is now an entry of the SafeIo list (4.9, class SUPERVISION, mask 0x30, expected 0x10, 8-bit access; the engine got an access width per entry). A cleared LVDRE or a set LVDIE is seen within one safety cycle (S1). H9 closed except VLPR/VLPS; the bootloader sets LVDRE itself since an earlier change. Host verified; board proof open.

    Update (2026-10-02, safety review check point, findings SFP-F02 … SFP-F04 of reviews/code-inspection/INS-SFP-1.md (not published, available on request)). Section 4.4: RGD0_WORD2 is now really compared every cycle (it was claimed but never read), WORD2 of every descriptor is compared in all fields of the bus masters 0 … 3 (before only M0 … M2), the rows name descriptors 1 … 7 (guard, part of SFP-F12), and the statement that the descriptors keep M2/M3 out of the protected RAM is corrected: descriptor 0 grants them rwx (H10, section 8, section 0). Host verified with a register model and 15 mutants; board check B17 (fmea section 8) open.

    Update (2026-10-04, re-check of CM-02, decision BRD a). Board check B17 (2026-10-02, fmea.md 8.2) reads RGD0_WORD3 = 0: the valid bit of descriptor 0 is not set after init(). Section 4.4 and H10 carry this as a caveat: the M2/M3 rights of descriptor 0 may not be in effect; until the reference manual settles it this document keeps the unfavourable reading, and the restriction of descriptor 0 stays.

    This document lists, for the family s32k1xx, every peripheral, register class, clock, interrupt and pin that a stage-1 mechanism of concept.md / fmea.md depends on, with the configuration the mechanism expects, who writes that configuration, what re-checks it, and where each value comes from (derivative database mcudb, board, project, or a constant of the family port). It is derived from mcudb/s32k1xx/*.yaml, from fmea section 5.2 (register classes of SM-21/SM-22) and from the code of platforms/s32k1xx; register facts that the code relies on were read again in the S32K1xx Reference Manual Rev. 13 in the repository ([RM13], doc/hardware/s32k1xx/S32K-RM.pdf) where section 11 says so.

    Scope. Stage 1 only, as in fmea.md: mechanisms whose detection runs on the MCU and uses only the MCU, its peripherals and the configuration. Device-dependent mechanisms (SM-33, SM-40 … SM-43, SM-52) have their HSI in the device packages. The hardware paths of hardware-mechanisms.md are not used today; section 9 lists them only so that their registers are not mistaken for unused.

    Not a copy of the reference manual. The tables name registers and fields and the value neXtBSW expects; for the meaning of a field see [RM13]. Where a field is written by the OpenBSW driver in external/openbsw (never changed in the submodule), the table says so.

    1. Reading rules¶

    1.1 Columns¶

    Each table in section 4 has one row per register or field group:

    Column Meaning
    Register / field peripheral register and the fields that matter; x = instance or index from the configuration
    Expected the value or relation the mechanism assumes while the ECU runs
    Written by the code that sets it (file under platforms/s32k1xx unless stated), or "reset value" if nobody writes it
    Re-checked by the mechanism or check that detects a deviation at run time, and how often; "—" = nothing
    Value from family = constant of the family port (register facts, fixed choices of the mechanism); mcudb = derivative database; board = boards/<board>/board.yaml; project = projects/<project>/project.yaml (including module parameters); derived = computed by tools/bswgen or tools/nxconfig from those

    1.2 Status words for the check¶

    Word Meaning
    cyclic compared with the expected value in every safety cycle (nominal 10 ms, guaranteed 17 ms while the task runs, fmea section 2) or at the stated period
    start compared once after it was written
    self-healing rewritten before each use, so a drifted value does not survive the next use
    fail-safe by access a drift makes the next access of the mechanism fault (bus fault → HardFault → SM-17), which is a safe reaction
    not checked a drift is not detected; the row names the consequence — these rows are the findings of section 8

    The bootloader phase is not supervised by the MCU watchdog. From the reset until the application has enabled the watchdog in its start-up, a hang (program flow, a peripheral that never answers) is not detected by any neXtBSW mechanism; it ends only by a reset from outside (power cycle, the SBC watchdog the bootloader serves — always with an SBC without software development mode (SDMS 0; since an earlier change also if the SBC is only read), with bootloader.sbc_watchdog: serve also with it; AoU-34 — or a tester's ECU reset). The SBC watchdog then supervises only the bootloader's main loop, not its program flow. Why SDMS 0 is always served (safety review SBC watchdog 2026-10-06, SDMS0-1 c): after an SBC reset without development mode the UJA113x watchdog is a timeout watchdog with 128 ms that already runs in Standby (public data sheet UJA113X_SER Rev. 2, Table 7 with 7.2.1 and Table 8). A bootloader that left it alone would be reset over and over without a valid application and would hand the application only the rest of 128 ms since the SBC reset; leave therefore takes effect only with SDMS 1. The same holds for an SBC that is only read (safety review bootloader 0.3.10 2026-10-07): the watchdog runs whether or not the bootloader needs the SBC as its transceiver, so the hook sets up the watchdog alone; it needs Standby for the setting (data sheet 7.2, 7.3.3) but not Normal mode for serving, so V2 and CAN stay as found. The updater is not changed: it still refuses to run unless the SBC watchdog is off (SDMS 1). This is acceptable because the bootloader configures no pin of a power output: all outputs keep their reset state while it runs (AoU-07, AoU-SEC-3), and a bootloader that stays is a state with de-energised outputs. The decision to start the application does not rest on RAM state of the past: since an earlier change the start is checked again immediately before hal_jump_to_app(), and a record without compatibility block is not started. Since an earlier change (bootloader 0.3.8) that second check reads record, compatibility block and entry again from flash and requires the record's size and CRC field to be the ones the single CRC-32 over the image of bl_init() was computed for and matched; it does not compute a second CRC over the image (0.3.7 did, about 160 ms per start after the start-up window). This is sufficient because the bootloader issues no flash command between the two checks: erase, download and the record write need the programming session, which keeps the bootloader from jumping. An image body changed without such a command (debugger, bit error) is not seen again before the jump; it is covered by the flash ECC and by the application's ROM check SM-14 at its start (bootloader README, "One CRC per start"). The flash read path of the checks is unchanged (ECC of the program flash; a non-correctable error during the check is a bus fault and resets, BLI-F02).

    4.15 SM-34, SM-53 — no MCU hardware of their own¶

    SM-34 (device reports to the safe supervisor) is a software report path in RAM; its hardware interface is that of the reporting device package. SM-53 (defined run-down) drives the supply role through its driver; since an earlier change its last run-down step walks the safe outputs table (the registers of 4.10, the same walk as the fault handlers), and since an earlier change an overdue restart ends in the software reset of 4.7 after the same walk. The rest is device-dependent.

    8. Findings — configuration that is relied on but not re-checked¶

    IDs H1 … H10 are local to this document. Proposals, not decisions; the maintainer assigns task IDs.

    # Finding Consequence if the value drifts Proposal
    H1 NVIC enable and priority of the watchdog warning IRQ (WDOG_EWM_IRQn) are written once (enable by the OpenBSW driver, priority left at its reset value) and never read back. SM-02 checks WDOG_CS[INT] only with the IRQ disabled or delayed, the watchdog still resets, but the de-energising before the reset (SM-01 reaction, SM-17 walk) is lost; the pins go to their reset state (AoU-07) add NVIC enable and priority of the vector to checkWatchdogControl() (same pattern as checkLpitDeadman), expected values from the family port; or class SUPERVISION of the SafeIo list
    H2 SCB_SHCSR fault enables must stay 0: BusFault_Handler and UsageFault_Handler print and reset without the walk, MemManage is DefaultISR a set enable bit turns an MPU violation or an ECC read error into a handler that does not switch the outputs off before the reset either a start-up + cyclic check SHCSR & (MEMFAULTENA|BUSFAULTENA|USGFAULTENA) == 0 in the family safety port, or point all three vectors at customHardFaultHandler; the second removes the dependency
    H3 ERM (CR0) and FTFC (FERCNFG[DFDIE]) fault interrupts must stay disabled: their handlers (isr_erm.cpp, isr_ftfc.cpp) print and loop forever without the walk. Nobody sets their priority, so an enabled one would run at the reset level 0 like the watchdog vector, which then cannot preempt the loop an enabled ERM/FTFC IRQ turns SM-15/SM-16 into "stuck in an ISR until the watchdog resets" — 250 ms without de-energising, then the reset make the two handlers walk the table and reset (as HardFault_Handler_Final does), and add ERM_CR0 == 0, DFDIE == 0 to a cyclic check; alternatively state them as configuration rules in the safety manual
    H4 the LPIT functional clock (PCC_LPIT[PCS], SCG divider SIRCDIV2 in the demo) is not checked; TVAL1 is checked in ticks a slower LPIT clock stretches the deadman time-out beyond 10 ms (a faster one gives false trips, safe direction) include PCC_LPIT (CGC, PCS) and the source divider in the deadman check or in class SYSTEM_CLOCK
    H5 the system clock (SCG RCCR, dividers, source status) is not in the register list (class SYSTEM_CLOCK reserved). The FTM of a PWM group counts the system clock, so PAIRnDEADTIME (checked in ticks) means a different time at a different clock: a faster clock shortens the dead time — the hazard of ASG-01 that no other mechanism sees. SM-04 notices a changed clock only through the OS tick, i.e. only if SysTick runs on the same wrong clock and the change exceeds the period tolerance (12 … 17 ms band) shoot-through risk on a bridge with a clock that is too fast but inside SM-04's band SCG class with RCCR/CSR (source and dividers), SOSCCSR/SPLLCSR (CM, CMRE, VLD, LK — the lock is only a write guard, [RM13] 28.3.8); expected values derived from the clock plan
    H6 FTMx_OUTMASK, FTMx_SWOCTRL and GPIOx_PDOR are not read back (known, G1) the safe state is written but not confirmed (unchanged)
    H7 SIM_PLATCGC (clock gates of MPU, ERM, EIM, DMA, MSCM; reset value 0x1F) is not written and not checked; what a gated MPU or ERM does to SM-10…13 and SM-15 was not analysed here possibly a silently inactive MPU or ERM analyse against [RM13] ch. 11/15/22 and add CGCMPU, CGCERM to the cyclic check (class SUPERVISION)
    H8 SIM_CHIPCTL[ADC_SUPPLYEN] is written once at init and not checked assumed safe direction (the supply reading fails the band → SM-20) — not verified host test of that case in safe-system, or include the bit in the rotation write (self-healing)
    H9 PMC low-voltage detect reset is off: PMC_LVDSC1[LVDRE] = 0 after POR and nobody sets it ([RM13] 41.7.1.2); only the low-voltage reset (LVR) and POR act. Partly closed by an earlier change (decision of the safety responsible 2026-09-30, AN-066): boardInit() sets LVDRE in every start (SM-59). Closed by an earlier change (cyclic check and class SUPERVISION) (bootloader sets LVDRE); remaining: LVD off in VLPR/VLPS before a later change: a supply between LVD and LVR threshold was detected by SM-20 (1.2 V / 3.3 V band) only, at safety-task speed. Until a follow-up task: a bit flip that clears LVDRE went unnoticed until the next start (the LVR still acts); since an earlier change it is CHECK_REGISTER_ERROR within one safety cycle (S1 without reset) add PMC_LVDSC1 (mask 0x30, expected 0x10, 8-bit access) to the cyclic check — class SUPERVISION of the SafeIo list (generator collect_safe_io()) or a check next to checkWatchdogControl() - done by an earlier change in the SafeIo list; board proof open
    H10 descriptor 0 (whole address space) grants the bus masters M2 (DMA) and M3 (ENET, S32K148) rwx, so the locked gate word and the guard do not keep them out of the protected RAM, the safety stack and the guard; master assignment per [RM13] 15.1.2 Table 15-3 (M4 … M7 not implemented). Corrected by an earlier change (finding SFP-F03): this row said before that the descriptors give M2/M3 no access.     Observation without a finding: WDOG_CS[DBG] = 0 (the watchdog stops in a debugger halt) and FTMx_CONF[BDMMODE] = 01 (outputs safe in a halt) are consistent with the deadman design of SM-06; CS[STOP] = CS[WAIT] = 1 keep the watchdog running in the low-power modes neXtBSW does not use today.
