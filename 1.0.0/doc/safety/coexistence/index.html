    Baseline: v0.2.0

    What this document is. The coexistence decision of the safety plan (activity P9-02, P6-06) worked out for every module in the demo image: which software is ASIL B, which stays QM, and for each QM module the argument per kind of interference that it cannot violate an ASIL B requirement — or the finding that says why the argument does not hold yet and which task closes it. It is the work product doc/safety/coexistence.md named by the safety plan (P9-02, CM-09) and the safety case (EW-20).

    Licence rule. ISO 26262:2018 is cited by part and clause only (for example "6-7.4.8"), requirements are restated in our own words; no text, table or figure of the standard is reproduced.

    What it is not. Not the partitioning design (builds it; section 7 is the hand-over), not the qualification of pre-existing software, not a statement that the image is free from interference today.

    1. Reading of the rule and classes¶

    1.1 What the standard asks (own words)¶

    • 6-7.4.8, 9-6. When software elements with different ASILs — or QM and ASIL elements — share one image, either everything is developed to the highest ASIL, or it is shown for each lower-rated element that it cannot interfere with the higher-rated ones. Without that evidence the lower-rated element inherits the highest ASIL.
    • 6-7.4.9. If freedom from interference rests on partitioning, the shared resources are handled so that the separation holds, the partitioning software itself is developed to the highest ASIL of the partitions, and its effectiveness is shown at integration. Hardware support for the partitioning is demanded only at ASIL D; an MPU on one core is admissible at B.
    • 6-Annex D. Interference is considered in three kinds: timing and execution (blocking, deadlock, livelock, wrong allocation of execution time, wrong synchronisation), memory (corruption of content, access to memory allocated to another element), exchange of information (repetition, loss, delay, insertion, masquerade, corruption, wrong sequence of data, blocking of a communication channel).
    • 9-6 is the coexistence clause; 9-5 (decomposition) is not used at stage 1 (safety plan T-08).

    Stage 1 has one ASIL (B) and QM. So the question per module is binary: B, or QM with evidence.

    1.2 Classes¶

    Class Meaning Development
    B-SM implements a software safety requirement (component of sw-architecture.md section 1) part 6 at ASIL B (allocation, 6-7.4.6)
    B-SEP provides the separation other arguments rest on: scheduler, task and stack layout, interrupt lock, start-up, vector table, linker script part 6 at ASIL B or qualified per 8-12 (6-7.4.9)
    B-DEP called by ASIL B code before the safe state is reached, or set up so that an ASIL B mechanism relies on it part 6 at ASIL B or qualified per 8-12
    QM-C QM; stays QM only with the coexistence rows of section 3 argued QM process (tests, static analysis as for all code); counts as ASIL B while a row is open

    1.3 Direction of calls¶

    Interference from QM to B is what the standard names. In this code base it also enters the other way: when ASIL B code calls QM code, a fault of the QM code runs in the ASIL B context (its stack, its priority, its interrupt lock). The rule used here:

    • a QM function may be called from ASIL B code after the safe state has been reached (the outputs are de-energised by then; a fault of the callee can only delay the reset, which the MCU watchdog bounds) — example: the hard-fault dump uses printf after the safe outputs table was walked;
    • before the safe state, every callee is B-DEP or the call is removed. The linker cross-reference of the safety archives (section 2.3) is the list of such calls.

    1.4 When a QM module counts as QM¶

    A QM-C module counts as QM for a release claim only when every coexistence row of section 3 that names it has status argued or AoU. A single open row makes it ASIL B for that release. This keeps the claim honest while is not done: today 8 of the 9 QM-C modules with code in the image are ASIL B by this rule (section 0), which is the state the gap analysis described (row 6-13).

    4. The separating element at ASIL B¶

    Decision fixes that the software implementing the separation is ASIL B. Concretely, for neXtBSW on S32K1:

    Element Module Why it separates Route to ASIL B
    FreeRTOS scheduler, tick, context switch, configASSERT S-RTOS temporal separation: the safety task preempts every application task; the priorities are the argument of CA-06, CA-11, CA-14, CA-28 pre-existing: qualification per 8-12 or replacement — the route is decided in a separate task (iso-q5, rtos-comparison.md)
    Task table, priorities, stacks, OS hooks S-OSB the layout the temporal and memory arguments rest on; stack overflow reaction own development per part 6; tasks.yaml checked by nxconfig (above_application)
    MPU set-up, gate, descriptor check M-MEM (MemoryProtection) spatial separation of the supervisor; basis of every future partition own development per part 6 (already B-SM)
    ISR hooks and SAFE_ISR wrapper M-LCY (IsrHooks) opens the gate for exactly the safety interrupts own development (already B-SM)
    Interrupt lock, vector table, start-up, linker script S-INT the lock is the critical section of every monitor; the linker script places .mpu_bss and the safety stack copies of OpenBSW (lock, start-up) and own linker script: own development per part 6 where modified, 8-12 where identical

    What the S32K1 MPU can and cannot do for partitions (register facts from mcudb, hsi-s32k1xx.md):

    • The NXP system MPU grants an access if any valid region descriptor grants it. A protected window therefore has to be cut out of the full-access area: since an earlier change all 8 descriptors of S32K144 are used (descriptor 0 for the debugger and, as written by an earlier change, the other bus masters, 1, 3 and 5 for three full-access tiles around the two protected windows 2 and 4: supervisor data and safety stack, 6 for the stack guard, 7 for the tail).
    • One more protected window costs two descriptors (the window and one more tile) — so no further window fits on S32K144, S32K142, S32K146 and S32K116 (8 descriptors, all used) without freeing descriptors, and about four more fit on S32K148 (16). Consequence for a separate task: the partition model has to be designed within the 8 descriptors (or free descriptors first), and the restriction of descriptor 0 for the masters M2/M3 (AoU-41) must not need a descriptor of its own. This bounds to a two-partition model on the small derivatives: one contiguous ASIL B data window (safety-related SWC data and stacks, switched at the context switch) against everything QM (CX-6).
    • FreeRTOS on this family uses the non-MPU Cortex-M4F port: every task runs privileged, and the kernel data (task control blocks, ready lists, queues) lie in general RAM writable by every task (CX-5). The system MPU can discriminate supervisor and user accesses, but only if the kernel runs QM tasks unprivileged — which needs a port with a system-call layer. That is a question for the RTOS route: FreeRTOS has such ports only for the ARM core MPU, which S32K1 does not have (rtos-comparison.md section 2.5).

    Consequence for the argument: on S32K1, kernel data corruption by a QM task is detected, not prevented — through the timing mechanisms that the corruption would trip (MCU watchdog SM-01 … SM-03, period check SM-04, halt deadman SM-06) and the kernel asserts. Whether that detection argument is sufficient at ASIL B is decision point Q-CX1 (section 9.3).
