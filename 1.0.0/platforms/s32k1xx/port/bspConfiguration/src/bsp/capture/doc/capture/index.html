    Input capture, s32k1xx (capture)¶

    Port module of the s32k1xx family: measures period, frequency and duty cycle of a PWM input with the dual edge capture of an FTM (IO-03) and hands values and a quality to the RTE. It has no board device: it measures the input_capture[] entries of the board that the project uses (use.input_capture). Its parameters are module parameters of the project (modules.capture, project_parameters: true).

    The manifest lies next to the family driver because the module is the input capture of the s32k1xx family; the comment in module.yaml says a second family brings its own driver for the same parameters (names and derived values are family neutral, only the register encoding is not).

    State: verification mock - on a board only the time-out without an input signal has been seen (see Verification).

    Interface¶

    File Content
    platforms/s32k1xx/port/bspConfiguration/include/bsp/capture/InputCapture.h bios::InputCapture: init(), update(), get(channel) -> Measurement, getName(channel), ChannelCountAll; QUALITY_*
    InputCapture.cpp (this directory) implementation
    bsp/capture/inputCaptureConfiguration.h generated by tools/bswgen: channels, counter clock, prescaler, measurable period range, timeout and update cycle in counter ticks
    integration/captureConfiguration.h generated: the parameter values

    Measurement: frequency_mhz (milli-Hertz), period_us, duty_permille (0.1 %, at least 1 while there is a pulse), quality. Quality values are the QLF_* values of the RTE: DEBOUNCE 0 (no valid measurement yet), OK 1, TIMEOUT 8, ERROR 16 (tools/rtegen/test_rtegen.py compares both lists).

    Without any used input_capture entry the class compiles to empty functions and every channel reports noMeasurement().

    Configuration¶

    • Board: input_capture[] with name, timer instance, channel and pin (board reference). The signal is captured on the pin of the even channel of an FTM pair.
    • Project: use.input_capture selects the channels; modules.capture sets min_frequency_hz (default 50), timeout_ms (200) and update_period_ms (10), with the rule timeout_ms > update_period_ms. Ranges and the full descriptions are in the modules reference.
    • Derived by the generator: the counter prescaler from min_frequency_hz (one period must fit into half the counter range) and the counter clock from the clock model. The generator refuses a too low frequency and an update_period_ms in which the counter could wrap twice, instead of measuring wrongly.
    • RTE: rte.yaml connects ports to capture.<Channel>.<value> with <value> one of freq_mhz, period_us, duty_permille, qlf (tools/rtegen); an unconnected qlf is reported, so a component cannot mistake a kept value for a current one.

    Behaviour¶

    • init() configures and starts the counters and arms the first measurement of every channel.
    • The FTM pair (2k, 2k+1) captures two edges in one-shot mode; two measurements alternate on each channel: period (rising to rising edge) and pulse (rising to falling edge, the high time). The counter runs freely over its whole range, so no interrupt is used: update() reads what the hardware captured, re-arms the other measurement and derives frequency, period and duty cycle.
    • A value is QUALITY_OK only if a period and a pulse measurement of the same channel completed within the timeout and the period lies inside the configured range. Otherwise the last valid values are kept and the quality says why: TIMEOUT for a missing signal (no edges, also a constant level), ERROR for a period out of range, an implausible pulse, or an update() that came too late (two consecutive calls saw a counter overflow).
    • update() and get() have no lock and must run in one task; the generated RTE plans both into the same task. update() has to be called every update_period_ms.

    Limits and known gaps¶

    • s32k1xx FTM only; no driver of another family exists for these parameters.
    • The positive measurement (period, duty cycle, range checks) has not been done on a board; according to module.yaml it needs a signal source or bridge on the board.
    • Host tests exist, but tools/test/tests.yaml names them under tools/bswgen/test/capture_host, outside this directory, so the modules reference shows "Host tests: none" for this module.

    Tests¶

    tools/test -k bswgen (entry bswgen, group python), in tools/bswgen/test_bswgen.py:

    • BswGenCaptureTest - generator: register values, prescaler, range and refusals from board, project parameters and clock model, on an own profile with two channels on two counters;
    • BswGenCaptureHostTest - compiles InputCapture with the generated configuration and runs tools/bswgen/test/capture_host/input_capture_host_test.cpp against a RAM model of the FTM with the real register layout: register configuration after init, alternating measurements, normal, very small and very large duty cycle, counter overflows, missing signal, period below and above the range, a late update(); against the eval board demo profile and a test profile. no_capture_host_test.cpp covers a project without a capture channel.

    Verification¶

    From module.yaml: verification: mock - "On the eval board only the time-out without an input signal is confirmed; period, duty cycle and the range checks are covered by generator and host tests only."
